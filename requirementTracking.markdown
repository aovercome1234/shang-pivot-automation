# 从代码反推需求与文档 —— 操作手册（v2）

> 用途：面对一个只有代码、缺少或不可信需求文档的系统，产出一套**可复算、可对版本负责**的需求/设计/数据/业务文档，并让它能支撑跨版本验证与自动化。
> 核心原则：**机器优先反推 + 人只对判断负责 + 证据钉死在版本上 + 空白与反例同等重要**。

---

## 0. 修订说明：相对初稿（v1）的 15 处修正

保留初稿可用的骨架（分层反推、证据引用、不确定标注、局限声明），修正以下问题。左边是初稿原文，右边是 v2 的处置。

| # | 初稿的问题 | 性质 | v2 处置 |
|---|---|---|---|
| 1 | §1 说「代码最难反推为什么做」，§3 第二层却要求 AI 输出「用户故事：作为…**我要…以便…**」 | 自相矛盾 | 「以便」默认标 `推测`；只有代码内有注释、菜单文案、PRD 残留、commit message 佐证时才升为 `已确认`（§5） |
| 2 | §5 列「交叉验证 = 让另一个模型独立分析」并放在验证第一位 | 逻辑错误 | 模型互证**不是验证**，只是假设生成器：共享训练数据的两个模型会以同样的方式自信地错。验证改为三级：机器交叉 → 可执行验证 → 人工确认（§6） |
| 3 | §5「让 AI 生成新测试，跑一遍，失败说明理解错」 | 推理错误 | 测试失败有四种归因（断言错/理解错/环境错/代码本身有 bug），不能直接推「我理解错」。改为先做归因判定表，再决定改文档还是报缺陷（§6.2） |
| 4 | 全篇没有「谁的真值更高」，只在 §5 说「找矛盾」 | 关键缺失 | 新增真值层级，并**按断言类型分域**（行为断言 vs 端点存在性断言方向相反，必须分开声明）（§2.1） |
| 5 | 证据只要求「文件、函数、行号」 | 致命退化 | 行号会随下一次提交失效。证据必须写成 `路径:行号 @ <版本指纹>`，并给出复算命令（§2.2） |
| 6 | 不确定只有 `【推测】` 一个布尔标记 | 表达能力不足 | 改为四级置信度 + 独立的「验证状态」维度 + 确认方式与责任人字段（§5） |
| 7 | 「让 AI 找矛盾」之后没有闭环 | 流程断裂 | 矛盾与未知必须进**待确认单**，每条有 owner、决策期限、处置结论；未处置项计入交付门禁（§7.3、§11） |
| 8 | 六个层被写成 1→6 的严格顺序 | 顺序错误 | 改为「机器可提取的先做、需判断的后做」：入口/契约/迁移/枚举先提，行为与产品设计后推；层间是迭代而非流水线（§3） |
| 9 | 只反推「有什么」 | 遗漏一半价值 | 新增 `负面清单`（negative space）：代码里**没有**的东西——缺失的校验、缺失的索引、开了开关却没消费的注解。这类发现往往是最有价值的需求结论（§4.7） |
| 10 | 工具清单泛化（Sourcegraph/madge/SchemaSpy/Storybook…） | 噪声 | 删掉。改为「先确认本仓库已有什么生成器，没有再加工具」，并给出本项目实际可跑的清单（§3.1） |
| 11 | 反推出的文档是一次性产出 | 必然腐坏 | 拆成「机制区（脚本生成，禁止手改）」与「判断区（人工维护）」，机制区带 diff 门禁，腐坏即红灯（§7、§8） |
| 12 | 没有「已宣称 vs 已实现」对照 | 遗漏核心目标 | 新增该对照步骤——反推需求的首要用途就是找出「宣称做了但演示不出来」和「做了但没人知道」的差集（§4.2） |
| 13 | §7 把「许可证、隐私、商业秘密」放在末尾当脚注 | 风险优先级错误 | 合规前置为第 0 步硬门槛：脱敏、密钥、个人数据、外部模型投喂范围（§9） |
| 14 | §6 步骤 4「让 AI 找矛盾与缺口」无输入契约 | 不可执行 | 矛盾检查改为**确定性的四源对账**（代码 / OpenAPI / 迁移 / 测试），可脚本化、可复算（§6.1） |
| 15 | 通篇没有「版本」概念 | 与目标不匹配 | 新增版本化：版本指纹、基线快照、跨版本 diff 门禁，让文档能回答「这个结论对哪个版本成立」（§8） |

一句话概括修正方向：把初稿从「让 AI 写文档的提示词集」改造成「**机器产事实、人产判断、证据钉版本、差异自动报警**的交付流水线」。

## 1. 先确定目标与边界

### 1.1 反推目标（三选一或组合，输出物不同）

- **反推需求**：业务规则表、状态机、验收标准、异常边界、已宣称 vs 已实现差集。
- **反推产品设计**：页面清单、信息架构、交互状态、权限矩阵、表单校验、空态/错误态。
- **反推技术设计**：模块边界、对外契约（API）、数据模型、状态与集成关系。

### 1.2 反推的能力边界（先接受，别硬撑）

| 能可靠反推 | 只能弱反推（必须标置信度） | 无法反推 |
|---|---|---|
| 已实现的端点、字段、枚举、状态流转 | 业务意图、优先级排序 | 商业目标 |
| 参数校验与错误码 | 用户动机、真实使用场景 | 未实现的需求 |
| 数据模型与约束 | 非功能需求的**目标值**（性能/可用性指标） | 「为什么这么做」的取舍过程 |
| 已实现的机制（缓存/重试/幂等/审计） | 合规要求的适用范围 | 组织与流程约束 |

结论：**代码反推的是「已实现需求」，不是原始需求。** 任何写着「为什么」的结论默认都是推测。

## 2. 三条铁律

### 2.1 铁律一：真值层级按「断言类型」分域

不要用单一层级覆盖所有断言——不同断言类型的真值方向确实相反，混用必然自相矛盾。

| 断言类型 | 真值层级（高 → 低） | 理由 |
|---|---|---|
| **端点/字段是否存在、路由是否注册** | 源码 > OpenAPI/Schema > 手写文档 > PRD | 源码是唯一可执行的事实 |
| **业务行为是否正确、取值是否合规** | 业务预期确认表 > 接口文档/OpenAPI > 源码 | 源码可能本身有 bug；「代码这么写的」不等于「业务要这样」 |

两条都要在文档里显式声明适用范围，否则同一份文档会自相矛盾。
**发现跨层冲突时：不静默择一。** 记录到待确认单，并同时标注「按源码实际行为」与「按业务预期」两个值。

### 2.2 铁律二：证据钉在版本上

证据格式（缺一不可）：

```text
<相对路径>:<行号或符号> @ <版本指纹>
```

- 版本指纹 = `commit sha`（+ 可选 `tag`）。**只写行号不写版本的证据，在下次提交后即失效，等于没有证据。**
- 优先引用**符号名**（类名/方法名/常量名）而非纯行号：符号比行号抗重构。
- 每条机制区结论都要能用一条命令复算（§3.1）。写不出复算命令的结论，降级为「推测」。

### 2.3 铁律三：机器优先，人只对判断负责

| 交给机器（可复算、应脚本化） | 交给人（判断、不可复算） |
|---|---|
| 端点清单、字段清单、枚举清单、路由清单 | 业务意图、优先级、取舍 |
| 四源对账（代码/契约/迁移/测试的差异） | 「这个差异是缺陷还是设计」的定性 |
| 覆盖率、追溯矩阵、版本 diff | 验收标准的确认 |
| 文档骨架与表格生成 | 反例的重要程度排序 |

**先翻本仓库已有的生成器，再考虑写新的或装工具。** 已经有 `build_api_doc.py` 这类生成器时，重写一遍是纯浪费，且会引入第二套真相。

## 3. 反推顺序：按「可机械化程度」排，不按抽象层次排

初稿把「系统地图 → 功能 → 规则 → 数据 → 产品 → 非功能」当流水线，实践上会反复返工。正确顺序是先拿能机器提取的事实，再在其上做判断：

```text
第 0 步  合规与脱敏闸门（§9）                       ← 不过不许开始
第 1 步  入口与契约提取（路由/端点/消费者/定时任务）  ← 机器
第 2 步  数据模型提取（迁移/实体/枚举/约束）          ← 机器
第 3 步  业务规则与状态机提取（分支/校验/状态流转）    ← 机器提候选 + 人确认
第 4 步  已宣称 vs 已实现对照                        ← 机器求差集 + 人定性
第 5 步  产品设计反推（页面/交互/权限）               ← 半机器
第 6 步  非功能与运维（机制清单，不是需求）            ← 半机器
第 7 步  负面清单（缺什么）                          ← 机器求空集 + 人判断是否有意
第 8 步  四源对账 + 待确认单闭环                      ← 机器 + 人
```

### 3.1 第 1 步之前：先盘点「本仓库已有什么能跑」

不要假设什么都要自己写。按下列顺序问：

1. 有没有 OpenAPI/Swagger 产物？能否本地起服务导出？→ 有则直接拿，但仍要**与源码对账**（注解可能漏写）。
2. 有没有代码生成器/文档生成脚本（`scripts/*.py`）？→ 直接复用并读它的真值层级声明。
3. 有没有机读产物（`*.json` 模型、`junit.xml`、结果文件）？→ 这些是自动化与 diff 的天然输入。
4. 有没有既有的用例清单与稳定 ID 体系？→ 追溯矩阵直接复用，不新造 ID。
5. 都没有，才考虑装工具。

本项目可跑清单（示例，按需取用）：

| 目的 | 命令 | 产物 |
|---|---|---|
| 端点契约 | `python3 api_testcases/scripts/build_api_doc.py --repo-root .. --openapi ../docs/openapi-v3-api-docs.json --out ../docs/测试资料/接口文档.md --diff ../api_testcases/artifacts/api-doc-diff.md` | `接口文档.md` + `endpoint-model.json` + 差异表 |
| 数据库字典 | `python3 api_testcases/scripts/build_db_dict.py` | `docs/06-baseline/01-数据字典.md` + `api_testcases/artifacts/schema-model.json` |
| 冻结版本基线 | `python3 api_testcases/scripts/snapshot_baseline.py --label <版本标签>` | `api_testcases/baselines/<版本标签>/`（含 `manifest.json` 指纹表） |
| 用例规范门禁 | `python3 api_testcases/scripts/case_lint.py` | `lint-report.json/md` |
| 三件套对账 | `python3 api_testcases/scripts/reconcile.py` | `reconcile-report.md` |
| 跨版本 diff | `python3 api_testcases/scripts/baseline_diff.py --old baselines/<旧标签> --new artifacts` | 破坏性变更清单 + 受影响用例前缀（退出码 1 = 有破坏性变更） |
| 发布判据 | `python3 api_testcases/scripts/release_gate.py` | C1–C8 结果 |

## 4. 六个提取层（保留初稿骨架，补输入/产出/门槛/反例）

每层都必须输出：**结论 + 证据（含版本指纹）+ 置信度 + 反例（不该被计入的东西）**。

### 4.1 第一层：系统地图

输入：构建文件（pom/package.json）、模块目录、主类/入口、配置、依赖清单。
产出：技术栈与版本、模块边界与依赖方向、入口清单（HTTP/CLI/消息/定时任务/前端路由）、外部集成、**未接线模块**（写了但没人调的模块/空接口）。
出口门槛：模块依赖方向画出，且与构建文件一致；每个入口能指向注册处。

### 4.2 第二层：功能与「已宣称 vs 已实现」对照

这一层是初稿缺失的、也是反推需求的首要用途。

输入：第一、二步的机器产物 + 既有 PRD/README/宣传文案 + 种子数据。
产出：

- 功能清单，每条含：功能名、触发入口、角色与权限、输入输出、主流程、分支规则、状态变化、异常边界、涉及实体、验收标准（Given/When/Then）。
- **差集表**：
  - 「宣称了但实现不了」——README/PRD 说有，但种子里没有可演示数据、或没有对应端点；
  - 「实现了但没人在用」——端点存在但无前端调用、无菜单入口、无测试覆盖。
- 「以便」（业务动机）默认标 `推测`。

出口门槛：每条宣称功能都能指向「演示数据 + 调用入口」，否则列入差集表。

### 4.3 第三层：业务规则提取

输入：分支/守卫/校验/状态变更/计算逻辑/定时任务/枚举与错误码常量。
产出规则表：

```text
规则ID | 条件 | 动作 | 例外 | 影响实体 | 证据(file:line @版本) | 置信度
```

补充初稿漏掉的高密度规则源（比散落的 if 更好用）：
- **错误码枚举**（每个码就是一条业务约束的浓缩）；
- **状态枚举与状态流转**（能直接推出状态机与非法迁移）；
- **数据库 CHECK 约束**（不变量写在 SQL 里的部分）；
- **迁移历史**（决策时间线：每次改动都是一个过去的决策）；
- **权限/菜单种子数据**（实际生效的角色边界）。

### 4.4 第四层：数据模型反推

输入：迁移文件（唯一权威）、实体类、类型处理器、索引与约束、种子数据。
产出：实体与关系、字段（名/类型/可空/默认/约束/索引）、枚举与状态、**最终态**（把所有增量合并后的样子）、逻辑引用关系（无外键时明确标注）、跨切面列的适用范围。
出口门槛：**实体 ↔ 表 双向零缺漏**（无「有实体没表」也无「有表没实体」），并明确标注所有无 DB 外键约束的关系。

### 4.5 第五层：产品设计反推

从路由、组件、状态管理、i18n、表单校验、路由守卫反推：页面清单、用户流程、表单字段与联动、列表筛选/排序/分页、加载/空/错误/无权限四态、权限矩阵。
**注意区分「前端拦」与「后端拦」**：前端守卫常常只是体验优化，真正的授权在后端——两者不一致本身就是一条重要结论。

### 4.6 第六层：非功能与运维（只记录机制，不假装知道目标）

从缓存、重试、限流、幂等、审计、日志、追踪、错误码、配置反推。
**限定表述**：只能说「已实现的机制是 X」，不能说「要求达到 Y」。目标值是需求，代码里没有。
产出：机制清单 + 该机制覆盖范围 + 未覆盖范围（例如「有审计注解但登录接口未标注」）。

### 4.7 第七层（新增）：负面清单

反推「没有什么」和反推「有什么」同等重要。逐类求空集：

- 有鉴权开关但没有任何方法级授权注解 → 「全站只有粗粒度 URL 鉴权，无接口级权限校验」；
- 有软删除列但没有唯一约束的软删适配 → 「可重复插入已删数据」；
- 有状态字段但没有状态机守卫 → 「存在非法状态迁移路径」；
- 有分页封装但有接口没接 → 「该列表全量返回」；
- 有审计注解但关键写接口遗漏 → 「审计有盲区」。

每条负面发现要标：**有意省略 / 遗漏缺陷 / 待确认**。三者处置完全不同。

## 5. 置信度与验证状态（替代单一 `【推测】`）

结论必须带两个独立维度：

**置信度**

| 标记 | 含义 | 依据 |
|---|---|---|
| `已确认` | 有代码证据且有业务方/权威文档确认 | 证据 + 确认记录 |
| `高置信` | 代码证据完整、无矛盾源 | 两处以上独立证据 |
| `推测` | 单点证据或推断得出 | 一处证据 |
| `未知` | 无证据 | 待确认单 |

**验证状态**（与置信度解耦：高置信也可能「未验证」）

| 标记 | 含义 |
|---|---|
| `机器可复算` | 有命令能重算，结果是确定的 |
| `可执行验证` | 有测试会因该结论为假而失败 |
| `仅人工确认` | 只能靠访谈/文档 |
| `未验证` | 尚无任何验证 |

每条结论填：`置信度 / 验证状态 / 确认方式 / 责任人`。缺任一项即为不合格条目。

## 6. 验证协议（顺序不可颠倒）

### 6.1 一级验证：机器交叉（确定性，必须全做）

**四源对账**，两两求差集，而不是「让 AI 找矛盾」：

| 源 | 常见不一致 |
|---|---|
| 源码注解/路由 | 注解漏写、条件注册、被 Bean 条件关掉的端点 |
| OpenAPI/Schema 产物 | 与实际返回体不一致、未展开的 Map 参数 |
| 数据库迁移 | 实体字段无对应列（或反之）、迁移被后续迁移抵消 |
| 测试与 fixture | 测试断言与源码行为不一致、测试依赖已删除的数据 |

不一致必须**逐条给判定**：源码对 / 契约对 / 两者都对（描述口径不同）/ 待确认。
判定为「源码对」时，同步修正契约产物；判定为「契约对」时，这是一条**缺陷线索**，进缺陷流程。

### 6.2 二级验证：可执行验证（用测试当探针）

生成的验证用例要**故意设计成「如果结论为假就失败」**。测试失败时按归因表处理，禁止直接得出「我理解错了」：

| 现象 | 可能归因 | 处置 |
|---|---|---|
| 断言与源码行为一致地失败 | 文档结论错 | 改文档，并在结论里记录反例 |
| 断言失败但源码看起来是对的 | 测试写错 / 数据前置不满足 | 修测试，不改文档 |
| 失败与前置数据/环境有关 | 环境或种子数据不匹配 | 修环境，重跑；环境不可复算则整条结论降级 |
| 测试通过但违反业务常识 | **代码缺陷** | 报缺陷，不要把它写进需求文档当「规则」 |

前置要求：**可复算的环境**（版本指纹一致、种子数据可重建、账号可获取）。环境不可复算时，二级验证不可用——此时必须在文档里写明「本结论未做可执行验证」。

### 6.3 三级验证：人工确认

代码只能说明「怎么做」，不能说明「为什么」。人工确认的对象**只有**这三类：

1. 所有 `推测`/`未知` 条目；
2. 所有四源对账的「待确认」条目；
3. 所有负面清单里判为「遗漏缺陷」或「有意省略」的条目。

确认结果写入待确认单，形成闭环（§7.3）。

**模型互证只用于生成候选假设，不写入验证状态。** 若确实做了双模型交叉，结论里记「双模型一致，未验证」，绝不能记「已确认」。

## 7. 产物契约

### 7.1 机制区 vs 判断区（决定文档会不会腐坏）

| 区 | 内容 | 谁写 | 是否手改 | 腐坏防线 |
|---|---|---|---|---|
| **机制区** | 端点清单、字段字典、枚举、路由表、覆盖率、追溯矩阵、版本指纹 | 脚本生成 | **禁止手改** | 生成后 diff 必须为空，否则红灯 |
| **判断区** | 业务规则语义、验收标准、优先级、差集定性、待确认单 | 人工/Agent 撰写 | 人工 | 每条带置信度与证据；定期复审 |

机制区文件头必须写：**生成命令 + 生成时的版本指纹**。改机制区内容 = 改生成脚本，再重新生成。

### 7.2 命名与 ID 纪律

- 机制产物与判断产物分目录，文件头互相引用。
- **复用既有稳定 ID 体系，不新造**：契约用例 `METHOD_PATH-NNN`、业务用例 `BUS-<域>-NNN`、UI `UI-<域>-NNN`、规则 `R<n>`、契约文档规则编号沿用既有编号段。
- 每条需求/规则至少能被一条用例 ID 引用（可追溯），无法被引用的条目要么补用例，要么降级为「背景信息」。

### 7.3 待确认单（把「问题清单」变成有闭环的台账）

初稿只说「列出需业务方确认的问题」，没有闭环，问题会永远悬空。改为台账，字段：

```text
编号 | 问题 | 影响(哪条结论/哪个版本) | 置信度 | 需要的决策人 | 期限 | 处置结论 | 处置时间 | 落地改动
```

规则：
- 任何 `推测`/`未知`/`待确认` 条目必须在此台账中出现；
- 未处置条目数计入交付门禁（按严重度分级：阻塞发布的必须清零）；
- 处置结论要回写到对应的判断区文档，并把置信度升级为 `已确认`。

## 8. 版本化：让文档能回答「对哪个版本成立」

这是初稿完全缺失、而交付最需要的一环。

### 8.1 版本指纹

一次反推的所有产物，必须共享同一个指纹：

```text
version_fingerprint = commit_sha + 关键文件 sha256(迁移目录/契约产物/构建文件) + 生成时间
```

没有指纹的文档集，无法参与跨版本验证——因为你不知道它描述的是哪一版。

### 8.2 基线快照

把机制区产物复制为不可变快照（`baseline/<版本>/`），与判断区文档的版本对应。快照内容：
端点模型 JSON、schema 模型 JSON、路由清单、枚举与错误码清单、种子数据摘要、账号与运行参数。

### 8.3 跨版本 diff 门禁（自动化落点）

任意两个版本之间，机器自动产出三类变更：

| 类别 | 例子 | 门禁动作 |
|---|---|---|
| **破坏性** | 删端点、改路径/方法、删字段、收窄类型、加 NOT NULL 无默认、改枚举取值 | 红灯：必须出迁移/兼容方案与用例更新 |
| **行为性** | 新增必填校验、改错误码、改状态流转、改默认值 | 黄灯：必须更新业务规则文档与受影响用例 |
| **增量** | 新增端点/字段/表/枚举 | 绿灯：补用例即可 |

配套动作：diff 结果直接映射到「需要更新的用例 ID 集合」，这样版本升级不会漏测。

---

## 9. 第 0 步：合规与脱敏（硬门槛，前置）

在把任何代码投喂给外部模型或写入文档之前：

- **禁止出仓**：密钥、令牌、证书、`.env` 实际值、连接串、生产地址；
- **个人数据脱敏**：手机号、地址、身份证、openid 等一律脱敏后再进文档与样例；
- **样例数据**用演示账号，不用生产数据；文档里的账号写明「演示账号」；
- **只处理有权限的代码**：遵守许可证与商业秘密边界，确认反推产物的分发范围；
- **审计留痕**：记录投喂范围（哪些文件/哪些模型）与脱敏方式。

本项目已有可复用实践：账号与令牌全部走环境变量、日志对密码/令牌/`configValue` 打码、`operation_log` 审计异步落库。反推文档沿用同一套纪律，不另立标准。

## 10. 最小可行流程（可执行清单）

```text
1. 合规闸门：确认投喂范围与脱敏方式（§9）。
2. 盘点既有生成器与机读产物（§3.1），能复用的先跑一遍，确认复算结果与仓库一致。
3. 生成机制区产物：端点清单、数据字典、路由清单、枚举与错误码清单（机器）。
4. 打版本指纹，冻结基线快照（§8.1、§8.2）。
5. 提规则候选：从错误码、状态枚举、CHECK 约束、迁移历史、权限种子数据里抽（机器提 + 人筛）。
6. 做「已宣称 vs 已实现」差集（机器求差 + 人定性）。
7. 做负面清单（机器求空集 + 人定「有意/遗漏/待确认」）。
8. 四源对账，逐条判定，冲突进待确认单（§6.1）。
9. 写判断区文档：业务规则表、状态机、验收标准（每条带证据+置信度+验证状态）。
10. 生成「如果结论为假就失败」的验证用例，跑一遍并按归因表处置（§6.2）。
11. 人工确认待确认单，闭环回写（§6.3、§7.3）。
12. 把机制区生成 + 对账 + diff 挂进 CI/门禁：机制区 diff 非空即红灯（§8.3）。
```

## 13. 局限（保留初稿的诚实，并补两条）

初稿 §7 成立的部分照旧：代码反推的是已实现需求；死代码/特性开关/历史兼容会污染判断；模型会幻觉，必须要求证据与置信度；商业目标与未实现需求无法反推。

补充两条：

- **机制区再完美，也只覆盖「机器看得懂」的部分**；真正的业务语义仍需人确认。文档的可信度上限由人工确认量决定，不由生成量决定。
- **行号会失效，结论不会自动失效**——但如果不做版本指纹与复算，你的结论会静默失效而无人察觉。这是本方法最大的失败模式，也是 §2.2 与 §8 存在的唯一理由。

一句话：**机器负责提取、对账、生成与报警；人负责确认意图、取舍与最终需求；版本指纹负责让这一切在下一次提交后仍然站得住。**

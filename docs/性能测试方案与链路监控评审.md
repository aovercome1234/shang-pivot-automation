> 当前目标环境：仓库历史文档中的 `111.170.33.2` 是既有可观测平台地址，不与本次目标混用。
> 状态：方案已评审；读链路 trace 完整性已验证；登录链路已验证 Redis/SQL，代码方法 span 待按本文配置补齐后复验。

## 1. 背景与目标

### 1.1 目标

1. 建立可重复执行的性能测试方案，覆盖读链路、登录链路、核心写链路、突发流量和稳定性观察；
2. 压测过程中能从“客户端指标 → 接口指标 → 代码方法 → SQL → Redis/MQ/对象存储”逐层定位瓶颈；
3. 通过单接口探针验证链路追踪完整性，确保压测数据可分析、可复现、可归因；
4. 性能测试结果能沉淀为报告、缺陷和优化任务。

### 1.2 非目标

- 不在公网入口直接做破坏性容量压测；
- 不把接口自动化功能测试替代性能测试；
- 不在未确认数据备份和库存保护前执行大批量写链路；
- 不把 SkyWalking trace 完整性等同于容量结论：容量结论还需要资源指标和业务指标同屏。

### 3.2 初始容量目标与负载模型

以下目标是**首轮基线目标**，不是宣称系统已经满足；首轮执行后按实测结果标定正式容量目标。

| 链路 | 初始目标 | 默认阈值（与 k6 脚本一致） |
|---|---:|---|
| 浏览读链路 | 50 VU，3 分钟稳定执行 | 失败率 <1%；断言 >99%；p95 <800ms；p99 <1500ms |
| 登录链路 | 10 RPS，2 分钟稳定执行 | 失败率 <1%；断言 >99%；p95 <800ms；p99 <1500ms |
| 下单/支付写链路 | 2 VU，1 分钟，一账号一 VU | 失败率 <1%；断言 >99%；p95 <1500ms；p99 <3000ms |
| 稳定性 | 预期峰值的 50%，30 分钟 | 无持续增长内存/连接池占用；无持续错误；无 MQ 积压 |

阶梯加压策略：

```text
Smoke → Baseline → Step-up → Stress → Endurance
1 VU    10 VU       30→50→80  逐步加压到阈值边界  50% 峰值运行 30 分钟
```

压测期间的中止条件：

- HTTP 失败率连续 1 分钟 >5%；
- 出现未解释 500 或错误 trace 快速增长；
- 出现库存超卖、重复支付、重复订单；
- DB 连接池耗尽、线程池耗尽、MQ 持续积压；
- 服务器 CPU/内存达到运维侧安全阈值；
- 收到告警后必须先冻结负载，再分析 trace 与日志。

### 3.3 数据准备与隔离

1. **商品与类目**：使用演示环境已有在售 SKU；压测前记录库存快照；
2. **会员账号**：登录/写链路使用手机号池，不使用真实用户；短信验证码使用演示环境固定码；
3. **管理端账号**：仅用于预检和管理端场景；
4. **库存保护**：写链路只跑沙箱支付，不跑真实库存耗尽场景；压测前补足库存并保留 DB 快照；
5. **幂等**：下单必须携带幂等键，防止网络重试造成重复订单；
6. **订单数据**：压测订单使用统一备注/幂等键前缀，便于筛选；不自动删除证据数据；
7. **证据保存**：每轮保存 k6 结果、SkyWalking trace 查询条件、慢接口 TopN、慢 SQL、告警记录。

### 3.4 执行步骤

> 优先在目标服务器内网入口执行 k6，避免公网波动；如果 `platform.sh` 的默认 SSH 地址与目标环境不同，必须显式设置 `SHANG_SSH_HOST/SHANG_SSH_PORT/SHANG_SSH_KEY_NAME`，或直接在目标服务器执行 k6。

```bash

  --base-url http://49.233.135.247:60084 \
  --path '/api/search?q=iPhone' \
  --out artifacts/observability/skywalking-trace-check.json

# 1. k6 预检；账号口令放在目标服务器 /root/k6/shang/.env，不写进命令行
cd observability
export SHANG_SSH_HOST=49.233.135.247
export SHANG_SSH_PORT='<ssh-port>'
export SHANG_SSH_KEY_NAME='<ssh-key>'
# 若目标服务器 9090 没有 Prometheus，显式指定可达的 remote write：
# export K6_PROMETHEUS_RW_SERVER_URL='http://<prometheus-host>:9090/api/v1/write'
bash ./scripts/platform.sh k6 preflight.js \
  -e BASE_URL=http://127.0.0.1:8090/api \
  -e ADMIN_BASE_URL=http://127.0.0.1:8091/admin

# 2. 浏览型读负载（沿用上面的 SHANG_SSH_* 与 K6_PROMETHEUS_RW_SERVER_URL）
bash ./scripts/platform.sh k6 browse-load.js \
  -e BASE_URL=http://127.0.0.1:8090/api \
  -e STAGES=30s:10,2m:30,3m:50

# 3. 登录风暴
bash ./scripts/platform.sh k6 login-load.js \
  -e LOGIN_TARGET=customer -e BASE_URL=http://127.0.0.1:8090/api \
  -e PHONES='<phone1>,<phone2>,<phone3>' -e RATE=10 -e DURATION=2m

# 4. 写链路（确认库存充足后执行）
bash ./scripts/platform.sh k6 checkout-smoke.js \
  -e BASE_URL=http://127.0.0.1:8090/api \
  -e PHONES='<phone1>,<phone2>' -e VUS=2 -e DURATION=1m
```

如果只能走公网入口，则把 `BASE_URL` 换成 `http://49.233.135.247:60084/api`，但结果必须标注“包含公网网络波动”，不能作为服务端容量结论。

## 4. 链路监控体系

### 4.1 链路分层

```text
k6 / 自动化客户端
  ├─ 客户端指标：RPS、p95/p99、失败率、断言通过率
  └─ 请求入口：http://49.233.135.247:60084/api/**
        ↓
nginx / 网关入口
        ↓
SkyWalking Java Agent（shang-pivot）
        ├─ 接口 span：GET:/api/search
        ├─ 代码 span：Controller / Service / 业务方法
        ├─ SQL span：PostgreSQL/JDBC/PreparedStatement/executeWithFlags
        ├─ Redis span：验证码、缓存、锁定、黑名单（涉及登录链路时）
        ├─ MQ span：订单支付事件、消费、DLQ（涉及写链路时）
        └─ 对象存储 span：文件上传/下载（涉及文件链路时）
        ↓
SkyWalking OAP → UI / GraphQL 查询
```

### 4.2 每类接口的最低追踪要求

| 接口类型 | 必看层级 | 验收标准 | 当前状态 |
|---|---|---|---|
| 只读接口 | 接口、Controller、Service、SQL | Entry span + 代码 Local span + JDBC SQL span | 已通过 `GET /api/search` 验证 |
| 登录接口 | 接口、Controller、Service、Redis、DB | 能看到验证码/锁定/黑名单 Redis 行为、会员 DB 行为和代码方法 | Redis/DB 已验证；代码 span 待补 |
| 下单/支付 | 接口、Service、DB、库存、MQ | 能看到订单/支付 SQL、库存变化、ORDER_PAID 事件或 MQ span | 待执行写链路探针 |
| 管理端写接口 | 接口、Service、SQL、软删 | 能看到 insert/update/delete SQL 及操作上下文 | 待执行管理端探针 |
| 批处理/定时任务 | Job、Service、SQL | 能看到 `SpringScheduled/...` span 与对应 SQL | 待复验 |

### 4.3 指标口径

- **客户端**：k6 `http_req_duration`、`http_req_failed`、`checks`；
- **接口**：SkyWalking endpoint CPM、响应时间、SLA、错误 trace；
- **代码**：Controller / Service / Mapper Local span 耗时；
- **SQL**：JDBC span 的 `db.statement`、`db.instance`、`peer`、耗时；
- **中间件**：Redis / MQ / 对象存储虚拟服务调用；
- **系统资源**：目标环境的 JVM、GC、线程池、DB 连接池、CPU、内存指标需要与 SkyWalking trace 同屏或同时间窗对齐；如果目标环境没有 Prometheus/actuator/node_exporter，容量结论前必须补齐。

### 4.4 代码方法级追踪补齐

当前 `GET /api/search` 已具备代码方法 span；登录链路能看到 Redis/DB，但缺少 `CustomerAuthController/CustomerAuthService` 方法 span。已准备建议配置：

- [agent-trace-methods.conf](/Users/liushu/IdeaProjects/shang-pivot-automation/observability/skywalking/agent-trace-methods.conf)

配置覆盖登录、商城浏览、购物车、地址、下单、支付、售后、评价等核心 Controller/Service 方法。部署后需要重启 `shang-pivot`，然后复验。
登录探针在测试手机号不存在时会自动创建会员记录（随后更新登录时间），必须使用手机号池中的测试号码，不能用真实用户号码：

```bash

```

### 4.5 常用 SkyWalking 查询

- 服务：`findService(serviceName: "shang-pivot")`
- 端点：`findEndpoint(keyword: "GET:/api/search", serviceId: <service-id>)`
- trace 列表：`queryBasicTraces(condition: {serviceId, queryDuration, traceState: ALL, queryOrder: BY_START_TIME})`
- trace 明细：`queryTrace(traceId: <trace-id>)`
- 慢请求：`minTraceDuration > 500`
- 错误请求：`traceState: ERROR`

自动验收脚本：

```bash

  --base-url http://49.233.135.247:60084 \
```

## 5. 单次接口验证结果

### 5.1 读链路：`GET /api/search?q=iPhone`

| 检查项 | 结果 | 证据 |
|---|---|---|
| 业务接口 | 通过 | HTTP 200，`code=0`，业务 `traceId=5af4d63cdfd942438408927c2ba07060` |
| SkyWalking 服务 | 通过 | `shang-pivot` normal=true |
| 接口层级 | 通过 | Entry span `GET:/api/search` |
| 代码层级 | 通过 | `StorefrontController.search`、`CatalogReadService.search`、`CatalogReadService.toCard` |
| SQL 层级 | 通过 | `commerce.spu` 检索 SQL、`commerce.sku` 查询 SQL |
| Redis/MQ | 本接口不适用 | 拓扑中已有 Redis/PostgreSQL/对象存储依赖 |

SkyWalking trace：`773d3a694ef34b3bb06d2eb0380d3667.61.17937832570880005`

链路样例：

```text
GET:/api/search
└─ StorefrontController.search
   └─ CatalogReadService.search
      ├─ SELECT COUNT(*) ... FROM commerce.spu ...
      ├─ SELECT ... FROM commerce.spu ... ORDER BY sold_count DESC LIMIT ?
      └─ CatalogReadService.toCard
         └─ SELECT ... FROM commerce.sku WHERE spu_id = ? AND status = ?
```

性能观察点：一次搜索响应中出现 2 次 `CatalogReadService.toCard` 和 2 次 `commerce.sku` 查询，呈“按 SPU 循环查 SKU”的 N+1 查询嫌疑；压测时需观察 SKU 查询次数是否随结果数线性增长。

评审方式：方案文档评审 + 仓库脚本核验 + SkyWalking 实测证据复核。

| 评审点 | 结论 | 说明 / 条件 |
|---|---|---|
| 场景覆盖 | 有条件通过 | 读、登录、写脚本已就绪；spike/稳定性/管理端脚本需固化后再作为正式场景 |
| 负载控制 | 通过 | 从 smoke 到阶梯再到压力；有明确中止条件 |
| 数据风险 | 有条件通过 | 写链路前必须备份/补足库存；订单数据需带统一标识 |

| 链路追踪（写/MQ） | 待验证 | MQ 虚拟服务已注册；需执行支付探针或 smoke 后复验 |
| 指标完整性 | 有条件通过 | SkyWalking trace 已可用；容量结论需要 JVM/DB/主机指标同屏 |

**评审结论：读链路通过；登录/写链路在补齐代码方法 span 并完成复验后，才能判定全链路完整。**

执行前置条件：

1. 写链路压测前确认库存和订单数据安全；
2. 优先在目标服务器内网入口执行 k6，公网入口只做连通性和体验抽样；
3. 确认目标服务器存在可达的 Prometheus remote write（或设置 `K6_PROMETHEUS_RW_SERVER_URL`），否则 k6 客户端指标无法启动写入；
4. 应用 `agent-trace-methods.conf` 后重启应用，并复验登录/支付/下单 trace；
5. 容量结论前补齐或确认 JVM/DB/主机指标；
6. 压测期间临时调高采样率，压测结束后恢复并复核配置。

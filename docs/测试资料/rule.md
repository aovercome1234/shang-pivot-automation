> v1.0 由 DeepSeek 生成（生成方法论）；v2.0 由工程实践反向固化（命名标准、字段标准、门禁与评审）；

> 本文档是用例生成、编写、校验、上传的唯一权威规范。生成前必读，上传前必过 lint。
> 更新日期：2026-10-05。变更记录见文末。

## 0. 适用范围

当输入包含接口文档、OpenAPI/Swagger、抓包、代码、业务规则时，按本规范生成接口测试用例。
同时约束：用例的编写（字段写法）、命名、稳定标识、数据管理、上传同步、质量门禁。

## 1. 角色

资深接口测试工程师：契约测试、边界分析、异常场景、权限安全、幂等并发、数据一致性。

## 2. 输入与真值层级（生成前必须明确）

输入：接口契约（URL/Method/Header/Path/Query/Body/响应/状态码/错误码）、业务规则（状态机/权限/约束/幂等）、
环境信息（baseUrl/token/测试账号）、非功能要求。

**预期值的真值层级（冲突时按优先级高者为准）**：

| 层级 | 来源 | 说明 |
|------|------|------|
| 1（最高） | 《业务预期确认表》 | 业务方拍板的行为规定；不存在时跳过 |
| 2 | 接口文档 / OpenAPI | 契约声明 |
| 3（最低） | 后端源码 | 实现事实；与上层冲突时**记录冲突并升级人工拍板**，禁止擅自二选一 |

**禁止用"探测线上实际行为"反推预期**——预期写"应该是什么"，探测只用于验证预期是否被实现满足。

## 3. 输出（字段标准——每个字段的写法要求）

输出 Markdown 表格（或结构化 JSON），字段与写法标准：

| 字段 | 写法标准 |
|------|----------|
| 用例ID（稳定ID） | 见 §5；全库唯一；生成后永不改变 |
| 优先级 | P0/P1/P2/P3（标准见 §8；禁止优先级通胀） |
| 类型 | 契约/正向/参数/边界/鉴权/权限/业务/幂等/安全/一致性 |
| 标题 | 见 §4 命名标准 |
| 前置条件 | 固定三段式（环境/账号/数据），见 §3.1 |
| 请求方法 | METHOD /path（含路径参数占位符） |
| 请求头 | 含鉴权约定：`Authorization: Bearer（账号从 pytest 环境变量取）` 或明确声明"不发送 Authorization" |
| 参数 | 具体值或**明确的取值约定**（`从 GET /v1/me/addresses 动态获取默认地址 id`）；禁止空占位符与固定数据库 ID |
| 步骤 | 可照做：环境引用 → 构造请求 → 发送 → 记录 → 断言 |
| 预期HTTP / 预期业务码 | 确定性值（如 `200`、`404`、`400 + UNAUTHORIZED`）；禁"待确认/4xx/符合约定/不 500 即可"等模糊表述（"非 500"仅可作为附加断言） |
| 断言点 | 至少覆盖：协议层（状态码）+ 业务层（业务码/message）+ 数据层（关键字段/副作用），安全类须覆盖敏感性（不泄露密码/堆栈） |
| 清理 | 必填。"无需清理（只读）"是合法值；写操作必须写清恢复动作 |
| 备注 | 引用来源（接口文档§x / 需求编号 / 拍板编号 MP-xxx） |

### 3.1 前置条件标准（固定三段式）

每条前置条件**固定三段，按序换行**，禁止重复堆叠、禁止残留编辑痕迹（如"原条件："）、禁止无信息量表述（如"按接口文档准备所需数据"）：

```
环境：baseUrl（BASE_URL）与测试账号由 pytest 环境变量提供（conftest 自动注入）。
账号：<三选一>
  · 普通用户 token（APP_TEST_ACCOUNT / APP_TEST_PASSWORD 登录后由 fixture 注入 Authorization）
  · 管理员 token（ADMIN_TEST_ACCOUNT / ADMIN_TEST_PASSWORD 登录后由 fixture 注入 Authorization）
  · 不发送 Authorization（验证未登录场景）／无需登录（免鉴权接口）
数据：<所需数据（含数量/状态）>；准备方式：<fixture 预置 或 具体接口步骤>
```

规则：
1. **账号必须指明角色与变量名**——管理端接口（/v1/admin/**）必须写「管理员 token」；仅写"运行时 token"不合格。
2. **数据必须指明"要什么 + 怎么来"**——路径参数类用例写清资源名与列表接口（如"先调用 GET /v1/me/addresses 取一条记录的 id"）。
3. 无数据依赖的用例省略「数据」段（可两行）；只读用例的清理写"无需清理（只读）"。
4. 参数列中禁止"从对应列表接口动态获取"这类模糊表述——必须写明具体列表接口。

### 3.2 请求体与负向用例标准

- **有请求体的接口**（POST/PUT，白名单除外）**必须写明请求体**（具体值或明确的取值约定），禁止"无请求体"。
- **无体动作接口白名单**（允许"无请求体"）：订单取消、售后取消、通知单条已读、全部已读。新增白名单需评审确认。
- **负向用例必须写清"缺什么、怎么缺"**：
  - 路径参数缺失：`不提供路径参数 X（URL 中省略该路径段），验证请求被拒绝`
  - body 字段缺失：`删除必填 body 字段 X；其余字段正常提供：{完整请求体}`
- **鉴权头必须标注角色**：管理端 `Authorization: Bearer <管理员 token>`；C 端 `Authorization: Bearer <普通用户 token>`；
  未登录用例明确写"不含 Authorization"。禁止裸写 `Authorization: Bearer` 或仅写"运行时 token"。

### 3.3 派生一致性与单一事实源

- 清单（test_cases_inventory.md）是**唯一内容源**；步骤区是"请求方法 / 请求头 / 参数"三字段的**派生视图**。
- 派生视图必须由字段**程序化重建**（格式：`请求：…<br>请求头：…<br>参数：…<br>步骤：…`），禁止在任何批量修改中单独编辑步骤区。
- 任何字段修改后必须整行重建派生内容；lint R24 强校验"步骤区 == rebuild(字段)"，防止副本漂移。
- 批量修改脚本必须**幂等**（重跑不产生叠加、不引入与场景矛盾的内容）；执行前先 dry-run 输出差异表。

### 3.4 场景-操作一致性与参数适用性

- **缺参场景不得出现"获取被缺参数"的动作**：缺路径参数用例必须写"不提供路径参数 X（URL 中省略）"，不得写"先取 id"。
- **正常路径参数用例必须给出取值方式**（具体列表接口，如"先调用 GET /v1/me/addresses 取一条记录的 id"）。
- **无路径参数的接口不得出现"路径参数"说明**（参数只描述实际发送的内容：body / query / 无参数）。
- **接口归属核对**：用例的 METHOD+路径必须在《接口文档》接口清单内（lint R14 机器核对，当前 62 个接口）。

### 3.5 需求追溯（已接线）

- 每条用例的备注引用需求编号（格式：`需求：AUTH-02`），用于需求↔用例双向追溯。
- 已接线：232 条备注全部写入需求引用；覆盖报告由 lint **R28** 输出（未覆盖需求逐条列出）。
- 未覆盖项分两类处理：可映射的补映射；前端页/观察项（如 AUTH-03/PAY-05/REV-03/SEC-*）在
  `artifacts/traceability/requirement-coverage.md` 标注"治理说明（无自动化用例）"。

### 3.6 断言标准（可机器判定格式，v2.6）

**核心原则**：断言必须能被一个不了解业务的执行者或脚本判定真伪。预期结果统一为三要素：

- **正向（HTTP 200）**：`HTTP=200；code=200；data.<字段路径>=<期望值/规则>；[附加断言]`
  - `code=200` 是本系统成功信封的真实业务码（`{code,data,message}`），不是 HTTP 码的同义反复。
  - `data.` 必须落到具体字段（如 `data.token` 非空、`data.items[].quantity=1`），或写明确的回查指令
    （如 `回查 GET /v1/cart 校验 data.items[].quantity 与提交值一致`）。
- **负向（HTTP 4xx/5xx）**：`HTTP=<code>；error.code=<词典词条 | 无（框架级）>；[附加断言]`

**禁用清单（lint R29/R30 强校验）**：

1. **禁止无判定对象的模糊词**：`结果一致 / 保持一致 / 结果正确 / 数据正确` 等，必须写清"回查哪个接口、比较哪个字段"
   （反例：`断言重复操作结果为「结果一致」`；正例：`回查 GET /v1/me/addresses 校验 data[].receiver 与首次提交一致`）。
2. **禁止把 HTTP 码写进业务码槽位**：`错误码符合 200/400/404`、`业务码=400` 一律禁止；
   正向写 `code=200`（真实成功码），负向写 `error.code=<词典词条>`；框架级 404 无业务码时写 `error.code=无（框架级）`。
   例外：源码采用"HTTP 200 + body 数值码"风格的接口族（如订单详情/取消、分页归一化），允许在 **expected_http=200** 的前提下
   把 body 数值码写进业务码列，但必须带括注说明来源（例：`500（源码现状：失败标志）`）。
3. 禁止 `data.xxx` 占位符与"符合约定/允许枚举"类空话（沿用 R06/R09）。

**校准说明（与"一刀切禁词"的差异）**：

- `符合 / 一致` 二字本身不禁，禁的是"没有判定对象"；`error.code 符合 VALIDATION_FAILED` 是合格断言。
- `业务码=200` 在正向用例合法（后端确实返回 code=200），但**仅此一条不构成数据层覆盖**——正向用例必须另有
  `data.` 或回查锚点（lint R29）。

## 4. 命名标准（正式格式 v1.1）

```
标题 = [模块/功能]_[测试场景/操作条件]_[预期业务结果]
```

- **模块/功能**：业务名（登录、注册、商品列表、提交订单、支付回调、管理员发货……）。
  中文名从《接口文档》取；管理端统一以「管理员」开头；C 端不加前缀。
- **测试场景/操作条件**：`典型请求`、`未带Token`、`无效Token`、`缺少必填参数`、`缺少路径参数{参数名}`、
  `重复提交`、`重复删除`、`重复标记`、`重复取消`、`重复添加`、`重复回调`、`重复账号`、`密码少于6位`、
  `非法分页参数`、`访问他人订单`、`库存不足`、`数量小于等于0`。
- **预期业务结果**：业务语言。**禁止出现 HTTP 状态码、业务码、错误码、状态枚举原文。**

**预期业务结果词典（统一用词，禁止自由发挥）**：

| 精确预期 | 标题用词 |
|---|---|
| HTTP 200（查询/列表/详情） | 查询成功 |
| HTTP 200（创建/新增/添加/发表） | 创建成功 |
| HTTP 200（修改/更新） | 修改成功 |
| HTTP 200（删除/移除） | 删除成功 |
| HTTP 200（发货） | 发货成功 |
| HTTP 200（审核动作） | 审核通过 |
| HTTP 200（登录/注册/下单/支付/取消/申请/校验/回调） | 登录成功 / 注册成功 / 下单成功 / 支付成功 / 取消成功 / 申请成功 / 校验成功 / 回调成功 |
| HTTP 400 + UNAUTHORIZED（未带/无效 Token） | 拒绝访问 |
| HTTP 400 + UNAUTHORIZED（错误凭据） | 提示账号或密码错误 |
| HTTP 400 + VALIDATION_FAILED | 提示参数错误（唯一性冲突按语义：提示账号已存在） |
| HTTP 400 + INSUFFICIENT_STOCK | 提示库存不足 |
| HTTP 400 + INVALID_QUANTITY | 提示数量不合法 |
| HTTP 400 + FORBIDDEN | 拒绝访问 |
| HTTP 404（缺路径参数场景） | 提示资源不存在 |
| HTTP 200（分页边界） | 正常返回 |
| 重复提交（PUT，结果一致） | 结果一致 |
| 重复删除（第二次拒绝） | 第二次被拒绝 |
| 重复标记（无新副作用） | 无新副作用 |
| 重复取消 | 不再产生副作用 / 被拒绝 |
| 重复添加 | 不产生重复记录 |
| 重复回调（安全断言） | 不得重复入账 |

**命名硬规则**：三段式缺一不可；全库唯一；禁止 `[METHOD 路径]` 段、`[API-AUTO]` 前缀、稳定 ID、`_1/_2` 编号后缀。

## 5. 稳定 ID 与追溯

- 稳定 ID 格式：`{METHOD}_{路径转大写下划线}`（契约用例）+ `-{三位序号}`，如 `PUT_V1_ME_ADDRESSES_ID-003`；
  业务用例：`BUS-{域缩写}-{序号}`，如 `BUS-ORD-001`。
- **稳定 ID 只存在于两个地方**：清单的用例ID列 + 禅道 keyword 字段（`API-AUTO,<稳定ID>`）。
  永远不出现在标题、正文中。
- 一切自动化匹配（上传、修复、结果回写、改名）**只允许按 keyword 匹配**，禁止按标题、禁止按页面 JSON 的
  `caseID` 字段（实际格式为 `"id":"case_N"`）。
- 变更追溯：接口/需求变更时按稳定 ID 做清单 diff（新增/删除/变更三列表），增量更新，不全量重发。

## 6. 生成流程

1. 解析契约：字段/类型/必填/长度/格式/枚举/默认值/错误码。
2. 识别业务规则：状态流转、权限、数据依赖、副作用。
3. 按覆盖维度设计场景（§7），用等价类/边界值/判定表/状态迁移/场景法/正交补充组合。
4. 为每条写可验证断言；去重；排优先级；补数据准备与清理。
5. 输出后立即过 lint（§11）——**lint 不通过禁止上传**。
6. 上传禅道（§10 工具契约）；执行结果回写；失败提 Bug。

## 7. 必须覆盖的维度与完成标准

维度（每接口按适用性覆盖）：契约、正向、参数、边界、响应、鉴权、权限、业务、数据一致性、
异常容错、幂等并发、安全、兼容、可观测。

**可量化完成标准（覆盖矩阵自动核对）**：每个接口至少有
① 正向 1 条 ② 未带Token 1 条 ③ 缺少必填参数 1 条 ④ 重复提交/幂等 1 条 ⑤ 边界（分页/越界，适用时）1 条。
缺口由覆盖矩阵脚本输出，覆盖率随版本追踪。

## 8. 优先级标准

- **P0**：核心正向、鉴权/权限、资金/库存/状态机、核心错误码。
- **P1**：边界、异常、业务规则细节、幂等、并发、依赖失败。
- **P2/P3**：安全深度、性能、可观测、极端组合。

**禁止优先级通胀**：P0 占比建议 ≤ 40%（当前 232 条中 P0 占 70%，需在评审时校准）。
冒烟集 = P0 子集，每次部署后必跑。

## 9. 断言层级

协议层（状态码/Header）→ 业务层（业务码/message/data）→ 数据层（DB/缓存/副作用）→ 可观测（日志/审计）。
每条至少覆盖前两层；P0 用例须覆盖数据层。
正向用例一律要求数据层锚点（`data.<字段>` 或明确回查指令，见 §3.6）；负向用例的锚点是 `HTTP=<code>；error.code=<词条>`。

## 10. 工具交互契约（禅道同步，血泪教训）

1. **步骤三件套必须齐全**：`steps[N]` + `stepType[N]=step` + `expects[N]`；缺 `stepType` 会静默丢步骤。
2. **成功判定必须为 `"result":"success"`**；空响应不等于成功。
3. 编辑端点 `/testcase-edit-{id}-false-0.html`，字段：product/module/story/scene/type/stage[]/title/pri/status/
   precondition/steps[N]/stepType[N]/expects[N]/keywords/uid/case/version/comment/script/fileList；
   先 GET 解析 uid/version。
4. 匹配只用 keyword；批量操作前先重扫现状（防并发修改）；请求间隔 ≥0.15s。
5. 全部工具变更必须同步更新 `test_cases_inventory.md`（清单是唯一内容源）。

## 11. 质量门禁（lint）与评审

- **lint（强制）**：上传前执行 `case_lint`（方案见《lint方案.md》）：标题规范/唯一性/禁用词/字段完备/
  预期确定性/占位符/环境硬编码/清理完整性/覆盖矩阵。**severity=fail 项不清零不得上传。**
- **评审（强制）**：上传后按《评审方案.md》执行——P0 全评、P1 抽评 ≥30%；评审状态在台账留痕
  （本部署禅道无原生评审入口，采用"工作台评审 + 台账 + 结论回写备注"等效流程）。
  **门禁口径（2026-10-05）**：存量豁免（已执行的继续执行，Blocker 问题单条撤回）；
  **增量生效**——新增/修改的用例必须 lint 清零 + 评审通过后方可上传执行。

## 12. 领域词典（强制引用）

- 词典位置：`docs/测试资料/领域词典.md`（词条出处=后端源码 `BusinessException` 全集 + 接口文档 + 需求文档 §7）。
- **规则**：用例「预期业务码/断言」中出现的大写枚举词必须属于词典「机器可读词表」（lint **R27** 强校验）；
  状态机类断言必须符合词典中的流转表；新增词条须先更新词典（附出处），再改用例。
- 当前词表：15 个错误码 + 15 个状态/枚举词（30 条；v2.6 补 CANCELLED）。

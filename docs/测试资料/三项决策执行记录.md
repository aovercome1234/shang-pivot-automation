## 决策 1：修生成器（已完成）

**改动**
1. `build_api_doc.py`：`body_presence` 判定由"出现 `hasText(x)` / `x == null`"收紧为**"该判断后紧跟 throw"**，
   即只把真正的存在性校验计入参数维度；赋默认值（`if (x==null) x=默认`）不再算校验。
   同时把该检测**下沉到服务层方法**（此前只看控制器，会漏掉 `AfterSaleService.apply` 这类校验）。
2. `generate_cases.py`：`POST /admin/dicts` 幂等策略由 `conflict` 改 `new_record`——
   原引用 `DictController:52` 是错的（该行不是唯一性校验，唯一性校验在 `PermissionController:49-51`）。

**结果**
| 项 | 值 |
|---|---|
| 参数维度适用端点 | 75 → **62**（剔除无存在性校验的创建接口） |
| 6 条空体用例 | **已移除**（`POST_ADMIN_{ATTRIBUTES,CATEGORIES,DEPTS,DICT_ITEMS,PERMISSIONS,WAREHOUSES}-003`） |
| `POST_ADMIN_DICTS-004` 预期 | CONFLICT → **0**（回查列表条数 +1） |
| 清单条数 | 474 → **467** |
| 门禁 | 离线 lint **fail 0**、规则自测 **33/33** |

**另记缺陷**：这 6 个创建接口提交空体返回 **500**（无校验时 DB 约束/NPE 兜底），应为 400。

## 决策 2：取消订单（已完成）

**改动**：`OrderSubmitService.cancel()` 在调用 `closeAndUnlock` 前增加状态前置校验——
非 `PENDING_PAY` 抛 `ORDER_STATUS_INVALID`；`closeAndUnlock` 保持静默幂等供超时关单 Job 复用。
（依据：需求文档 MALL-08「仅 PENDING_PAY 可取消」；原实现静默返回 200 属误导性响应。）

**验证**（本地修复版实例 8096，`ADMIN_BASE_URL=MALL_BASE_URL=http://127.0.0.1:8096`）
- `BUS-ORD-005`（取消已支付订单 → 应拒绝）：**失败 → 通过**
- 手工链路复测：下单 → 支付 → 发货 → 收货 → 申请售后 → 审核，全部 `code=0`

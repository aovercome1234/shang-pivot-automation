## 三、本轮发现的真问题（改造过程中暴露的）

### P0-1：pytest 结果无法映射回稳定 ID —— 结果文件为空

- **现象**：`artifacts/automation_results.json` 的 `results` 为空数组，但 junit 有 475 条测试。
- **根因**：`tests/contract/test_inventory_driven.py` 的参数化只用 `ids=[case_id]`，**从未挂 `zt_case` 标记**；
  而 `conftest._record_automation_result` 只认 `zt_case` 标记，取不到就 `return`。
- **危害（最严重）**：空结果 → 失败集为空 → **C3「失败 ⊆ 登记」自动成立**，门禁会误判为绿。
  这正是对照文档 §6-⑥ 说的"假绿/掩盖"。
- **修复**：
  1. 参数化改为 `pytest.param(c, id=..., marks=pytest.mark.zt_case(...))`；
  2. `conftest.pytest_sessionfinish` 结果为空时打印告警；
  3. **门禁加固**：C3 增加"结果文件为空 → 判红（回写链断，失败集不可信）"，且 C4 联动 C3。

### P0-2：登记表只查单向 → 登记过期可挂账

- **现象**：40 条登记中 14 条本轮已通过（前轮失败疑为环境/数据污染），6 条新失败未登记。
- **修复**：C3 改为**双向核对**（`失败 ⊆ 登记 ⊆ 失败`）；已通过的 14 条移入 `known-failures.json.retired`
  保留审计轨迹（不静默删除）；新失败的 8 条按缺陷归因补登。

### P1：C8 可被 `touch` 绕过

- **修复**：C8 不再看文件 mtime，改看结果内的 `finished_at`；并要求 `run_id` 存在、
  结果内记录的 `junit_sha256` 与当前 `junit.xml` 一致（结果与 junit 必须同批）。

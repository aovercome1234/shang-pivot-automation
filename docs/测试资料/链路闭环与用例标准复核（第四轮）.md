### 1.2 发现并修正的格式缺陷：前置条件里的 `<br>` 裸露

对比两张截图可见：元气购用例的前置条件是正常换行，尚品汇用例里**裸露着 `<br>` 标签**。

**取证**：抓页面 HTML 统计——`case_721` 中 `&lt;br&gt;` 出现 **2 次**，`case_234` 为 **0 次**。

**根因**：`zentao_sync.parse_inventory` 只对 `steps` 做了 `replace("<br>", "\n")`，
**`precondition` 没有转换**，于是前置条件里的 `<br>` 原样提交到禅道。

**修复**（两处）：
1. `_post_case` / `_edit_case` 推送前统一 `precondition.replace("<br>", "\n")`；
2. **指纹改为覆盖"实际推送的内容"**——原来指纹用未转换的原始值计算，
   导致转换规则变更后判定"无变化"而不重推（第一次重推 `repaired=0, skipped=474` 就是这么来的）。

**验证**：全量重推后随机抽查 20 条，**仍含裸露 `<br>` 的 = 0 条**。

## 2. 链路闭环

### 2.1 业务用例接入执行

BUS-* 业务链路用例原先被排除在执行范围外（"需链式造数"）。本轮纳入并补齐执行器能力：

| 能力 | 说明 |
|---|---|
| 简写请求体解析 | BUS 用例的 payload 是"人类可读简写"（`{skuId 先调用 …, quantity: 1}`），新增宽容解析器 |
| 裸 JSON 请求体 | BUS 的 payload 常直接是 JSON 字面量（无 `请求体：` 前缀）→ 识别为请求体 |
| 中文状态过滤 | "取一条状态为**待收货**的订单" → 映射 `PENDING_RECEIVE` 后过滤候选记录 |
| SKU 意图识别 | 约定提到 "SKU" 时走"列表→详情"两跳取 SKU，而不是误用 spuId |
| 任意字段名取值 | `取一条记录的 categoryId` / `取详情中的 SKU id` 等措辞统一解析 |

**效果**：BUS 用例从"全部不执行"变为 **14 通过 / 23 失败 / 13 跳过**（跳过均带原因）。

### 2.2 订单链路被 P0 缺陷阻断（D-18）

实测：**`POST /api/orders` 对任何入参都返回 500**——
连"不存在的地址"也 500（源码应返回 `BAD_REQUEST 收货地址无效`），
而 `idempotentKey` 缺失校验正常返回 400 → 崩溃点位于幂等查询之后、地址校验之前。

因此 **17 条依赖下单链路的业务用例（ORD/PAY/AS/REV/STK）全部失败**——
这不是用例问题，是链路本身不可用。购物车→结算→支付闭环**当前无法跑通**。

另有 D-19：`POST /api/auth/refresh` 传畸形 refreshToken（`invalid.refresh.token`）→ 500（应返回 `TOKEN_INVALID`）。

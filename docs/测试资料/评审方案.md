# 测试用例评审方案

> 目的：让 232 条用例从"AI 生成 + 自查"升级为"经人工评审、状态可追溯"的正式资产。
> 状态：**已启动（2026-10-05）**——工作单见 `artifacts/review/评审工作单.xlsx`，指引见 `artifacts/review/评审指引.md`。
> 依据：《rule.md v2.6》§11；禅道原生评审入口在本部署不可用（/testcase-review-* 不可达），
> 采用"工作台评审 + 台账留痕 + 结论回写禅道备注"的等效流程。

## 0. 门禁口径（2026-10-05 定稿：存量豁免 + 增量生效）

> 背景：门禁条款"评审未通过不得进入执行环节"与现状冲突——自动化已先跑起来（212/232 接入）。
> 若严格执行，需把已跑通的自动化全部挂起，代价不可接受。定口径如下：

1. **存量豁免**：当前 232 条用例（含已接入自动化的 212 条）豁免"先评审后执行"门禁，继续执行；
   存量用例的评审照常进行，用于质量确权与改进。
2. **单独撤回**：评审发现 **Blocker 类**问题（预期不可断言/步骤无法执行/数据依赖缺失/业务预期错误）的用例，
   **单条撤回执行**（该条自动化标记 xfail 或移除接入），修正并经复评通过后恢复。
3. **增量生效**：自 2026-10-05 起**新增或修改**的用例，必须走完整门禁——lint fail 0 → 评审通过 → 才允许上传执行。
   增量评审走轻量通道：只审变更条目（diff 清单）+ 主评人单签。
4. 口径记录在本文件与 rule.md §11；变更需评审发起人确认。
5. **本批定位**：执行后复核（历史原因：自动化先行）；下一批起恢复"评审先于执行"的增量门禁（评审通过才放行执行）。

## 1. 评审对象与前置条件

- 对象：禅道产品「元气购」`testcase-browse-1` 全部 232 条用例（P0=162 / P1=70）。
- 前置：① 用例已通过 lint（无 fail 项）；② 清单与禅道标题/keyword 一致；③ v1.1 命名已生效。
- **重要前置动作：优先级校准**（30 分钟）：当前 P0 占 70% 属通胀。先按 rule.md §8 重排：
  核心正向/鉴权/资金库存状态机/核心错误码 = P0（目标 ≤40%，约 90 条），其余降 P1。
  校准让"全评 P0"的成本可控。

## 2. 角色与职责

| 角色 | 人选（建议） | 职责 |
|------|--------------|------|
| 作者 | 测试工程师（AI 辅助） | 按意见修改、响应复评 |
| 评审人 A | 测试负责人 | 用例质量、覆盖度、可执行性 |
| 评审人 B | 开发代表 | 契约/实现一致性（错误码、状态机、边界） |
| 评审人 C | 产品/业务（关键用例） | 业务预期正确性（订单/支付/库存/权限） |
| 记录 | 禅道 | 评审状态、意见、结论留痕 |

单人评审可接受（A 为主），B/C 仅在"业务规则类"用例参与。

## 3. 分层评审策略

| 层 | 范围 | 策略 |
|----|------|------|
| 第一层 | 校准后的 P0（约 90 条） | **全量评审** |
| 第二层 | P1（约 140 条） | **抽评 ≥30%**（≥42 条），按模块+随机抽样 |
| 第三层 | 已知缺陷关联用例 | 评审时标注"缺陷跟踪中"（负数分页500 / 路由500 / 鉴权失效），不算用例问题 |

## 4. 评审检查单（逐条对照）

| # | 检查项 | 判据 |
|---|--------|------|
| 1 | 标题 | 三段式、无禁用词、语义与正文一致 |
| 2 | 前置条件 | 可执行：数据依赖有准备方式，账号/环境引用明确 |
| 3 | 步骤 | 照着能跑：请求构造、动态取值（路径参数/地址 id）说明清楚 |
| 4 | 预期 | 确定性值；无"待确认/4xx/符合约定"；与接口文档/源码一致 |
| 5 | 断言 | 覆盖协议层+业务层；P0 覆盖数据层/副作用 |
| 6 | 清理 | 写操作有恢复动作；只读有"无需清理（只读）" |
| 7 | 追溯 | 备注引用接口文档§/需求编号/拍板编号 |
| 8 | 优先级 | 符合 §8 标准（校准后） |
| 9 | 去重 | 与同类用例不重复（同接口同场景同预期仅一条） |
| 10 | 命名唯一 | 全库无重名 |

## 5. 评审流程（禅道操作）

1. **发起**：作者在禅道将用例置为待评审（由"由谁评审"字段指定评审人）。
2. **评审**：评审人逐条过检查单，结论三选：
   - ✅ 通过（记录评审时间）
   - ✏️ 需修改（写明具体意见，退回作者）
   - ⛔ 拒绝（原则性问题，需重写）
3. **整改与复评**：作者修改 → 复审仅看修改点 → 通过。
4. **归档**：评审记录（谁/何时/结论/意见）保留在禅道历史；汇总形成《评审报告》（覆盖率、一次通过率、遗留问题）。
5. **门禁**：评审未通过的用例**不得进入自动化执行环节**（未通过清单挂起）。

## 6. 通过标准

- 无 Blocker 类问题：标题违规、预期不可断言、步骤无法执行、数据依赖缺失。
- Minor 类（措辞、备注补充）可记录整改计划，不阻塞通过。
- 一次通过率目标 ≥80%（低于则先修生成侧规则，再重审）。

## 7. 时间安排建议

| 步骤 | 内容 | 周期 |
|------|------|------|
| D1 上午 | 优先级校准（P0 压到 ≤40%） | 0.5h |
| D1 下午 | 评审启动会：对齐检查单与流程（15 分钟）+ 首批评审（认证域 33 条） | 2h |
| D2–D3 | 商品/购物车/订单域（P0 全评） | 各 2h |
| D4 | 支付/售后/通知/管理端域 | 2h |
| D5 | P1 抽评（≥42 条）+ 汇总《评审报告》 | 3h |

首轮建议控制在**一周内闭环**；后续版本增量用例（变更 diff 出的新增/修改条）随版本走轻量评审。

## 8. 度量与持续改进

| 指标 | 定义 | 目标 |
|------|------|------|
| 评审覆盖率 | 已评审条数/应评审条数 | P0 100%、P1 ≥30% |
| 一次通过率 | 首轮通过/参评条数 | ≥80% |
| 问题分布 | 按检查单序号统计 Top3 | 用于反哺 rule.md / lint 规则 |
| 评审时效 | 提交→结论的平均时长 | ≤3 个工作日 |

**反哺机制**：评审发现的高频问题写入 rule.md（规范）与 lint 规则（机械拦截），做到"同类问题只出现一次"。

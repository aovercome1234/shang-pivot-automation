# 下单链路修复（源码级根因 + 验证）

> 触发：执行层发现"下单必 500"，导致「购物车→结算→支付→发货→收货→售后」整链不可用。
> 本轮定位到**三个源码级根因**并修复，端到端验证通过。日期：2026-10-06。

---

## 0. 结论

| 项 | 结果 |
|---|---|
| 根因 | **3 个**（都在后端源码/配置，不在用例） |
| 修复 | V20 迁移 + 1 行配置类改动 + JDBC URL 参数 |
| 验证 | **本地修复版实跑整链通过**：下单 → 支付 → 发货 → 收货 → 售后审核 |
| 连带修复的缺陷 | **D-13（售后审核 500）、D-14（地址列表 500）、D-15（地址删除 500）、D-18（下单 500）** —— 三处修复后全部消失 |
| 影响面 | 部署环境（111.170.33.2）同样存在这三处问题，**需重新部署才能生效** |

## 1. 根因一：`commerce.address` 缺 `trace_id` 列

**证据**（本地复现，日志按 traceId 定位）：
```
org.postgresql.util.PSQLException: ERROR: column "trace_id" does not exist
SQL: SELECT id,customer_id,name,phone,...,trace_id FROM commerce.address WHERE id=? AND deleted=false
### The error may exist in .../AddressMapper.java
```

**成因**：`V8__v2_customer_cart_address.sql` 建 `commerce.address` 时漏了 `trace_id`，
而 `Address` 实体继承 `BaseEntity`（后者声明 `private String traceId;`）→ MyBatis-Plus 生成的
SELECT 列清单带 `trace_id` → 所有按 id 查地址的语句必失败。

**为什么只有 address 中招**：其余表（cart / cart_item / favorite / browse_history / home_slot*）虽同样缺列，
但**它们的实体没有继承 BaseEntity**，SQL 里不带该列 → 不受影响。逐表核对后确认只有 `Address` 一处不一致。

**修复**：新增 `V20__fix_address_trace_id.sql`
```sql
ALTER TABLE commerce.address ADD COLUMN IF NOT EXISTS trace_id VARCHAR(64);
```
（Flyway 前向修复，不改已应用的 V8）

**影响**：D-14（`GET /api/addresses` 500）、D-15（`DELETE /api/addresses/{id}` 500）、
D-18 的地址查询环节（下单第一步就查地址）。

## 2. 根因二：乐观锁拦截器未注册

**证据**（根因一修好后暴露）：
```
MyBatisSystemException: Error updating database.
Cause: BindingException: Parameter 'MP_OPTLOCK_VERSION_ORIGINAL' not found.
SQL: UPDATE commerce.stock SET ..., version=?, ... WHERE id=? AND version=? AND deleted=false
   at .../StockMapper.updateById
```

**成因**：`Stock` 实体声明 `@Version private Integer version;`（乐观锁），
但 `MybatisPlusConfig` **只注册了 `PaginationInnerInterceptor`**，缺 `OptimisticLockerInnerInterceptor`
→ `updateById` 生成的 SQL 带 `AND version=?`，而该参数由拦截器负责绑定，拦截器缺失即 BindingException。

**修复**：`shang-common/.../config/MybatisPlusConfig.java`
```java
interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
```

**影响**：下单时锁库存（`UPDATE commerce.stock`）必失败 → 下单 500。

## 3. 根因三：JDBC 缺 `stringtype=unspecified`

**证据**（根因二修好后暴露）：
```
PSQLException: ERROR: column "address_snapshot" is of type jsonb but expression is of type character varying
SQL: INSERT INTO commerce."order" (..., address_snapshot, ...) VALUES (..., ?, ...)
```

**成因**：PostgreSQL JDBC 默认把 String 参数按 `varchar` 绑定，而 `commerce."order".address_snapshot`
是 `jsonb` → 写入被拒。需在连接串加 `stringtype=unspecified` 让服务端自行推断类型。

**修复**：
- `application.yaml` 默认 `DB_URL` 增加 `stringtype=unspecified`
- `.env.example` 同步
- **部署环境**：`/etc/shang-pivot/shang-pivot.env` 的 `DB_URL` 也要加该参数

**影响**：下单写订单必失败（**这也是"订单表里只有种子数据、下单功能从未成功过"的原因**）；
售后审核（更新售后单）同样中招 → D-13。

## 5. 部署指引（需在服务器执行）

1. 用修复后的代码重新构建 JAR 并替换 `/opt/shang-pivot/current/app.jar`；
2. **在 `/etc/shang-pivot/shang-pivot.env` 的 `DB_URL` 追加 `&stringtype=unspecified`**（否则下单仍失败）；
3. `systemctl restart shang-pivot` —— 启动时 Flyway 会自动执行 `V20` 补 `trace_id` 列；
4. 复验：`curl -X POST .../api/orders`（用测试会员）应返回 `code=0`，或直接看 `/api/addresses` 不再 500。

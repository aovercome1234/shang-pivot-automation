# 验收标准治理手册（v1.0）

> 目的：让"验收标准"本身可管理、可升级、可验收——解决"标准反复升级导致已通过的内容失效"的问题。
> 更新：2026-10-04。配套：rule.md（内容标准）、lint方案.md（机械门禁）、评审方案.md（人工层）。

## 1. 标准升级路线（Q1）

### 1.1 版本策略

| 版本位 | 含义 | 示例 |
|--------|------|------|
| vX.Y 的 Y+1 | **验收维度增加/收紧**（存量内容需回归） | v1.0→v1.1 标题业务化；→v2.1 前置三段式 |
| X+1 | 流程或结构变化（生成方式/工具链/字段结构） | v1→v2 真值层级+门禁体系 |

### 1.2 升级触发条件（满足任一即启动）
1. 发现**新的问题类型**（评审/执行/使用中发现且现有规则无法拦截）；
2. 业务/契约变化（接口变更、业务拍板更新）；
3. 执行反馈（⑧ 中"因用例缺陷导致的失败"归因）；
4. 外部要求（合规/审计）。

### 1.3 升级五步流程（缺一不可）
1. **归纳问题类型**（不针对单条）：归类到"矛盾类型库"（§2），确定是既有类型漏检还是新类型；
2. **写入 rule.md 条款**（内容标准先行，明确"合格长什么样"）；
3. **映射为 lint 规则 + 自测样例**（规则 + 坏例/好例锁定，`lint_selftest.py`）；
4. **全量回归**：lint 全量重跑 + 全部 fail 清零 + 抽样人工复核 + 推送禅道；
5. **发布版本**：rule.md 变更记录留痕（版本号/日期/变更/影响面）。

### 1.4 冻结机制
- 生成/修改批次开始前**冻结**当前标准版本；批次内不升级；
- 升级发生时 = 上一批"已通过"自动失效，**必须触发全量回归**（不是增量）；
- 所有阶段状态汇报必须带限定词：`对 rule.md vX.Y 通过`。

### 1.5 当前已有 vs 改进空间

| 机制 | 状态 |
|------|------|
| 命名/字段/前置/请求体/负向用例/派生一致性标准（rule.md §3.1-3.3） | ✅ 已有 |
| 26 条 lint 规则 + 自测回归（坏例必报/好例不报） | ✅ 已有 |
| 矛盾类型库（8 类，见 §2） | ✅ 已有（本手册） |
| **改进空间 ①**：rule.md 条款 ↔ lint 规则 **双向追溯矩阵**（防"孤儿规则"和"无规则条款"） | 🔶 待补（半天） |
| **改进空间 ②**：需求编号 ↔ 用例 追溯（L3 层，需从需求文档提取编号） | 🔶 待补 |
| **改进空间 ③**：执行反馈闭环（⑧ 的失败归因反哺规则，含漏报率统计） | 🔶 待 ⑧ 运行后 |

### 1.6 如何验收"标准完善"（五项检查，全绿才算完善）
1. **条款↔规则覆盖率 = 100%**：每条内容标准至少有一条 lint 规则，或注明"为何不可机械检、由谁兜底"；
2. **反向覆盖 = 100%**：每条 lint 规则都能追溯到 rule.md 条款（无孤儿规则）；
3. **矛盾类型库闭环**：每个已知类型有"规则 + 坏例 + 好例"，新类型 24 小时内完成闭环；
4. **漏报率 = 0**：人工评审/lint 漏掉、后被发现的"本可机械检出"问题数 / 总发现问题数（目标 0，来源：评审问题清单比对）；
5. **基线全绿**：当前 232 条 lint fail 0 + 自测 23/23 + 在线核对通过。

## 2. 矛盾类型库（Q2：语义矛盾的系统解法）

**核心思想**：语义矛盾 = "字段之间的约束被违反"。把"要靠理解发现的矛盾"转化为"可机械判定的约束检查"——穷举矛盾类型，逐条规则化。

| # | 矛盾类型 | 检查形式 | 规则 | 状态 |
|---|----------|----------|------|------|
| C1 | 空体矛盾（body 接口写"无请求体"） | 方法+路径签名 ↔ 参数 | R21 | ✅ |
| C2 | 角色矛盾（token 角色 ↔ 端点端别） | 路径前缀 ↔ 请求头 | R23 | ✅ |
| C3 | 副本漂移（步骤区 ↔ 字段） | 派生重建等式 | R24 | ✅ |
| C4 | 场景-操作矛盾（缺参场景却写"取参"；正常场景缺取值方式） | 标题场景 ↔ 参数语义 | R25 | ✅ |
| C5 | 参数适用性矛盾（无路径参数却写路径参数说明） | 路径结构 ↔ 参数 | R26 | ✅ |
| C6 | 占位符/硬编码/环境泄漏 | 正则 | R09/R10/R11 | ✅ |
| C7 | 枚举缺失（预期引用未定义枚举，如"允许枚举"） | 预期文本 ↔ 枚举词典 | R06 | ✅（部分） |
| C8 | 状态机矛盾（预期状态不在允许流转内） | 预期 ↔ 领域状态词典 | 待补（需状态机词典） | 🔶 |
| C9 | 数值一致性（金额/库存断言与基准矛盾） | 预期 ↔ 数据基准 | 待补（需执行基准） | 🔶 |

**三层解法（按可判定性分配）**：
1. **可机械判定** → lint 规则（C1-C7 已覆盖）；
2. **需要领域知识** → 建"领域词典"（状态机流转表/枚举值表/必填字段表），用例预期必须引用词典词条（C8/C9 的解法）；
3. **不可判定** → **评审（人）+ 执行（机器）兜底**——这是最后防线，不能省。

**关键认识**：矛盾类型是**有限集合**。当前 9 类覆盖绝大多数；剩余风险主要在"领域词典未建立"的部分。

## 3. 副本漂移的解释与根治（Q3）

**用 Excel 类比**：工作表里有"明细页"和"汇总页"（手工复制粘贴的副本）。改了明细没改汇总，两个数字就对不上——数据"漂移"了。我们的用例里：**"参数"字段**和**步骤区里的"参数：…"**是同一份数据的两个副本；批量脚本改了字段、没改副本（或改了一个措辞忘了另一个）。

**根治三件套（已落地）**：
1. **单一事实源**：清单是唯一内容源，任何数据只有一处"权威定义"；
2. **派生重建**：步骤区不存"内容"、存"公式"——每次修改后从字段**重新生成**（= 汇总页改成公式 =SUM(明细)，而不是粘贴数值）；
3. **机器等式校验**：R24 强制"步骤区 == 由字段重建的结果"，副本一旦漂移立即报错。

**配套纪律**：批量脚本必须幂等（重跑不叠加）；执行前 dry-run 输出差异表；禁止单独编辑派生区。

**本次教训的残留变体（已全部清除）**：同一个陈旧描述存在 3 种措辞变体，逐轮修复才清完——这正是"副本漂移"的典型表现（同一语义的多个手工副本各自漂移）。根治后此类问题将由 R22/R24/R26 在生成侧直接拦截。

### 4.2 lint 自身的验收方法（五查）
1. **规则回归自测**（`lint_selftest.py`）：每条规则"坏例必报、好例不报"——当前 **23/23 离线规则通过**（R14/R19/R20 在线模式覆盖）；
2. **误报率**：人工核对每次 fail/warn 的准确性，目标 100% 真问题（最近一次修正：R25 的过宽正则导致 1 例误报，已改为精确短语匹配）；
3. **漏报率**：以"评审/使用者发现的问题总数"为分母，统计"lint 本可机械检出却漏掉的"（目标 0）——本轮实测：R21-R26 的六类矛盾之前全部漏检，已补齐；
4. **覆盖率**：rule.md 条款 ↔ 规则双向 100%（§1.6 第 1/2 项）；
5. **稳定性与基线**：同一输入多次运行结果一致；当前 232 条 **fail 0 / warn 1（仅 P0 通胀提示）**，在线核对通过。

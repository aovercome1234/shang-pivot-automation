# 03 · 版本验证与自动化

> **判断区文档**（人工维护），描述「怎么用前面几份文档做跨版本验证」。工具是机制区，按本文命令复算。
> 版本指纹：**`810986c`**　·　核对日期：2026-10-10

---

## 1. 思路：把「版本验证」拆成三件可执行的事

反推出的文档最容易死在「下次提交后就没人知道它描述的是哪一版」。本套文档用三个机制把它焊死：

| 机制 | 解决什么问题 | 落点 |
|---|---|---|
| **指纹** | 「这份文档描述的是哪一版？」 | `00-版本基线.md` §5 指纹表 + `baselines/<label>/manifest.json` |
| **复算** | 「文档是不是已经过期了？」 | 生成器重跑 + `git diff --exit-code`：无差异 = 未过期 |
| **diff 分级** | 「升级到这个版本会打断什么？」 | `baseline_diff.py`：BREAKING / BEHAVIORAL / ADDITIVE + 受影响用例集合 |

一句话：**能复算的绝不用眼看；能分级的绝不写成一段话。**

## 2. 新鲜度判定：三个必须全绿

```bash
# 0) 前提：确定版本指纹
cd /Users/imac/Desktop/电商自动化测试/shang-pivot-master
git rev-parse --short HEAD            # → 810986c

# 1) 重算机制区产物
cd api_testcases
python3 scripts/build_api_doc.py --repo-root .. --openapi ../docs/openapi-v3-api-docs.json \
    --out "../docs/测试资料/接口文档.md" --diff artifacts/api-doc-diff.md
python3 scripts/build_db_dict.py --fingerprint "810986c"

# 2) 无差异 = 机制区文档与源码一致（这是「未过期」的机器判据）
cd ..
git diff --exit-code -- 'docs/测试资料/接口文档.md' 'api_testcases/artifacts/endpoint-model.json' \
    'docs/06-baseline/01-数据字典.md' 'api_testcases/artifacts/schema-model.json' \
  && echo "✅ 机制区一致" || echo "🔴 机制区已过期：把差异当作本次变更的一部分提交"

# 3) 指纹是否与基线文档一致
cd api_testcases && python3 scripts/snapshot_baseline.py --label 810986c
git diff --exit-code -- baselines/810986c && echo "✅ 指纹一致" || echo "🔴 指纹已变：这是新版本，走 §4 流程"
```

**判定规则**

| 结果 | 含义 | 动作 |
|---|---|---|
| 第 2、3 步均无差异 | 文档与当前源码、当前版本完全对应 | 可直接引用 |
| 第 2 步有差异 | 有人改了源码/迁移但没重算文档 | **先重算并审视差异**，再把差异连同代码一起提交 |
| 第 3 步有差异但第 2 步无差异 | 契约变了（指纹变），文档已同步 | 这是**新版本**：按 §4 冻结新快照并跑 diff |

> 现状（2026-10-10 实测）：第 1 步复算与仓库内文件**逐字节一致**，`api-doc-diff.md` 同步一致（`{"源码端点":135,"OpenAPI端点":135,"共有":135,"仅源码":0,"仅OpenAPI":0}`）。
>
> **幂等前提（别改）**：生成器的时间戳是**粘性**的——`build_db_dict.py` 在内容未变时沿用旧 `generated_at`，`snapshot_baseline.py` 同理沿用旧 `created_at`。这是刻意的：若每次复算都刷新时间戳，第 2、3 步会永远报「有差异」，整个判定失效。内容真的变了（含 `--fingerprint` 变化）才写新值。需要强制指定时用 `build_db_dict.py --generated-at "<值>"`。

## 3. 基线快照的目录约定

```text
api_testcases/
├── artifacts/                     # 工作区：最新一次生成的机读产物（会被覆盖）
│   ├── schema-model.json          # 36 表 / 359 列（build_db_dict.py 产出）
│   ├── endpoint-model.json        # 135 端点（build_api_doc.py 产出）
│   ├── api-doc-diff.md            # 源码 ↔ OpenAPI 差异表
│   └── automation_results.json    # 最近一次执行结果（含 junit sha256 新鲜度绑定）
└── baselines/                     # 不可变快照：每个版本一份，只增不改
    └── 810986c/
        ├── schema-model.json      # 冻结副本
        ├── endpoint-model.json    # 冻结副本
```

**纪律**：`baselines/**` 只增不改。需要修正已冻结快照 = 说明当初冻错了版本，应新开一个 label（如 `810986c-r1`）并记录原因，不要就地改——否则历史 diff 结论全部失效。

## 4. 版本升级验证流程（新版本发布前必须走完）

```text
步骤 1  取新版本指纹（commit + 迁移范围）
步骤 2  重算机制区产物（§2 的第 1 步）
步骤 3  对旧快照跑 diff：
          python3 scripts/baseline_diff.py --old baselines/<旧label> --new artifacts --out /tmp/diff.md
步骤 4  按分级处置（下表）——BREAKING 不处置完不许发版
步骤 5  按 diff 给出的用例前缀集合重跑受影响用例
步骤 6  更新判断区文档：业务规则/状态机（行为性变更）、API/数据字典（增量）
步骤 7  冻结新快照：snapshot_baseline.py --label <新label>
步骤 8  跑门禁：release_gate.py（C1–C8）
```

### 4.1 变更分级与门禁动作

| 级别 | 典型变更（工具自动识别） | 门禁动作 |
|---|---|---|
| 🔴 **BREAKING** | 删表 / 删列 / 改列类型 / 列变 NOT NULL 且无默认 / 新增 NOT NULL 无默认列 / 删唯一索引 / 删约束 / 索引列变更 / 删端点 / 鉴权要求变更 / 新增必填字段 / 删请求体字段 / 删响应字段 / **字段映射：JSON 字段消失、JSON 类型变更（如 Long→number）、新增一致性偏差** | 必须出迁移或兼容方案；必须更新受影响用例；**diff 退出码 1 直接卡发布** |
| 🟡 **BEHAVIORAL** | 列放宽为可空 / 有默认值下变 NOT NULL / 默认值变更 / 新增唯一索引 / 新增约束 / 新增或消失失败码 / 必填字段放宽 / **字段映射：来源列变更、底层类型变更** | 必须更新 `02-业务规则与状态机.md` 与受影响用例；允许发版但不能静默 |
| 🟢 **ADDITIVE** | 新增表 / 新增可空列 / 新增非唯一索引 / 新增端点 / 新增请求体或响应字段 / **字段映射：新增实体、新增 JSON 字段** | 补用例即可 |
| ⚪ **INFO** | 表/列注释变更、端点摘要文案变更 | 无需动作（但注释口径变了要顺带核对业务文档） |

### 4.2 受影响用例集合

`baseline_diff.py` 会输出受影响端点的稳定 ID 前缀（与 `test_cases_inventory.md` 的 `METHOD_PATH` 命名**完全一致**，不新造 ID），并直接给出可复制的命令：

```bash
cd api_testcases && python3 -m pytest tests/contract -k '<PREFIX1> or <PREFIX2>'
```

**已验证**：135 个端点派生出的前缀**全部命中**清单中既有用例 ID（135/135），因此该映射可直接用于回归筛选。→ 已确认 / 机器可复算。

## 6. 自动化落点

### 6.1 现有可复用脚本（**不要重写**）

| 脚本 | 用途 | 产物 |
|---|---|---|
| `build_api_doc.py` | 源码 → 接口文档 + 端点模型 + 源码↔OpenAPI 差异 | `接口文档.md`、`endpoint-model.json`、`api-doc-diff.md` |
| `build_db_dict.py` | 迁移 → 数据字典 + schema 模型（无法识别的 DDL 直接报错中止） | `01-数据字典.md`、`schema-model.json` |
| `build_field_map.py` | 实体源码 + schema 模型 → 字段映射（DB 列 ↔ 实体字段 ↔ 接口 JSON），并自动比对双向一致性 | `04-字段映射.md`、`field-map.json` |
| `build_call_graph.py` | 解析 Java/TS 源码 → 前端→端点→控制器→服务→表 调用链路 | `05-调用链路.md`、`call-graph.json` |
| `build_graph_page.py` | 把 `call-graph.json` 渲染成自包含交互页面（零依赖、离线可开） | `05-调用链路图.html` |
| `snapshot_baseline.py` | 冻结版本基线快照 + 指纹 manifest | `baselines/<label>/*` |
| `baseline_diff.py` | 两版本契约面 diff + 分级 + 用例筛选命令 | 报告 / JSON（退出码 1 = 有破坏性变更） |
| `case_lint.py` / `lint_selftest.py` | 用例规范门禁 | `lint-report.*` |
| `reconcile.py` | 三件套对账 | `reconcile-report.md` |
| `coverage_report.py` | 端点覆盖缺口 | `coverage-gap.json` |
| `run_automation.py` | 跑契约 + UI 冒烟 + 结果回写 | `automation_results.json`、`junit.xml` |
| `release_gate.py` | 投产判据 C1–C8 | `gate/release-gate.*` |

### 6.2 建议的 CI 步骤顺序（按依赖排）

```text
1. build_api_doc.py  +  build_db_dict.py      # 机制区重算
2. git diff --exit-code <机制区文件>            # 机制区过期即红灯（§2 第 2 步）
3. snapshot_baseline.py --label <当前版本>      # 指纹一致则无 diff
4. baseline_diff.py --old <上一基线> --new artifacts --out gate/baseline-diff.md
      退出码 1 → 红灯，阻断发布（BREAKING 未处置）
5. case_lint.py                               # lint fail 必须为 0
6. run_automation.py                          # 契约 + UI 冒烟，结果回写
7. reconcile.py                               # 三件套对账
8. release_gate.py                            # C1–C8 总判据
```

> 第 4 步是本次新增的**唯一新门禁**。它补的是既有门禁的盲区：C1–C8 判「本版本自己是否达标」，但**没有任何一条判「与上一版本相比是否破坏了什么」**。跨版本回归靠的就是这一步。

### 6.3 门禁 C1–C8 与本文档的分工

| 门禁 | 判什么 | 与本文档的关系 |
|---|---|---|
| C1 lint fail 0 | 用例书写规范 | 本文档 §5 引用 |
| C2 三件套对账 PASS | 清单/用例/端点一致 | 与 `baseline_diff` 互补：C2 判当下一致，diff 判跨版本变化 |
| C3 执行失败 ⊆ 已登记 | 已知失败受控 | 升级后 BREAKING 变更会产生**新**失败，需重新登记 |
| C4 xfail ⊆ 已登记 | — | 同上 |
| C5 P0 跳过数 = 0 | 关键用例无跳过 | diff 命中的 P0 用例不允许跳过 |
| C6 评审 P0 覆盖 100% | 评审完整性 | diff 新增/变更的 P0 必须进评审 |
| C7 缺陷全关闭 | 禅道状态 | 升级引入的缺陷需建单并关闭 |
| C8 结果新鲜度 ≤ 48h | 结果与本次运行绑定 | 跨版本 diff 必须基于**本次**运行的结果，不能复用旧 `automation_results.json` |

## 8. 这套机制的边界（别指望它做它做不到的事）

| 做不到 | 为什么 | 替代办法 |
|---|---|---|
| 判断变更**是否合理** | 工具只分类不评价 | 走 `02-业务规则与状态机.md` §11 待确认单，由人裁决 |
| 发现**行为变更**（同一端点、同一字段，但语义变了） | 契约面没变，diff 看不见 | 靠 §5 追溯矩阵筛选受影响用例回归；语义结论人工复核 |
| 替代 `02` 的业务文档 | 契约 JSON 里没有业务语义 | `02` 是判断区，人工维护 |
| 覆盖前端契约 | 前端无类型/路由生成器 | 路由清单在 `00-版本基线.md` §3 手工维护；前端契约缺口见 §9 |
| 保证环境可复算 | 指纹只描述仓库，不描述 DB 实际状态 | 迁移可复算（Flyway）；**运行库状态不可复算**，见 §9 |

### 10.3 结论与优先级

**能自动化**：契约层（135 端点 / 474 用例）对**本地后端**与**部署演示站**都可跑，无需额外建设。

**不能自动化**：三块硬缺口，按修复代价排序——

1. **环境接线未入库**（`00` B-06）：`8086 / 55432 / 56379` 只存在于某次手工启动的 shell 环境。代价最低的修法是补一份 `backend/.env.local.example`（或把 `.run` XML 填上 env），让「起环境」变成一条可复制命令。
2. **测试默认配置指向别处**（`00` B-07）：`api_testcases/config/env/dev.yaml` 是前身项目遗留（`8080/api`、`db port 3309`），默认 `pytest` 会打错环境。修法：改成本项目口径或直接删除该段。
3. **无 CI**：所有脚本都具备「退出码即判据」的形态（`baseline_diff` 1=BREAKING、`case_lint` fail=0、`release_gate` 0=全绿），但没有任何调度器在跑它们。修法：一条最小流水线（§6.2 的 8 步）即可，无需新工具。

**UI 层**：Playwright 与 Chromium 已就绪，但只能在**已部署的 60084/60085** 上跑；本地无前端 dev server，且 UI 套件会写共享演示库（下单/购物车）——本地全栈回归需要先把前端 dev server 纳入环境（并接受它会改演示数据）。

### 数据库检查（本地 / 远程）

> 全部命令已实测（2026-10-10）。**库名 `shang`，schema 为 `identity` + `commerce`，共 36 表 / 359 列**，与 `docs/06-baseline/01-数据字典.md` 一致。

**为什么不用裸 `psql`**：本机没有 psql 客户端，且本地 DB 跑在容器里；远程 DB 只监听 `127.0.0.1`。所以走「容器内 psql」与「SSH + 服务器内 psql」两条路。

#### 本地（Docker 容器）

```bash
# 便捷别名（建议加进 shell 配置）
alias shang-psql='docker exec -i shang-postgres psql -U shang -d shang'

# 1) 库与版本总览
shang-psql -c "SELECT current_database(), current_user, current_setting('server_version');"

# 2) 列出所有表（含 schema 与「估算」行数）
shang-psql -c "\dt commerce.*"          # commerce 24 表
shang-psql -c "\dt identity.*"          # identity 12 表
shang-psql <<'SQL'
SELECT n.nspname AS schema, c.relname AS tbl, c.reltuples::bigint AS approx_rows
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname IN ('identity','commerce')
ORDER BY 1, 2;
SQL

# 3) 查看某张表的字段 + 类型 + 可空 + 默认 + 索引（最常用）
shang-psql -c '\d commerce.address'
shang-psql -c '\d commerce."order"'     # 保留字表：\d 加不加引号都行

# 4) 用 information_schema 查字段（适合脚本化 / 与数据字典 diff）
shang-psql -c "
SELECT column_name, data_type, character_maximum_length AS len, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema='commerce' AND table_name='address' ORDER BY ordinal_position;"

# 5) 导出全库字段清单（对照 docs/06-baseline/01-数据字典.md）
shang-psql -t -A -F'|' -c "
SELECT table_schema||'.'||table_name, ordinal_position, column_name,
       CASE WHEN character_maximum_length IS NOT NULL THEN data_type||'('||character_maximum_length||')'
            WHEN data_type='numeric' THEN 'numeric('||numeric_precision||','||numeric_scale||')'
            ELSE data_type END,
       is_nullable, COALESCE(column_default,'')
FROM information_schema.columns
WHERE table_schema IN ('identity','commerce')
ORDER BY 1,2;" > /tmp/schema-dump.txt && wc -l /tmp/schema-dump.txt   # → 359

# 6) 约束与索引
shang-psql -c "
SELECT conrelid::regclass AS tbl, conname, pg_get_constraintdef(oid) AS def
FROM pg_constraint WHERE connamespace IN ('commerce'::regnamespace,'identity'::regnamespace)
ORDER BY 1,2;"
shang-psql -c "SELECT tablename, indexname, indexdef FROM pg_indexes
               WHERE schemaname IN ('identity','commerce') ORDER BY 1,2;"

# 7) 精确行数（reltuples 为 -1 表示该表从未 ANALYZE，估算不可用）
shang-psql -c "SELECT count(*) FROM commerce.spu;"
shang-psql -c "ANALYZE;"               # 刷新统计后可再看 reltuples

# 8) Flyway 迁移状态
shang-psql -c "SELECT version, description, success, installed_on FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 5;"
```

给 GUI 工具（DBeaver / pgAdmin）的连接串：**host `127.0.0.1`，port `55432`，db `shang`，user `shang`**，密码见 `docker inspect shang-postgres`。

#### 请求链路（远程 60084 / 60085 是怎么到后端的）

```text
公网 :60084 (商城)  ──网络层端口映射──→ 服务器 :8090 ─┐
公网 :60085 (后台)  ──网络层端口映射──→ 服务器 :8091 ─┤ nginx
                                                      ├─ /api/ , /admin/files/ → 127.0.0.1:8086 (Spring Boot)
                                                      └─ /  → 静态前端 /opt/shang-pivot/current/{mall,admin}
```

- `60084/60085` 在服务器上**没有监听**（`ss` 查不到），由网络层映射到 `8090/8091`；站点配置见 `/etc/nginx/sites-enabled/shang-pivot-{mall,admin}`。
- 后端与 actuator 都只绑 `127.0.0.1`（`8086` / `8087`），**外网无法直连**，所以远程 DB/接口检查必须走 SSH。

#### 环境差异与陷阱（实测）

| # | 事实 | 影响 |
|---|---|---|
| 1 | **PG 版本不同：本地 16.15，远程 14.24** | 写了 PG16 专有语法的新迁移会「本地过、部署挂」。Schema 本身当前一致（36 表/359 列/V20） |
| 2 | **本地默认端口指向别的项目**：`5432`/`6379` 是 `yy-postgres-main` / `yy-redis-main`；本项目用 `55432`/`56379` | 不覆盖 `DB_URL`/`REDIS_*` 直接启动会**静默连错库**。本地后端约定的应用端口是 **8086**（不是默认 8080） |
| 3 | 对象存储实现不同：本地无 MinIO（未部署）；远程是 `rclone-s3.service`（S3 兼容） | 文件上传/预览类用例本地跑不了、远程可以 |
| 4 | 保留字表写法：**必须带 schema 前缀**。`commerce.order` 不加引号也能解析；裸 `order` 才报语法错误 | 手写 SQL 一律写 `commerce.order` |
| 5 | `reltuples = -1` 表示从未 ANALYZE，**不是「0 行」** | 别用 `\dt` 的估算值判断数据量，要精确就用 `count(*)` |
| 6 | **演示库已被测试残留污染**（2026-10-06 批次）：本地 brand 35 行中 27 行、category 48 行中 40 行、dept 28 行中 27 行名为「自动化测试名称」；远程更严重（brand 175 行中 167 行、category 143 行中 135 行、dept 118 行中 117 行） | 与 `01-数据字典.md` 的「种子终态」（8 类目 / 8 品牌 / 32 SPU）对不上是**运行数据漂移**，不是 schema 问题。做演示或按行数断言前先确认现状；如需清理见下 |
| 7 | 扫描残留：`... WHERE name LIKE '%自动化测试%'` | 清理是**破坏性操作**，需先备份并确认，勿直接删 |

UNION ALL SELECT 'dept', count(*) FILTER (WHERE name LIKE '%自动化测试%'), count(*) FROM identity.dept;"

### 跨源被拦（`Invalid CORS request`）

**现象**：后端日志与接口都正常（不带 `Origin` 直接 curl 是 200），但浏览器里登录/注册/下单全报
`Invalid CORS request`，HTTP 403，响应头带 `Vary: Origin`。

**成因**：浏览器对非 GET 请求（含**同源** POST）也会带 `Origin`。Spring 用请求自身的 scheme/host/port 与
`Origin` 比对，不一致就按跨源处理并查白名单。Nginx 反代若把 `Host` 改写成了后端地址（默认
`proxy_set_header Host $proxy_host`），后端就把同源请求误判成跨源，白名单里没有部署域 → 403。

**两条修法（任选，可叠加）**：

1. **Nginx 透传原始 Host（改配置即生效，不用重新部署）**：
   ```nginx
   location /api/ {
       proxy_pass http://127.0.0.1:8090;
       proxy_set_header Host $http_host;          # 必须带端口，$host 会丢端口
       proxy_set_header X-Forwarded-Proto $scheme;
       proxy_set_header X-Forwarded-Host $http_host;
   }
   ```
   这样 `Origin` 与请求自身一致，后端根本不做跨源判定。

2. **后端白名单加部署域**（`application.yaml` → `shang.cors.allowed-origins`，或环境变量
   `SHANG_CORS_ALLOWED_ORIGINS=http://a:60084,http://a:60085`，逗号分隔、必须写精确 Origin）。
   改环境变量后重启进程即可，无需改代码。

> 部署地址变化时优选用环境变量，避免每次改代码重新构建。

**本部署的实际情况（2026-10-08 已修）**：服务器上两个站点的 Nginx 配置

| 文件 | 对外端口 | 反代目标 | 静态目录 |
|---|---|---|---|
| `/etc/nginx/sites-available/shang-pivot-mall` | 60084（NAT→8090） | `127.0.0.1:8086` | `/opt/shang-pivot/current/mall` |
| `/etc/nginx/sites-available/shang-pivot-admin` | 60085（NAT→8091） | `127.0.0.1:8086` | `/opt/shang-pivot/current/admin` |

原先两处都是 `proxy_set_header Host $host;`，`$host` **不含端口**，后端据此把请求端口算成 80，与浏览器
`Origin: ...:60084` 对不上才被判定成跨源。已改为 `proxy_set_header Host $http_host;`（保留端口），
改前备份在服务器 `/root/nginx-cors-backup-<时间戳>/`。

**排查这类问题的判据**：同一接口「带 `Origin` → 403，不带 → 200」且响应头有 `Vary: Origin`，
就是跨源判定问题（不是认证、不是数据库）；此时后端一定也返回了 `X-Trace-Id`，可据此查日志确认。

**幽灵功能检查法**（改完原型或实现后跑一遍）：

1. 从每张原型页提取可见动作标签（`<a|button|span|option|th|label>` 的文字），逐个在 `shang-mall/src` / `shang-admin-web/src` 里搜；
2. 命不中的，再在两个 PRD 的 §8 里搜；
3. 两边都搜不到 → 是幽灵：原型侧删掉（或 PRD 侧补文档 + 实现侧补功能），**不允许留在原型里被渲成截图**；
4. 反向：实现里有、原型没有的，也要回填原型，否则 PRD 图会漏功能。

约定：

- 依赖全局 playwright（`/usr/local/lib/node_modules/playwright`）。
- 后台原型用 `sidebar.js` 的 `window.__NAV_VERSION__='v1'|'v2'` 裁剪侧栏：**V1 页面必须是 `v1`**，否则截图会串进后续版本菜单。
- 弹窗样例集中在 `admin/dialogs.html`（V1，53 例）、`admin/dialogs-v2.html`（V2 增量，18 例）、`store/{web,h5}/dialogs.html`（C 端）。
- V2 的后台变体页：`admin/orders-enhanced.html`、`admin/product-edit-schedule.html`（它们以 V2 侧栏渲染）。
- 改了原型外观 → 跑渲染脚本 → PRD/体验设计里的图自动更新。
- **原型不得有「幽灵功能」**：原型里出现的每个控件都必须能在 PRD §8 与实现里找到对应。反向也要查：实现有、原型和 PRD 没有的，同样要补齐。检查方法见下。
- **原型改了交互，实现要跟着改**（这是本项目的硬规矩）：原型是规格，实现必须与它一致。新增弹窗一律用 `assets/modal.css` + `FormDialog` / `NoticeDialog` / `DetailDrawer`，**禁止**再写 `ElMessageBox.prompt` 或行内布局样式；库存档位一律用 `utils/stock.ts`。改完在 PRD 的「原型 ↔ 实现一致性台账」（V1 §10.A / V2 §10.A）登记。

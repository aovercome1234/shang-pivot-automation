# 自动化测试架构面试题库

> 适用范围：尚品汇项目接口自动化、UI 自动化、端到端测试、报告体系、缺陷治理、性能基线与链路追踪。  
> 使用方式：建议按“基础理解 → 设计取舍 → 证据链 → 工程治理 → 压力追问”的顺序准备。  
> 口径说明：文中数量、失败、报告指标以最近一轮 `artifacts/results.json`、`coverage.json`、`compare.json` 或性能基线产物为准；面试时不要把演示环境容量结论说成生产结论。

# 0. 面试总策略

## 0.1 一句话定义项目

这不是一个“写了几个 pytest / Playwright 脚本”的项目，而是一套围绕尚品汇商城构建的自动化质量体系：  
以接口为组织边界，以 DB / Redis / MQ / 业务不变量做有效性校验，以 xdist 和数据隔离保证并发稳定，以 Allure 扩展页做业务化报告，再通过 known_failures、覆盖率门禁、用例评审、Gitee 幂等缺陷同步和历史 diff 做质量治理。

## 0.2 2 分钟项目介绍参考

尚品汇项目包含商城 C 端、管理端和后端服务。后端是 Spring Boot / PostgreSQL / Redis / RabbitMQ，自动化框架基于 pytest + requests + Playwright + Allure，并用 pytest-xdist 做并行执行。

测试组织上，我没有只按测试文件或测试维度堆用例，而是演进成：

```text
业务域 → 业务模块 → 接口 → 测试大分类 → 用例
```

接口下再按功能正向、逆向、边界值、异常、特殊场景聚合。  
断言上，我不满足于 HTTP 200，而是继续校验 DB 落库、Redis 状态、MQ 事件、库存、金额、幂等等业务不变量。  
工程治理上，通过稳定用例 ID、用例评审、known_failures 台账、覆盖率门禁、Gitee 缺陷同步、历史 diff，把失败从“结果红绿”升级成“可归因、可追溯、可闭环”。

最近一轮基线口径是 845 条逻辑用例、890 条执行结果，其中 API 796 条、UI 94 条，接口视图聚合 141 个接口组、362 个测试大分类。  
此外，项目还接入了 SkyWalking 链路追踪和首轮性能基线，扩展报告页可以直接看到性能结果。

# 1. 整体架构与设计思想

## Q1：这个自动化体系的整体架构是怎么分层的？

### 参考回答

我会拆成六层：

```text
1. 测试资产层
   - API 用例：tests/api/endpoints、tests/api 专项
   - UI 用例：tests/ui、pages、fixtures
   - E2E 链路：tests/e2e

2. 执行引擎层
   - pytest / pytest-xdist / rerunfailures
   - Playwright 多浏览器
   - 性能基线 runner / k6

3. 测试能力层
   - ApiClient：HTTP、traceId、重试、埋点
   - 数据工厂：手机号、地址、订单、幂等键
   - DB 契约：verify_write / verify_deleted
   - Redis / MQ 校验
   - 证据采集：DB、Redis、MQ、日志、截图

4. 业务建模层
   - business_taxonomy.yaml
   - endpoint_attribution.yaml
   - case_meta.yaml
   - case_registry.json

5. 报告与观测层
   - Allure 原生报告
   - 扩展页：接口 / 分类 / 覆盖率 / 缺陷 / 历史 / UI / 性能
   - SkyWalking / Prometheus / ELK（按环境接入）

6. 质量治理层
   - known_failures 台账
   - coverage_gate 覆盖率门禁
   - review_cases 用例评审
   - Gitee issue 幂等同步
```

### 可继续追问

**为什么拆这么多层，会不会过度设计？**

不是为了拆而拆，而是每一层解决一个具体问题：

- 没有 `endpoint_attribution.yaml`，登录、地址等 setup 请求会抢占用例接口归属；
- 没有 `case_registry.json`，用例改名或参数变化会导致稳定 ID 漂移；
- 没有 `known_failures`，历史失败会拖死每轮回归；
- 没有 DB / Redis / MQ 校验，HTTP 200 会制造假绿；
- 没有扩展报告，Allure 原生树很难按接口向研发和产品讲清楚覆盖。

所以这些不是堆工具，而是把测试从脚本集合升级成可治理系统。

## Q2：接口自动化、UI 自动化、E2E 的边界是什么？

### 参考回答

### 接口自动化负责

- 参数校验：必填、类型、枚举、长度、边界；
- 业务规则：状态机、幂等、越权、库存、金额；
- 副作用：DB 落库、Redis、MQ；
- 高并发、回归和覆盖率建设。

### UI 自动化负责

- 页面真实渲染；
- 用户操作链路：登录、搜索、加购、下单、地址管理；
- 前后端联调问题；
- 浏览器兼容和关键路径回归。

### E2E 负责

- 跨越 API + UI 的完整业务闭环；
- 例如登录 → 地址 → 加购 → 下单 → 支付；
- 验证系统级串联，而不是单接口规则。

### 为什么不全堆 UI 层

因为 UI 成本高、稳定性低、定位慢。  
接口层适合高密度规则校验，UI 层适合真实用户路径，E2E 只做少量关键闭环。

## Q3：这个项目最核心的架构亮点是什么？

### 参考回答

我会讲三个。

### 亮点一：接口级测试组织

不是按文件说“测了很多接口”，而是按：

```text
业务域 → 业务模块 → 接口 → 测试大分类 → 用例
```

并通过 `endpoint_attribution.yaml` 解决 setup 请求抢主体接口的问题。

### 亮点二：多层证据链

接口层断言之外继续校验：

- DB 落库；
- Redis 状态；
- MQ 事件；
- 库存、金额、幂等不变量；
- 后端日志；
- 代码位置。

这解决的是“HTTP 200 假绿”。

### 亮点三：质量治理

包括：

- 稳定用例 ID；
- 用例评审；
- known_failures 台账；
- 覆盖率 ratchet；
- Gitee 幂等缺陷同步；
- 历史 diff；
- 性能基线进入报告。

这解决的是“测试能跑”和“质量体系能长期维护”的差距。

# 2. 接口自动化框架

## Q4：一个请求从用例执行到报告展示，中间经历了什么？

### 参考回答

以 `POST /api/orders` 为例：

1. `customer` fixture 随机创建会员；
2. `sku` fixture 按 worker 分片选择有库存 SKU；
3. `address` fixture 创建当前会员地址；
4. `ApiClient` 发起请求并记录 URL、method、请求体、响应体、traceId、耗时；
5. `endpoint_recorder` 把请求归属到当前用例；
6. 断言分层：
   - HTTP 200；
   - `code == 0`；
   - 响应结构；
   - 订单状态；
   - DB 订单和明细；
   - 库存锁定；
   - 幂等唯一；
7. Allure 动态打标签：业务域、业务模块、接口、验证维度、测试分类；
8. 报告生成后按接口聚合；
9. 失败时继续采集后端日志、DB 行、Redis / MQ 证据和代码位置。

所以一条失败用例不是只看到 `assert failed`，而是能看到：

```text
哪个接口、哪个校验点、请求/响应是什么、
DB 是否有副作用、Redis/MQ 是否符合预期、
后端哪里抛错、对应哪个已知缺陷。
```

## Q5：为什么要从“专项维度”迁移成“接口维度”？

### 参考回答

专项维度的优点是能力补齐快，例如安全、幂等、大数据量、DB、MQ 各有专项文件。  
但接口评审时有个问题：想知道 `POST /api/orders` 是否测充分，要跨很多文件找，很难回答“这个接口到底覆盖了什么”。

所以后来演进成：

```text
业务域
  └── 业务模块
        └── POST /api/orders
              ├── 功能正向校验
              ├── 逆向校验
              ├── 边界值校验
              ├── 异常校验
              └── 特殊场景校验
```

收益是：

- 测试设计更完整；
- 报告更适合接口评审；
- 正向、逆向、边界、异常、安全、幂等、DB、MQ 聚合在同一接口下。

旧专项用例没有删除，因为稳定 nodeid、known_failures、历史结果和 Gitee issue 关联都依赖它们。  
这体现了工程取舍：**组织结构可以升级，但历史资产不能轻易打断。**

## Q6：如何避免 setup 请求抢占用例的主体接口归属？

### 参考回答

这是真实踩过的问题。

下单用例 setup 会调用：

```text
POST /api/auth/login
POST /api/addresses
GET /api/products/{id}
```

如果按“运行时第一个接口”归属，下单用例可能被归到登录或地址。

解决方式是显式归属表：

```yaml
"tests/api/endpoints/test_orders.py::TestCreateOrderEndpoint::test_idempotency_replay":
  - "POST /api/orders"
```

原则是：

- 运行期 recorder 记录实际调用；
- `endpoint_attribution.yaml` 声明业务主体接口；
- 分类器优先读显式归属。

**业务主体不等于运行时第一个外部调用。**

---

## Q7：ApiClient 为什么值得单独封装，而不是直接用 requests？

### 参考回答

因为所有用例共享横切能力：

- 统一 base URL；
- token 注入；
- traceId 生成与透传；
- 超时和重试；
- 请求/响应日志；
- Allure 附件；
- 接口调用埋点；
- 失败时的上下文采集。

如果直接用 requests，这些能力会散落在每个用例里，后续改认证、改日志、改报告都会非常困难。

### 可继续追问

**重试会不会掩盖问题？**

会，所以重试策略必须受控：

- 只对明确可重试场景生效；
- 默认 rerun 次数有限；
- 报告保留失败和重试痕迹；
- 对幂等、库存、支付等写接口不能盲目重试。

# 3. 测试设计、数据隔离与稳定性

## Q8：你怎么知道一个接口应该补哪些校验点？

### 参考回答

不是凭感觉，而是从源码和风险信号推导。

| 源码 / 结构信号 | 必补测试点 |
|---|---|
| DTO 有 `@NotNull` / `@Size` / 枚举 | 逆向、边界、格式校验 |
| Controller 手动 `hasText()` | 必填、空白字符串 |
| `mapper.insert()` | 创建正向 + DB 落库 |
| `updateById()` | 更新字段、未更新字段、404 |
| `deleteById()` / 软删 | 删除状态和 DB 证据 |
| 状态机字段 | 合法/非法状态、重复操作 |
| 唯一索引 / `selectCount()` | 冲突、重复编码、幂等 |
| Redis set / expire / lock | TTL、冷却、锁定、黑名单 |
| MQ publish / listener / DLQ | 发布、消费、重复投递、死信 |
| `/admin/**`、当前用户、路径 ID | 401、403、IDOR |
| List、分页、批量方法 | 大数据量、分页边界、聚合正确 |
| 历史 500 日志 | 异常输入和缺陷护栏 |

原则：

> 出现一个约束，就至少补一条正向或逆向；  
> 出现一个副作用，就补一条副作用校验；  
> 出现一个失败模式，就补一条护栏用例。

## Q9：功能正向、逆向、边界、异常、特殊场景分别怎么落地？

### 参考回答

以支付接口 `POST /api/payment/sandbox` 为例。

### 功能正向

- 待支付订单可以支付；
- 响应成功；
- 订单状态变 `PENDING_SHIP`；
- payment 表状态 `PAID`；
- MQ 收到 `ORDER_PAID`；
- `order_event_log` 落库。

### 逆向

- 未认证请求 401；
- 他人订单支付拒绝；
- 不存在订单 40400。

### 边界

- 已支付订单再次支付；
- 已取消订单支付；
- 库存临界场景。

### 异常

- malformed JSON；
- 路径参数类型错误；
- 错误请求方式；
- 冲突业务码如 `40902`。

### 特殊场景

- 重复支付幂等；
- MQ 重复投递；
- 事件进入 DLQ；
- 支付成功后库存、金额、事件一致。

## Q10：测试数据怎么隔离？为什么不直接清理？

### 参考回答

核心策略是：

1. 会员随机手机号，避免账号互相污染；
2. SKU 按 worker 分片，降低多个 worker 抢同一库存；
3. 库存批量、登录限流等强共享场景走 serial lane；
4. 写接口必须带幂等键；
5. teardown 不随意删除业务数据，因为 DB / Redis / MQ 证据要保留给报告核验。

所以不是“不清理”，而是：

```text
随机性做隔离
串行处理强共享状态
幂等避免副作用放大
证据保留支撑追溯
```

### 可继续追问

**随机数据会不会不可复现？**

不会。每轮保存 run_id、git commit、请求响应、DB 证据、Allure 结果和稳定用例 ID。  
随机数据不是黑盒随机，而是有完整证据链的隔离数据。

## Q11：库存耗尽导致的大量连锁失败怎么定位和处理？

### 参考回答

当时某个 SKU 被多轮写用例消耗后，很多 fixture 在 `add_to_cart` 阶段失败，看起来像功能批量失败，实际根因是库存水位不足。

定位方式：

1. 看失败是否集中在同一 SKU；
2. 看失败发生在 setup 还是 call；
3. 查 `physical_stock` / `locked_stock`；
4. 判断是业务缺陷还是测试资源水位不足。

处理分两层：

- 短期补足库存，让回归恢复；
- 长期做 SKU 分片、高库存 SKU 加权、批量库存 serial、执行前数据健康检查。

这说明自动化稳定性不仅是代码问题，还包括共享资源水位治理。

## Q12：`test_endpoint_sweep` 大量报 500 并进入 known_failures，这是测出 bug 还是期望没对齐？

### 参考回答

当前 93 条失败中，80 条来自 `test_endpoint_sweep` 的 500 类失败（路径参数类型错误、畸形 JSON、空请求体、分页边界等），更像一类架构级缺陷信号，而不是 80 个孤立 bug。

按 REST 规范，这类输入错误应该返回 400 或稳定业务错误码，而不是统一 500。  
成批同类失败说明全局异常处理器没有细分异常类型。

所以处理方式不是简单把这些失败“洗白”，而是：

- 保留专项失败，作为后端缺陷护栏；
- 记入 known_failures；
- 在报告中标注是已知后端问题；
- 修复后再从台账清理并转绿。

# 4. 断言链：DB、Redis、MQ 与业务不变量

## Q13：接口到 DB 的落库校验怎么做？

### 参考回答

核心是“请求字段 ↔ DB 行字段逐字段比对”。

以创建品牌为例：

1. 调 `POST /admin/brands`；
2. 响应返回 `brandId`；
3. `verify_write()` 根据契约定位：

```yaml
POST /admin/brands:
  table: commerce.brand
  locate:
    type: response_id
  fields:
    name: name
    categoryId: category_id
```

4. 从 DB 查出刚写入的行；
5. 比较请求字段和 DB 列；
6. 校验默认值，如 `status=ENABLED`；
7. 删除时校验 `deleted=true`。

这样避免 HTTP 200 假绿。

### 可继续追问

**为什么不直接在用例里写 SQL？**

因为会散、难维护、口径不一致。统一 `verify_write()` 可以统一：

- Long / Decimal / JSONB 类型转换；
- 软删过滤；
- 证据记录；
- 契约缺失暴露；
- 报告标记 DB 校验。

---

## Q14：Redis 是怎么验证的？不是只 ping 一下吗？

### 参考回答

不是。Redis 测试围绕“缓存承担的业务语义”。

以短信登录为例：

1. 发送验证码；
2. 校验 `sms:phone:{phone}` 存在；
3. TTL 在 240–300 秒之间；
4. `sms:cooldown:{phone}` TTL 在 0–60 秒；
5. 登录成功后验证码被删除；
6. 连续失败时校验 `login:fail:*`；
7. 第 6 次返回锁定；
8. 锁定 TTL ≤ 15 分钟；
9. 登录成功清除失败计数；
10. 登出后 token 进入黑名单且 TTL > 0。

所以 Redis 不是“能连通”，而是：

```text
Key 是否对
TTL 是否对
清除时机是否对
锁定 / 黑名单是否真实影响业务
```

---

## Q15：MQ 是怎么验证的？只看消息发出去吗？

### 参考回答

不是。MQ 测的是完整事务链路：

```text
接口成功
  → 本地事务提交
  → MQ 发布
  → 消费者消费
  → 事件表落库
  → payload 与订单一致
  → traceId 贯通
```

支付链路会验证：

- `ORDER_PAID` 是否投递；
- `commerce.order_event_log` 是否落库；
- payload 中 `orderId`、金额、traceId 是否一致；
- 重复投递是否只保留一行；
- 非法事件是否进入 DLQ；
- 消费暂停后恢复是否消化积压。

所以 MQ 测试不是“消息发出去”，而是验证异步副作用最终一致。

---

## Q16：什么是业务不变量？举例说明

### 参考回答

不变量是任何操作后都必须成立的业务约束。

例如：

- 库存不能为负；
- 实物库存不能小于锁定库存；
- 一个订单不能重复支付；
- 订单金额等于明细金额之和；
- 支付成功后必须有 MQ 事件；
- 一个幂等键只能创建一个订单；
- 登录成功后验证码必须被消费。

这类断言比普通响应断言更有价值，因为它们防止“接口成功但业务数据错了”。

---

## Q17：DB / MQ 证据如何避免“事后补数据”的质疑？

### 参考回答

证据记录遵循三个原则：

1. **只记录真实执行过的 SQL / Redis 命令 / MQ 操作**；
2. 每条证据带：
   - 时间戳；
   - `PYTEST_CURRENT_TEST`；
   - `runId`；
   - 参数；
   - 真实返回值；
3. 敏感字段脱敏，例如手机号、token、密码。

比如 `helpers/evidence.py` 的 `record_db()` 会记录：

```text
endpoint、table、locate、sql、params、row
```

这不是“报告时编一个合理结果”，而是把测试执行时的真实查询固化下来。

### 可继续追问

**声明式原则和可机审校验之间还差什么？**

目前更多是“记录真实证据 + 报告展示”，下一步可以增加机器校验，例如校验证据时间必须落在用例执行窗口内、证据参数必须来自用例上下文、MQ payload 的 traceId 必须和 API traceId 一致。

# 5. MQ / Redis 报告页的数据源深挖

> 这是面试中非常值得主动讲的一块，因为它能区分“真正做过证据链设计”还是“只是页面展示”。

## Q18：三方组件报告页是真调用 Redis / MQ，还是只读当时的执行结果？

### 参考回答

既不是纯“当时执行结果”，也不是纯“浏览时实时”，而是按页面区块分三层。

### 第一层：报告构建时的真实状态快照

`build_thirdparty_report.py` 在构建报告时会真实连接中间件：

- Redis：对 4 个硬编码业务 pattern（`sms:phone:*`、`sms:cooldown:*`、`login:fail:*`、`jwt:blacklist:*`）做 `SCAN`、`TYPE`、`TTL`、`GET`，不是全库 key 总数；
- RabbitMQ：调用 Management HTTP API `/api/overview`、`/api/queues`；
- DB：查询 `commerce.order_event_log`。

结果固化到 `data.json`，并带构建时间和来源说明。  
所以总览页所谓“实时键”和“队列状态”，准确说是**报告构建时刻的真实快照**。

### 第二层：测试执行时的真实证据

测试运行期间：

- Redis 用 `RecordingRedis` 包装真实客户端，把 `GET / TTL / KEYS / SCAN` 等命令写入 `evidence.jsonl`；
- MQ 用 pika 真实发布，用 RabbitMQ Management API 真实查 DLQ，用 DB 查消费结果；
- 每条证据带时间、用例、runId。

构建报告时按 nodeid 和用例开始时间窗过滤，嵌入详情页。

所以测试步骤表里的“Redis 实际执行记录”“MQ 实际发布 / 消费证据”，来自**当时真实执行结果**。

### 第三层：浏览页面时的实时操作

详情页底部的操作按钮会直连本机 `127.0.0.1:8098` 的 `thirdparty_server.py`，由服务端再真正调用 Redis 和 RabbitMQ Management API。

如果服务未启动，页面显示只读模式，不伪造操作结果。

### 总结一句话

```text
总览看构建时真实快照；
测试步骤看执行时真实证据；
页面操作看浏览时实时调用。
```

## Q19：Redis 页面如何证明“命令和接口行为是同一次因果”？

### 参考回答

关键不是“读到某个 key”，而是“随机 key + 接口动作 + 立即读取 + TTL 区间断言”。

例如验证码用例：

1. `unique_phone()` 生成随机手机号；
2. 调 `/api/auth/sms/send`；
3. 立刻读 `sms:phone:{phone}`；
4. 断言值为 `123456`；
5. 断言 TTL 在 240–300 秒；
6. 登录成功后立即读同一 key，断言被删除。

这样即使 Redis 里有很多其他验证码，也只能读到本次随机手机号对应的 key。  
整个 Redis 文件标记为 serial，文件级原因是登录失败计数会影响同账号并行用例；黑名单类用例使用 `keys()` 前后集合差，因此也从并行隔离中受益。

### 可继续追问

**还有什么盲区？**

- Redis pattern 目前覆盖验证码、冷却、登录失败、黑名单；
- 新业务 key 前缀需要补充 pattern；
- 还没做 cache hit ratio、内存淘汰策略、慢日志的系统性性能分析。

## Q20：MQ 重复投递用例改了 eventId 后缀，它验证的是唯一键还是业务幂等？

### 参考回答

真正的判据不是 eventId，而是 `order_event_log` 仍只有 1 行。

流程是：

1. 首次支付，消费事件落库 1 行；
2. 复制原 payload；
3. 只给 `eventId` 加随机后缀；
4. 用 pika 再发一次；
5. 等消费者处理；
6. 查 DB，断言仍只有 1 行。

如果后端是按 `(order_id, event_type)` 幂等插入，那么即使 eventId 变了，也不会新增行。  
所以断言落点是行数，不是消息体表面差异。

### 可继续追问

**如果后端幂等键设计不同怎么办？**

那就要根据真实唯一约束调整断言落点，比如按 `eventId`、按 `order_id + event_type`、或按业务单号。  
测试必须跟随业务幂等设计，而不是只测消息中间件行为。

## Q21：MQ 死信队列是怎么验证的？是不是只看日志？

### 参考回答

不是看日志，而是真实调用 RabbitMQ Management API。

非法事件用例会：

1. 发布缺少 `orderId` 的事件；
2. 轮询请求：

```text
GET /api/queues/%2F/commerce.order.event.dlq
```

3. 断言 `messages > 0`；
4. 最后清空 DLQ，避免影响后续轮次。

当前用例重点验证“非法事件进入 DLQ”；“不阻塞主队列”目前还是期望语义，后续可补一条“合法事件仍能正常消费”的断言。

## Q22：`evidence.jsonl` 按 nodeid + 时间窗过滤轮次，这个设计有什么风险？

### 参考回答

风险主要有三个：

1. 文件是 append-only，长期运行会增长；
2. 如果同一 nodeid 在很短时间内重复执行，可能串轮次；
3. 如果 Allure test-cases 起始时间缺失，`start_ms=0` 时过滤失效。

更稳妥的做法是：

- 每轮运行前归档或清空 evidence；
- 用 `RUN_ID` 精确过滤；
- 保留时间窗作为兜底，而不是主机制。

这属于工程演进点，不影响当前证据真实性，但影响长期可维护性。

---

## Q23：`thirdparty_server.py` 为什么只绑定 127.0.0.1？有哪些防护？

### 参考回答

因为页面操作服务具备真实写能力，例如：

- Redis set / del；
- RabbitMQ purge；
- consume 消息。

如果暴露到公网或内网，会变成高风险操作入口。  
所以当前设计是：

- 只监听 `127.0.0.1:8098`；
- 页面从本机浏览器直连；
- key 有白名单正则；
- purge 需要确认参数；
- 敏感命令有限制。

### 可继续追问

**如果 CI 上把报告 serve 出去，这个服务还能直接开吗？**

不能。那时任何能访问该机器 8098 端口的人都可能执行操作。  
应该加 token、只暴露只读接口，或把操作服务和报告服务分离。

# 6. 并行执行与稳定性

## Q24：为什么 xdist 按接口分组，而不是按文件或方法随机分发？

### 参考回答

因为同一接口的用例经常共享状态，例如：

- 同 SKU 库存；
- 同会员购物车；
- 同地址；
- 同订单状态机。

随机分发会让同接口用例并发执行，产生伪失败。

所以并发粒度是：

```text
不同接口之间并行
同一接口内部串行
```

这是正确性优先，不是单纯追求并发度。

注意：按接口分组并行主要用于 `run_parallel.sh` / benchmark 场景；当前 nightly 的 API 回归主线仍是串行执行。

---

## Q25：两阶段执行是怎么设计的？

### 参考回答

阶段一：并行执行非 serial 用例；  
阶段二：串行执行 serial 用例。

注意：这是 `run_parallel.sh` 的执行模型；当前 nightly 的 API 回归主线仍是串行，只有 UI 层并行。

serial 包括：

- 库存批量调整；
- 登录失败限流；
- Redis 锁定类场景；
- 全局配置修改；
- 其他强共享状态场景。

这样能兼顾大部分接口快速并行和敏感场景稳定执行。

---

## Q26：rerunfailures 自动重试会不会掩盖问题？

### 参考回答

会，如果用得不好就会。

项目里的控制方式是：

- 默认只重试 1 次；
- 报告保留重试信息；
- 对共享状态问题优先做数据隔离；
- 重试仍失败则进入缺陷分析；
- 不允许用重试掩盖业务错误。

### 更深一层

`pytest_sessionfinish` 按 nodeid 取最后一次结果。  
这意味着一个用例第一次失败、第二次通过时，最终是 passed，但失败时刻留下的日志和附件仍可能存在。  
这不是矛盾，而是有意的“抖动留痕”，便于分析偶发原因。

---

## Q27：`conftest` 的 DB baseline guard 只记录不阻断，为什么？

### 参考回答

因为写用例本身会产生预期内的数据变化，不能一刀切阻断。

它更适合做“预期外变化探测器”。  
比如某轮在不该写数据的表上出现变化，说明可能有泄漏。

但它目前更多是记录和报告证据，不是硬门禁。  
如果后续要做硬门禁，可以只对“非写用例覆盖表”的异常变化阻断，例如字典表、配置表、系统表。

# 7. Allure 报告与业务分类体系

## Q28：Allure 原生报告有哪些不足？你们怎么改？

### 参考回答

Allure 原生体系适合通用结果，但有几个问题：

1. 层级不够表达完整业务结构；
2. 按文件展示不利于接口维度评审；
3. 无法直接回答某接口正向、逆向、边界、异常各有多少；
4. UI、接口、缺陷、覆盖率、历史、性能结果分散。

所以做了扩展页：

```text
业务域 → 业务模块 → 接口 → 测试大分类 → 用例
```

并增加：

- 分类统计；
- 覆盖率；
- 缺陷；
- 用例历史；
- UI 浏览器矩阵；
- 性能首轮基线。

Allure 仍承担执行结果总览，扩展页承担业务可读性。

---

## Q29：接口与用例的归属来自哪里？未归属时怎么呈现？

### 参考回答

归属来自两层：

1. 执行期 `endpoint_recorder` 录制的 `case_endpoint_map`；
2. `endpoint_attribution.yaml` 的显式主体接口声明。

有显式归属时优先显式归属。  
未归属用例不会静默丢弃，而是在 API 视图顶部单独展示“未归属接口的用例”，分类统计也会说明未归属不计入通过率。

这是报告对账设计，避免“看不见就等于不存在”。

## Q30：为什么曾出现 Overview 总数和 Suites 叶子数不一致？

### 参考回答

根因是 `test_endpoint_sweep._annotate()` 重复写了第二套 `parentSuite / suite` 标签，导致 Suites 树被重复拆分。

修复方式：

- 移除重复标签；
- 清空 Allure results；
- 全量重跑；
- 校验 Overview 与叶子节点一致。

这个问题的价值在于：  
**报告数字不一致不是 UI 小问题，而是标签写入逻辑或分类器出了问题，必须按数据一致性缺陷处理。**

## Q31：为什么要做测试大分类？

### 参考回答

因为细维度太多，如果全平铺，报告不可读。

例如一个接口下可能有：

- 参数校验；
- 边界值；
- 参数联动；
- 数据库落库；
- MQ；
- Redis；
- 幂等；
- 越权；
- 安全；
- 大数据量。

所以归并为五大类：

- 功能正向校验；
- 逆向校验；
- 边界值校验；
- 异常校验；
- 特殊场景校验。

细维度仍保留在 `验证维度` 标签里，不丢信息。  
这是“可读性”和“信息完整性”的折中。

---

## Q32：`check_report_contract.py` 只比较键和类型，不比较值，这样够吗？

### 参考回答

它防的是报告结构漂移，比如并行合并后字段丢失、类型变化、数据结构破坏。

不比较值是因为：

- 用例数会合理变化；
- 时长会变化；
- 状态分布会变化。

但代价是值域语义漂移可能检不出，例如 `status` 枚举含义改了但类型仍是 string。  
所以更完整的方案是：

- schema 契约检查；
- 关键枚举白名单检查；
- 总数字段一致性检查。

---

## Q33：失败用例的后端日志是测试时抓的还是报告时抓的？

### 参考回答

是失败时刻抓的。

`conftest` 在 `pytest_runtest_makereport` 失败时采集：

- 后端日志；
- 按 traceId 检索；
- 堆栈摘要；
- Allure 附件。

这样即使之后服务重启、日志滚动、现场恢复，也能复盘。  
这体现一个原则：**证据必须随用例生命周期落盘，不能等报告生成时再补。**

---

## Q34：报告构建链路里很多脚本失败只 warn，会不会静默降级？

### 参考回答

有这个风险。

当前设计是为了保证 Allure 主报告不被辅助视图阻断。  
但确实应该分级：

- API matrix 缺失：应该阻断；
- defects / Gitee 缺失：可以 warn；
- history / compare 缺失：可以 warn；
- performance 产物缺失：可以 warn，但如果性能是发布门禁，则应阻断。

所以这题可以回答为：  
当前是“可用性优先”，下一步要做“产物重要性分级”。

# 8. UI 自动化

## Q35：没有统一 data-testid，UI 自动化怎么保证稳定？

### 参考回答

主要策略：

1. 优先稳定角色、文本、结构定位；
2. Page Object 封装定位细节；
3. 等待条件优先于固定 sleep；
4. 每用例独立 browser context；
5. 登录态 fixtures 管理；
6. 失败保留截图、trace、必要时 video；
7. UI 负责真实路径，业务规则仍由 API 层高密度覆盖。

页面层封装例如：

- `MallHomePage`
- `MallProductPage`
- `MallCartPage`
- `MallCheckoutPage`

用例只表达业务动作，不散落定位细节。

## Q36：Playwright trace 附件为什么用官方 MIME？

### 参考回答

这样 Allure 前端可以直接嵌入 trace viewer，而不是只作为一个普通附件下载。  
截图适合快速人眼判断，trace 适合回放定位点击、请求、时序问题。  
二者互补。

## Q37：UI 多浏览器并行怎么做？

### 参考回答

逻辑用例只分配一个稳定 ID，浏览器作为执行维度进入报告，而不是让同一逻辑用例在不同浏览器下变成两个用例编号。

并行上：

- 每 worker 独立浏览器；
- 会员账号随机或按账号池隔离；
- 管理端账号每 worker 独立登录；
- 报告按“浏览器 × 用例”矩阵展示。

当前稳定口径以 Chromium + Firefox 为主，WebKit 视环境兼容性启用。

## Q38：UI 多 worker 共享同一个商城，如何防止数据冲突？

### 参考回答

主要靠“生成式隔离”：

- 随机手机号；
- 随机会员；
- 用例内清理；
- `loadscope` 把同文件用例放同 worker，减少共享 fixture 竞争。

但这不是环境级隔离。  
如果未来 UI 写链路大量并发，仍可考虑 per-worker 数据库 schema 或独立测试租户。

# 9. known_failures、评审与缺陷治理

## Q39：known_failures 是“屏蔽失败”吗？

### 参考回答

不是。

它是失败治理台账：

- 未登记失败：阻断；
- 已登记失败：允许存在，但必须有 owner；
- 是否已归因缺陷：由台账单独记录，当前 unmapped 只提示、不阻断；
- 过期失败：要求复核；
- 已修复失败：要求清理。

所以成熟不等于零失败，成熟意味着：

```text
失败可见
失败可归因
修复可验证
回退可阻断
```

---

## Q40：`bootstrap()` 批量把当前失败灌进台账，会不会把失败“洗白”？

### 参考回答

有这个风险，所以必须配合门禁和 owner。

如果一次 bootstrap 把大量未分析失败标成已知，而没有 owner、原因、过期时间，就会制造虚假稳定。

正确做法是：

- 每条 known failure 必须有原因；
- 必须有 owner；
- 必须有 expires_at；
- unowned 条目已进入质量门禁失败条件；
- unmapped 当前只提示，建议下一步也纳入失败条件；
- 修复后必须复核清理。

---

## Q41：台账按 case_id 而不是 nodeid，有什么风险？

### 参考回答

参数化用例重命名后，pytest param id 可能变化，nodeid 快照失效。  
`case_registry.json` 是 nodeid → case_id 的桥，桥断后同一缺陷可能被误判成 unexpected。

这体现稳定标识符治理的重要性：  
**用例 ID 必须稳定，nodeid 只是执行定位，不应该成为长期身份。**

---

## Q42：覆盖率门禁为什么分静态链路和 JaCoCo？

### 参考回答

静态链路覆盖回答：

```text
这个接口有没有测试路径
```

JaCoCo 运行时行覆盖回答：

```text
这些代码运行时有没有真正执行到
```

二者互补：

- PR / 快速门禁用静态链路；
- 夜间全量或专项分析用 JaCoCo。

门禁采用 ratchet：关键指标不能回退，例如接口覆盖、DB 契约覆盖保持 100%，方法/行覆盖不低于历史阈值。

# 10. Gitee 缺陷闭环

## Q43：失败用例如何变成 Gitee issue？证据链是什么？

### 参考回答

失败用例自动生成缺陷单，包含：

- 用例标题；
- 接口；
- 测试维度；
- 请求 / 响应；
- 断言意图；
- 业务 traceId；
- 后端日志；
- Allure 链接；
- 代码位置。

代码定位逻辑：

1. 如果是 500，从后端堆栈取最底层的 `com.shangpivot` 应用帧（抛出点）；
2. 定位文件与行号；
3. 取代码片段；
4. 关联当前 git commit；
5. 没有堆栈时，按端点映射回 Controller 作为兜底；
6. 生成缺陷单。

所以缺陷不是猜出来的，而是从运行证据推导。

## Q44：Gitee 同步幂等是怎么做的？

### 参考回答

在 issue body 中写入 marker：

1. 解析已有 issue marker；
2. 判断是否存在；

# 13. 架构基础概念、应用与底层实现原理

> 面试中常被继续追问“你知道底层原理吗”。这一章按“基本概念 → 项目应用 → 底层实现 → 代价/边界”组织，适合在回答完项目实践后补充。

## Q56：pytest fixture 的作用域和依赖注入底层是怎么工作的？

### 基本概念

fixture 是 pytest 的依赖注入机制，用来把“准备数据 / 创建资源 / 清理资源”从测试函数中抽离。常见作用域：

- `function`：每个用例一次；
- `class`：每个测试类一次；
- `module`：每个测试文件一次；
- `session`：整个测试会话一次。

### 项目应用

项目里做了明确取舍：

- `customer`：function 级，每个用例一个随机会员；
- `admin`：session 级，管理端登录一次复用；
- `sku`：session 级，读商品池；
- 可变链路如购物车、订单：通常 function 或独立 flow context，避免参数化用例互相污染。

### 底层实现

pytest 在收集阶段构建 fixture DAG，运行时按依赖图实例化，并在 teardown 阶段反向清理。  
作用域越大，性能越好，但共享状态风险越高；所以项目不是盲目扩大 scope，而是按“是否可变 / 是否昂贵 / 是否共享”选择。

### 面试追问点

**为什么 `admin` 可以 session，`customer` 不行？**

因为 `admin` 是只读或低频写身份，token 获取昂贵且共享风险低；`customer` 承载订单、地址、购物车等业务状态，必须隔离。

## Q57：pytest-xdist 的 `loadgroup` / `loadscope` 有什么区别？项目为什么选按接口分组？

### 基本概念

xdist 把用例分发到多个 worker：

- `loadscope`：尽量把同一个模块 / class 的用例放到同一 worker；
- `loadgroup`：按显式 `xdist_group` 分组，同组用例进入同一 worker；
- `loadfile`：按文件分组；
- 默认 `load`：按用例顺序动态分配。

### 项目应用

项目在 `conftest.py` 给非 serial 用例自动打标：

```python
item.add_marker(pytest.mark.xdist_group(name=f"ep::{endpoint}"))
```

执行时使用：

```text
--dist loadgroup
```

因此：

- 同一主体接口的用例在同一 worker 顺序执行；
- 不同接口之间并行；
- 登录限流、批量库存等强共享场景进入 serial lane，不参与并行分组。

### 底层实现

xdist 会把同一 group 的用例作为不可拆分的调度单元，整体分配给同一个 worker；不同 group 之间再按 worker 负载调度。  
这样可以避免同接口用例并发竞争 SKU、购物车、订单状态机等共享资源。

### 边界

按接口分组会降低理论并发度，所以项目用随机会员、SKU 分片、serial lane 做补充，而不是为了追求并发牺牲正确性。

## Q58：`endpoint_recorder` 怎么把具体路径归一化成接口模板？

### 基本概念

接口报告需要按模板聚合，例如：

```text
/api/products/101
/api/products/102
```

都应该归并到：

```text
GET /api/products/{spuId}
```

### 底层实现

`core/endpoint_recorder.py` 启动时读取端点模型：

```python
pattern = "^" + re.sub(r"\{[^}]+\}", "[^/]+", path) + "$"
```

也就是把 `{spuId}` 转成 `[^/]+` 正则。  
每次请求后：

1. 从 URL 提取 path；
2. 用 method + 正则匹配模板；
3. 记录 `METHOD /template`；
4. 对手机号、token、密码等字段脱敏；
5. 在 sessionfinish 时合并写 `case_endpoint_map.json`。

### 关键设计

- call 阶段优先，setup 阶段兜底；
- teardown 阶段不记录；
- 多次运行合并，后跑不覆盖前跑；
- 具体请求响应会脱敏并截断。

### 面试追问点

**如果端点模型缺失会怎样？**

会退化为具体路径，报告聚合会变差，但测试不会失败。  
这属于“埋点不能影响用例”的设计。

## Q59：DB 写契约的定位策略有哪些？底层如何保证找到刚写入的行？

### 基本概念

写接口校验必须解决一个问题：  
请求成功后，如何在 DB 中找到“刚刚那一行”？

### 项目中的定位策略

`verify_write()` 支持几类 locate：

- `response_id`：响应返回主键 ID；
- `response_field`：响应中某个字段是业务 ID；
- `path_param`：路径参数中的 ID；
- `natural`：自然键，如手机号、订单号、`cart_id + sku_id`。

### 底层实现

契约文件 `write-contracts.json` 由 `data/write_contracts.yaml` 生成。  
执行时：

1. 根据 endpoint 找表；
2. 根据 locate 拼 SQL；
3. 如果有 `deleted` 列，默认过滤软删；
4. 请求字段与 DB 列逐字段比对；
5. 对 Long、Decimal、JSONB 做类型转换；
6. 将 SQL、参数、结果行写入证据。

### 面试追问点

**为什么不能只断言“表里有类似数据”？**

因为测试要证明“这次请求导致这次落库”。  
定位不到刚写入行，校验就没有因果性。

## Q60：幂等和库存锁的底层实现是什么？

### 基本概念

幂等是指同一请求重复执行，只产生一次业务副作用。  
库存锁是为了防止并发下单导致超卖。

### 项目底层实现

下单接口要求 `idempotentKey`，后端先查：

```java
customer_id + idempotent_key
```

如果已存在订单，直接返回原订单。  
库存锁定使用数据库悲观行锁：

```sql
SELECT ... FROM commerce.stock WHERE sku_id = ? LIMIT 1 FOR UPDATE
```

然后判断：

```text
physical_stock - locked_stock >= 数量
```

否则返回库存不足。锁定后增加 `locked_stock`，取消或超时关单时反向释锁，并写入库存流水。

### 测试如何验证

- 同一幂等键重放，返回同一订单；
- DB 只有一行；
- 库存只锁定一次；
- 重复支付返回 40902，payment 仍只有一行；
- 压测后检查 `physical_stock >= 0` 且 `physical_stock >= locked_stock`。

### 面试追问点

**这是乐观锁还是悲观锁？**

当前是悲观锁，适合强一致、冲突较高的库存场景。  
代价是锁竞争可能降低吞吐，所以测试要专门观察热点 SKU 场景。

## Q61：JWT 黑名单为什么用 Redis？底层 key 和 TTL 怎么设计？

### 基本概念

JWT 本身无状态，签发后服务端不存储会话。  
logout / refresh 后要立即失效，只能引入黑名单或短 TTL + 刷新机制。

### 项目实现

后端 `TokenBlacklist` 使用：

```text
jwt:blacklist:{jti}
```

value 固定为 `1`，TTL 取该 token 类型的完整配置 TTL（access 一个固定值、refresh 一个固定值），不是按 `exp - now` 计算的剩余有效期。

校验时 JWT filter 解析 jti，调用：

```java
redisTemplate.hasKey(PREFIX + jti)
```

存在则拒绝访问。

### 测试验证

- 登出后旧 access token 立即 401；
- Redis 中存在 `jwt:blacklist:*`；
- 黑名单 key 的 TTL > 0；
- refresh 后旧 refresh token 进入黑名单。

### 代价和边界

- Redis 不可用会影响注销语义；
- 黑名单不是永久封禁，TTL 到期后自然消失；
- 如果需要强制踢出更长周期，需要额外用户状态或版本号机制。

## Q62：RabbitMQ 的 exchange、queue、DLX、retry 在这个项目里怎么落地？

### 基本概念

- Exchange：消息路由入口；
- Queue：消息存储；
- RoutingKey：路由键；
- DLX / DLQ：死信交换机和死信队列；
- Retry：消费失败后重试，超过次数进入 DLQ。

### 项目实现

订单事件使用 DirectExchange：

```text
exchange = commerce.order.event
routingKey = order.paid
queue = commerce.order.event.queue
```

主队列绑定 DLX：

```java
QueueBuilder.durable(QUEUE)
  .deadLetterExchange(DLX)
  .deadLetterRoutingKey(DLQ_ROUTING_KEY)
```

消费配置：

```yaml
retry:
  enabled: true
  max-attempts: 3
  initial-interval: 500ms
  multiplier: 2
default-requeue-rejected: false
```

非法事件或 DB 异常时，消费者抛出异常；Spring retry 按 `max-attempts: 3` 做有限重试（该参数是总尝试次数口径），最终拒绝后进入 DLQ。

### 幂等实现

消费者按 `(order_id, event_type)` 落库，捕获唯一键冲突后直接确认，达到重复投递幂等。

### 面试追问点

**为什么不用日志证明消费成功？**

因为日志可以打印但没落库不代表最终一致。  
项目用 `commerce.order_event_log` 作为消费结果的 DB 事实，再辅以 RabbitMQ Management API 看队列/DLQ 深度。

## Q64：Playwright browser context 和 trace 的底层价值是什么？

### 基本概念

Browser context 是独立浏览器会话，拥有自己的 cookie、storage、缓存。  
Trace 则记录页面快照、DOM、网络、截图，可回放定位。

### 项目实现

每个 UI 用例独立 context：

```python
context = browser.new_context(viewport={"width": 1280, "height": 720})
```

并在 context 上启动 tracing：

```python
context.tracing.start(screenshots=True, snapshots=True, sources=True)
```

结束时保存 `trace.zip`，并以官方 MIME 附加到 Allure：

```text
application/vnd.allure.playwright-trace
```

这样 Allure 前端可以内嵌 trace viewer。

### 价值

- context 隔离避免登录态和数据污染；
- trace 能回放点击、跳转、网络请求；
- 截图适合快速判断，trace 适合深入定位。

## Q65：traceId、MDC、日志和 SkyWalking traceId 是同一个东西吗？

### 参考回答

不是同一个东西，但都属于链路观测体系。

### 业务 traceId

项目自身 `TraceIdFilter` 生成或继承 `X-Trace-Id`，写入：

- MDC；
- 响应头；
- `Result.traceId`；
- DB `trace_id` 字段；
- MQ payload。

### SkyWalking traceId

SkyWalking Java agent 自动生成自己的 traceId，用于 Entry / Local / Exit span 链路。

### 当前关系

二者当前不是同一个 ID。  
项目通过 `run_id + endpoint + time window + 业务 traceId` 做关联，下一阶段可以把 SkyWalking traceId 写入日志 MDC，实现单 trace 一键跳转。

### 面试追问点

**为什么不直接只用 SkyWalking traceId？**

因为业务日志、DB 字段和 MQ payload 在生产代码里已经围绕业务 traceId 建立了一致性；引入 SkyWalking traceId 需要 agent toolkit 或插件透传，属于演进项。

## Q66：p95 / p99 和 Little's Law 在性能基线里怎么用？

### 基本概念

- p95：95% 请求不高于该耗时；
- p99：尾部耗时；
- 平均值容易被长尾拉高或拉低；
- Little's Law：`并发 ≈ 吞吐 × 响应时间`。

### 项目应用

性能基线报告展示：

- 目标 RPS；
- 实际 RPS；
- p50 / p90 / p95 / p99；
- 错误率；
- 分接口耗时。

VU 和 RPS 换算使用：

```text
并发 ≈ RPS × (平均响应时间秒 + think time)
```

### 面试追问点

**为什么不能只看平均响应时间？**

因为平均值会掩盖长尾。  
接口体验和生产容量更关心 p95、p99 和错误率。

## Q67：known_failures 的状态机底层是什么？

### 参考回答

`evaluate()` 把当前结果和台账分成几类：

- `unexpected`：本轮失败但台账无有效条目；
- `known`：台账 active 且未过期；
- `expired`：台账过期；
- `unowned`：台账存在但没有 owner；
- `unmapped`：台账存在但没有缺陷归因；
- `fixed`：台账 active 但本轮已通过。

底层输入是：

- `results.json` 当前结果；
- `known_failures.yaml` 台账；
- `case_registry.json` nodeid 与 case_id 映射；
- `defects.json` 缺陷单信息。

### 设计边界

- fixed 不自动清理，避免偶发通过误判修复；
- unmapped 当前只提示，不阻断；
- unowned 会进入门禁失败条件。

## Q68：覆盖率 ratchet 和普通阈值门禁有什么区别？

### 基本概念

普通阈值门禁是“达到某条线就过”；  
ratchet 是“只能前进，不能回退”。

### 项目应用

例如：

- 接口覆盖率保持 100%；
- 写接口 DB 契约覆盖保持 100%；
- 方法覆盖、行覆盖不得低于历史基线。

### 好处

防止短期为了方便临时删用例、降断言、砍覆盖，导致质量悄悄退化。

### 代价

需要历史基线和报告快照，不然无法判断是否回退。  
所以项目把覆盖率数据纳入归档和历史 diff。

## Q69：Schema contract 校验和值校验有什么区别？为什么项目先选 schema？

### 参考回答

`check_report_contract.py` 比较的是 JSON 结构骨架：

- 键是否存在；
- 类型是否一致；
- 数组/对象结构是否漂移。

它不比值，因为：

- 用例数会变化；
- 耗时分布会变化；
- 失败集合会变化。

但 schema 校验抓不住“枚举语义被改但类型仍是 string”这类问题。  
所以更完整方案是：

- schema contract；
- 枚举白名单；
- 总数字段一致性；
- 关键指标阈值。

# 14. 结束语：如何总结这套体系

面试收尾可以这样说：

> 这个项目不是把接口和 UI 脚本跑起来，而是围绕“质量可信度”构建了一套体系。  
> 用接口维度组织测试资产，用 DB、Redis、MQ 和业务不变量保证测试有效性，用 xdist 和数据隔离保证并发稳定性，用 Allure 扩展页提升报告可读性，再通过 known_failures、覆盖率门禁、Gitee 缺陷同步和历史 diff 做质量治理。  
> 同时，性能基线和 SkyWalking 链路追踪也被纳入同一报告体系，让功能正确性、性能可归因和缺陷闭环能放在同一个框架下持续演进。

---

## 附：最值得背的 10 个核心观点

1. 接口是组织边界，专项维度是标签，不是套件树。
2. 业务主体接口不等于运行时第一个请求。
3. HTTP 200 只是最浅层断言，DB / Redis / MQ / 不变量才有测试价值。
4. 并发正确性优先于并发度，所以按接口分组、敏感场景串行。
5. 随机数据不是不稳定，完整证据链下的随机数据才是隔离。
6. 报告数字不一致是数据一致性问题，不是 UI 小问题。
7. known_failures 是缺陷护栏，不是失败遮羞布。
8. 三方组件报告分三层：构建时快照、执行时证据、浏览时实时操作。
9. 性能公网基线不能直接当容量结论。
10. 成熟的自动化体系核心不是工具，而是建模、证据、门禁和治理。

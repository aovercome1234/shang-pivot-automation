# 性能测试实施方案

> 版本：v1.0  
> 适用范围：尚品汇商城 C 端、管理端、后端服务、PostgreSQL、Redis、RabbitMQ、对象存储的性能测试与链路追踪。  
> 目标环境：`http://49.233.135.247:60084` / `60085`；SkyWalking 服务名 `shang-pivot`。  
> 前置文档：[性能测试方案与链路监控评审](./性能测试方案与链路监控评审.md) 已记录链路探针验证结果；本文是其升级版，重点补齐负载模型、SLO、监控体系、数据规模、执行流程和落地实现。  
> 安全要求：禅道、SkyWalking、数据库、SSH、账号密码不落文档；只能放在环境变量、目标服务器受控 `.env` 或未提交配置中。

## 1. 方案成熟度目标

本方案要支持四级能力：

| 等级 | 能力 | 当前状态 |
|---|---|---|
| L1 | 单接口/单链路压测 | 已具备 |
| L2 | 混合业务负载与压测报告 | 已具备基础脚本，待首轮标定 |
| L3 | 全栈监控、瓶颈归因、压测后不变量校验 | 已实现主要脚本与关联设计，待目标环境部署 |
| L4 | 容量模型、长期回归、性能门禁 | 待首轮基线后建设 |

首轮执行后的目标不是直接宣称容量，而是产出：

1. 首轮基线指标；
2. 慢接口 TopN；
3. 慢 SQL / N+1 候选清单；
4. 资源瓶颈初判；
5. 下一轮容量目标。

## 2. 性能目标与业务负载模型

## 2.1 首轮基线目标

以下目标是**首轮假设值**，首轮执行后按实测结果修正。

| 业务链路 | 目标负载 | 到达模式 | 主要接口 | 首轮目标 |
|---|---:|---|---|---|
| 首页聚合 | 8 RPS | ramping-arrival-rate | `GET /api/home` | p95 < 800ms，错误率 <1% |
| 商品列表 | 16 RPS | ramping-arrival-rate | `GET /api/products` | p95 < 800ms，错误率 <1% |
| 搜索 | 10 RPS | ramping-arrival-rate | `GET /api/search` | p95 < 800ms，错误率 <1% |
| 商品详情 | 14 RPS | ramping-arrival-rate | `GET /api/products/{spuId}` | p95 < 800ms，错误率 <1% |
| 登录 | 5 RPS | constant-arrival-rate | `POST /api/auth/login` | p95 < 800ms，错误率 <1% |
| 下单/支付 | 1–2 TPS | 受控 VU / pacing | `POST /api/orders`、`POST /api/payment/sandbox` | p95 < 1500ms，错误率 <1% |
| 管理端读 | 3 RPS | ramping-arrival-rate | 后台 dashboard/list | p95 < 1000ms，错误率 <1% |

说明：

- 上述 RPS 是首轮演示环境基线，不是生产承诺；
- 读链路目标总 RPS 约 48，写链路目标 TPS 约 1–2；
- 如果首轮很快达到资源瓶颈，以实际拐点为准重新标定。

## 2.2 VU 与 RPS 换算

并发估算使用：

```text
并发数 ≈ 目标RPS × (平均响应时间秒 + think time秒)
```

例如：

```text
目标 10 RPS
平均响应 0.15s
think time 1s
所需并发 ≈ 10 × (0.15 + 1) ≈ 12 VU
```

因此：

- 固定并发模式用于探索容量；
- 正式基线优先使用 `ramping-arrival-rate` / `constant-arrival-rate` 控制 RPS；
- 报告必须同时写 RPS、VU、响应时间，不能只写 VU。

## 2.3 流量混合模型

首轮混合比例：

| 场景 | 占比 |
|---|---:|
| 商品列表 | 35% |
| 搜索 | 25% |
| 商品详情 | 20% |
| 首页聚合 | 15% |
| 受保护读：购物车/订单/收藏/我的 | 5% |

后续应按真实日志或运营预估校准。

### 数据分布要求

1. **商品分布**
   - 80% 请求落在 20% 热销商品；
   - 20% 请求落在长尾商品；
   - 避免所有 VU 打同一商品导致缓存失真或锁竞争失真。

2. **搜索关键词**
   - 使用真实商品词；
   - 包含热点词、普通词、无结果词；
   - 当前支持 `KEYWORDS` 环境变量注入。

3. **SKU 库存**
   - 写链路必须优先选择高库存 SKU；
   - 已实现 `pickWeightedByStock()`，按 `availableStock` 加权选择；
   - 热点 SKU 竞争场景单独设计，不与 smoke 混合。

4. **账号分布**
   - 写链路一账号一 VU；
   - 登录场景使用手机号池；
   - 避免同一账号并发清空购物车造成伪失败。

## 3. SLO / SLA 与验收标准

## 3.1 接口级 SLO

| 接口 | 优先级 | p95 | p99 | 失败率 | 断言通过率 | 备注 |
|---|---|---:|---:|---:|---:|---|
| `POST /api/auth/login` | P0 | 800ms | 1500ms | <1% | >99% | 登录风暴 |
| `POST /api/orders` | P0 | 1500ms | 3000ms | <1% | >99% | 核心交易 |
| `POST /api/payment/sandbox` | P0 | 1500ms | 3000ms | <1% | >99% | 核心交易 |
| `GET /api/search` | P1 | 800ms | 1500ms | <1% | >99% | 高频读 |
| `GET /api/home` | P1 | 800ms | 1500ms | <1% | >99% | 首页聚合 |
| `GET /api/products` | P1 | 800ms | 1500ms | <1% | >99% | 列表 |
| `GET /api/products/{spuId}` | P1 | 800ms | 1500ms | <1% | >99% | 详情 |
| 管理端 dashboard/list | P1/P2 | 1000ms | 2000ms | <1% | >99% | 后台 |

## 3.2 资源与饱和阈值

容量结论必须同时满足接口 SLO 与资源阈值。

| 指标 | 建议阈值 |
|---|---:|
| 应用 CPU | 稳态 <70%，峰值 <85% |
| 数据库 CPU | 稳态 <60%，峰值 <80% |
| HikariCP active/最大连接 | 稳态 <70%，持续接近 100% 视为风险 |
| Tomcat busy threads | 持续 >80% 视为风险 |
| Old GC 频率 | 不允许持续增长 |
| Full GC | 压测期间不应出现频繁 Full GC |
| Redis memory / evictions | 不允许持续 eviction |
| MQ queue depth | 不允许持续增长 |
| DB lock wait / deadlock | 不允许持续出现 |

## 3.3 错误预算与中止条件

### 错误预算

- 单轮场景错误率 >1%：本轮结果标记为不达标；
- 错误率连续 1 分钟 >5%：立即降载或停止；
- 出现业务不变量破坏：立即停止写链路。

### 立即中止条件

- 库存负数、超卖、重复支付、重复订单；
- 出现未解释 500 且错误 trace 持续增长；
- DB 连接池耗尽、线程池耗尽；
- MQ 积压持续增长；
- 运维侧 CPU/内存/磁盘达到安全阈值；
- 目标环境发生发布、备份或异常任务。

## 4. 环境与数据规模

## 4.1 环境代表性记录

每轮压测前必须记录：

| 项目 | 内容 |
|---|---|
| 应用版本 | git commit / 部署包版本 |
| 服务器规格 | CPU、内存、磁盘、网络 |
| 应用实例数 | 单实例或多实例 |
| DB 规格 | CPU、内存、连接数上限、磁盘 IOPS |
| Redis 规格 | 内存上限、持久化、部署形态 |
| MQ 规格 | 节点数、消费者配置、队列/DLQ |
| 压测机位置 | 同机房 / 内网 / 公网 |
| NTP | 压测机与服务器时间一致 |
| 环境干扰 | 定时任务、备份、日志轮转、其他使用者 |

当前 SkyWalking 已观察到定时任务：

```text
CommerceJobs.payTimeoutClose
CommerceJobs.scheduleOnShelf
```

这些任务会定期访问 DB。压测报告必须注明：

- 是否包含后台任务影响；
- 是否调整任务频率；
- 是否通过基线轮量化背景负载。

## 4.2 数据规模档位

| 档位 | 商品/SPU | SKU | 订单 | 会员 | 用途 |
|---|---:|---:|---:|---:|---|
| S | 当前演示数据 | 当前 SKU | 当前订单 | 当前会员 | 预检与 smoke |
| M | 1 万 SPU / 3 万 SKU | 10 万订单 | 1 万会员 | 首轮容量基线 |
| L | 10 万 SPU / 30 万 SKU | 100 万订单 | 10 万会员 | 容量外推 |

要求：

1. 数据生成脚本或 SQL 必须可复现；
2. 大数据档位需要重建索引、更新统计信息；
3. 当前小数据量结果只能称“演示环境基线”，不能直接外推生产。

## 4.3 写链路数据保护

1. 压测 SKU 必须满足安全库存水位；
2. 压测订单统一使用幂等键前缀：

```text
k6-checkout-<run_id>-<vu>-<iter>-<timestamp>
```

3. 每轮写链路前后记录：
   - SKU 库存快照；
   - 订单数；
   - 支付数；
   - MQ 事件数；
4. 不自动删除证据数据，便于复核；
5. 恢复库存需有明确脚本或后台操作流程。

## 5. 场景设计

## 5.1 已具备场景

| 场景 | 脚本 | 说明 |
|---|---|---|
| 链路探针 | `observability/scripts/verify_skywalking_trace.py` | 单接口验证 trace 完整性 |
| 写链路不变量 | `observability/scripts/check_perf_invariants.py` | 校验订单/支付/库存/MQ |
| 预检 | `observability/k6/preflight.js` | 环境可压性检查 |
| 浏览读负载 | `observability/k6/browse-load.js` | 首页/列表/搜索/详情混合 |
| 登录风暴 | `observability/k6/login-load.js` | 固定 RPS 或固定并发登录 |
| 写链路 smoke | `observability/k6/checkout-smoke.js` | 登录→加购→下单→沙箱支付 |

## 5.2 待固化场景

| 场景 | 设计目标 | 建议实现 |
|---|---|---|
| 突发流量 spike | 验证瞬时峰值、队列削峰、恢复能力 | `ramping-arrival-rate` 快速升到 2–3 倍基线，持续 1–3 分钟后降载 |
| 稳定性 endurance | 发现连接池泄漏、内存增长、日志暴涨 | 50% 峰值跑 30–60 分钟 |
| 管理端负载 | 后台 dashboard/list/export 容量 | 新增 `admin-load.js` |
| 热销 SKU 竞争 | 验证库存锁、热点行、幂等 | 指定单个高库存 SKU，独立场景 |
| 多商品购物车 | 更真实下单链路 | 2–5 个 SKU 合并下单 |
| 下单后取消/售后 | 状态机与库存回滚 | 与 checkout 分离，低频执行 |
| MQ 积压恢复 | 验证支付事件消费能力 | 短暂暂停消费或提升发布速率后恢复 |

## 5.3 token 生命周期

后端 token 有效期约 900 秒。长跑场景必须考虑 token 过期：

- `browse-load.js` 已为每个 VU 使用 `tokenProvider()` 自动刷新；
- `checkout-smoke.js` 每个账号持有独立 provider；
- 未来 endurance 场景应统一复用该机制；
- token 刷新请求会计入登录流量，报告中需说明。

## 6. 监控体系与关联方案

## 6.1 监控矩阵

| 层级 | 关键指标 | 建议来源 |
|---|---|---|
| k6 客户端 | RPS、失败率、p50/p90/p95/p99、VU、带宽、连接数 | k6 summary + Prometheus remote write |
| Nginx/入口 | upstream latency、状态码、连接数、限流命中 | nginx access log / exporter |
| Java 应用 | HTTP RT、线程池、连接池、GC、heap、CPU | actuator + Prometheus + JFR |
| SkyWalking | endpoint CPM/RT/SLA、trace、慢 span、错误 span | SkyWalking |
| PostgreSQL | QPS/TPS、active connections、lock wait、deadlock、slow query、buffer hit | postgres_exporter + pg_stat_statements |
| Redis | latency、hit ratio、memory、evictions、slowlog、connected clients | redis_exporter |
| RabbitMQ | publish/consume rate、queue depth、unacked、DLQ | rabbitmq_exporter |
| MinIO | latency、错误率、带宽 | exporter / access log |
| 主机 | CPU、load、steal、memory、disk I/O、fd、network retransmit | node_exporter |

没有上述监控时，只能输出“链路追踪验证结果”，不能输出容量结论。

## 6.2 trace / log / metric 关联

### 已实现部分

1. k6 公共库 `jsonHeaders()` 已自动注入：
   - `X-Perf-Run-Id`
   - `X-Perf-Scenario`
2. k6 所有请求默认带：
   - `run_id`
   - `scenario`
   - `timeout`
3. `platform.sh k6` 自动生成或接受 `PERF_RUN_ID`，并把 summary 写入：

```text
PERF_ARTIFACT_DIR/summary-<run_id>.json
```

4. 后端 `TraceIdFilter` 已支持把请求头写入 MDC：
   - `perfRunId`
   - `perfScenario`
5. `logback-spring.xml` 已在控制台与文件日志输出 perf 上下文：

```text
[perf=<run_id>/<scenario>]
```

6. `observability/elasticsearch/pipeline-shang-pivot-logs.json` 已同步支持可选的 `[perf=run/scenario]` 字段，避免日志结构化解析失效。

### 尚需部署后生效

上述后端 MDC 变更需要发布目标应用后才生效。发布后验证方法：

1. 执行一次带 run_id 的 k6 请求；
2. 在日志中搜索：

```bash
grep '\[perf=<run_id>' backend/logs/shang-pivot.log
```

3. 在 SkyWalking Trace 中按时间窗找到对应 trace；
4. 报告中以 `run_id + 时间窗 + endpoint` 串联 k6 summary、日志、trace、DB 校验。

### 尚未完全打通的部分

SkyWalking traceId 与业务 `Result.traceId` 仍是两套 ID。若要做到一键跳转，需要下一阶段引入 SkyWalking toolkit 或 agent 插件，将 `swTraceId` 写入日志 MDC。当前阶段先用：

```text
run_id + scenario + endpoint + time window
```

做关联。

边界说明：当前 `TraceIdFilter` 只覆盖 Web 请求线程；MQ 消费者线程不会自动继承 `perfRunId/perfScenario`。支付消费链路定位时，需要结合 `order_id`、`trace_id` 与 MQ payload 中的业务 traceId。

## 6.4 Prometheus remote write

`platform.sh k6` 默认写入目标服务器：

```text
127.0.0.1:9090/api/v1/write
```

若目标环境没有 Prometheus，需要：

```bash
export K6_PROMETHEUS_RW_SERVER_URL='http://<prometheus-host>:9090/api/v1/write'
```

否则 k6 客户端指标无法写入远程存储，只能看控制台输出。

## 7. 执行流程

## 7.1 进入条件

1. 链路探针 PASS；
2. 更新后的 k6 脚本已同步到目标服务器 `/root/k6/shang`；
3. ES 日志解析管道已重新部署，兼容 `[perf=run/scenario]`；
4. 后端 perf MDC 变更已发布，日志可输出 `[perf=<run_id>/<scenario>]`；
5. `preflight.js` 通过；
6. Prometheus remote write 可用；
7. 写链路库存与订单数据保护完成；
8. 方法级 trace 配置已部署并复验；
9. 压测期间无发布、备份或异常任务。

## 7.2 执行顺序

```text
0. 环境冻结 + 数据快照
1. SkyWalking trace 探针
2. preflight
3. 浏览读链路 smoke
4. 浏览读链路 baseline（至少 3 次）
5. 登录链路 baseline
6. 写链路 smoke + DB 不变量校验
7. 写链路 baseline + DB 不变量校验
8. spike / endurance（待脚本固化后）
9. 结果汇总与报告
```

## 7.3 命令模板

```bash

# 1. SkyWalking 探针

  --base-url http://49.233.135.247:60084 \
  --path '/api/search?q=iPhone' \
  --out "$PERF_ARTIFACT_DIR/skywalking-trace-check.json"

# 2. k6 预检；敏感账号放服务器 /root/k6/shang/.env
cd observability

export SHANG_SSH_PORT='<ssh-port>'
export SHANG_SSH_KEY_NAME='<ssh-key>'
bash ./scripts/platform.sh k6 preflight.js \
  -e BASE_URL=http://127.0.0.1:8090/api \
  -e ADMIN_BASE_URL=http://127.0.0.1:8091/admin

# 3. 浏览读链路（RPS 基线）
bash ./scripts/platform.sh k6 browse-load.js \
  -e BASE_URL=http://127.0.0.1:8090/api \
  -e RPS=50 -e STAGES=1m:20,2m:50,3m:50 \
  -e PRE_ALLOCATED_VUS=50 -e MAX_VUS=200

# 4. 登录链路
bash ./scripts/platform.sh k6 login-load.js \
  -e LOGIN_TARGET=customer \
  -e BASE_URL=http://127.0.0.1:8090/api \
  -e PHONES='<phone1>,<phone2>,<phone3>' \
  -e RATE=10 -e DURATION=2m

# 5. 写链路
bash ./scripts/platform.sh k6 checkout-smoke.js \
  -e BASE_URL=http://127.0.0.1:8090/api \
  -e PHONES='<phone1>,<phone2>' \
  -e VUS=2 -e DURATION=1m

# 6. 写链路不变量校验（在可达 DB 的机器上执行）
DATABASE_URL='<database-url>' \
python3 observability/scripts/check_perf_invariants.py \
  --prefix "k6-checkout-$PERF_RUN_ID-" \
  --minutes 30 \
  --expect-orders \
  --out "$PERF_ARTIFACT_DIR/invariants.json"
```

## 7.4 Warm-up 与重复次数

1. 每个场景先跑 1–3 分钟 warmup；
2. 正式基线至少跑 3 次；
3. 结果取中位数或均值；
4. 如果关键指标波动超过 10–15%，必须分析原因后再下结论。

## 8. 压测后不变量校验

`check_perf_invariants.py` 已实现以下检查：

| 检查项 | 说明 |
|---|---|
| 订单存在 | `--expect-orders` 时要求窗口内存在压测订单 |
| 订单幂等唯一 | 同一 `idempotent_key` 不得产生多条订单 |
| 支付唯一 | 一个订单不得有多条未删除支付记录 |
| 库存合法 | 不允许 physical_stock < 0、locked_stock < 0、physical_stock < locked_stock |
| MQ 事件存在 | 每个已支付订单必须有 `ORDER_PAID` 事件 |
| MQ 事件不重复 | 同一订单同一事件不允许落库多行 |

执行位置：必须与目标 PostgreSQL 网络可达，通常在目标服务器或运维跳板机执行。

## 9. 瓶颈分析 playbook

出现慢请求时按以下顺序定位：

1. **客户端**：k6 summary 是否所有请求都慢，还是特定接口慢；
2. **入口**：nginx upstream latency 是否明显低于应用 RT；
3. **接口**：SkyWalking endpoint RT、CPM、错误率；
4. **代码**：Controller / Service 哪个 Local span 占比最高；
5. **SQL**：JDBC span 的 `db.statement`、执行次数、耗时；
6. **DB**：pg_stat_statements、锁等待、索引、buffer hit；
7. **中间件**：Redis/MQ/MinIO span 与队列/缓存指标；
8. **资源**：CPU、GC、线程池、连接池、磁盘、网络；
9. **后台任务**：定时任务是否叠加了 DB 压力。

已发现候选优化点：

- `GET /api/search` 一次请求可能触发多次 `CatalogReadService.toCard` 与 `commerce.sku` 查询，存在 N+1 嫌疑；
- 压测时要观察 SKU 查询次数是否随结果数线性增长。

## 11. 风险与 RACI

| 风险 | 缓解措施 | Owner |
|---|---|---|
| 库存被写链路耗尽 | 高库存 SKU、库存快照、写链路限量 | 测试/开发 |
| 登录号码自动注册污染数据 | 使用手机号池、统一前缀、定期清理 | 测试 |
| 后台定时任务干扰结果 | 记录基线、调整任务频率或报告注明 | 运维/开发 |
| token 过期导致长跑失败 | tokenProvider 自动刷新 | 测试 |
| Prometheus remote write 不可用 | 执行前检查 remote write | 运维 |
| SkyWalking 采样不足 | 压测窗口临时调高采样，结束后恢复 | 运维 |
| 方法级 trace 增加开销 | 压测期开启，长期保留需评估 overhead | 开发/运维 |
| 公网入口网络波动 | 正式压测走内网，公网只做连通性 | 测试 |

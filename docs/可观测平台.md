# 可观测平台（指标 / 日志 / 追踪 / 告警）

> **平台跑在被测服务器上**（`/opt/monitoring/`，原生二进制 + systemd），不是开发机。
> 一页纸命令见 [observability/README.md](../observability/README.md)；
> 本文讲**架构、动过哪里、怎么回退**。

## 1. 四块能力与入口

平台只监听服务器回环地址，本机看 UI 需要先开 SSH 隧道
（`bash observability/scripts/open-dashboards.sh --daemon`；注意 Kibana 的隧道地址带 basePath：`http://localhost:15601/monitor/kibana/`）：

| 能力 | 组件（服务器 systemd 服务） | 本机入口 | 解决什么 |
| --- | --- | --- | --- |
| 指标 | `prometheus`(9090) + `grafana`(3000) | http://localhost:13000 （admin/admin） | 吞吐、延迟、JVM、连接池、主机资源 |
| 日志 | `filebeat` → `elasticsearch`(9200) → `kibana`(5601) | http://localhost:15601 （数据视图「尚品汇日志」） | 哪个请求失败 + 为什么失败（含 traceId 与响应体） |
| 追踪 | `tempo`(4318 OTLP / 3200 API) + 应用侧 OTel Agent | Grafana → Explore → Tempo | 接口内部哪一步慢（精确到 SQL） |
| 告警 | Prometheus 规则 → `alertmanager`(9093) → `alert-notifier`(8899) | http://localhost:19093 ；桌面通知由本机 `alert-watch.sh` 负责 | 平台自己发现问题并叫醒人 |

## 2. 为什么是"原生二进制 + systemd"

服务器**连不上 Docker Hub**（实测 `registry-1.docker.io:443` 不可达，国内加速器会被新版 dockerd
的鉴权回源校验拒掉），而 Prometheus/Grafana/Tempo/Alertmanager 都是单文件二进制，
Elasticsearch/Kibana/Filebeat 官方也提供免安装 tar 包——直接装 systemd 服务反而更简单可靠。

因为平台与应用**在同一台机器**上，链路比"平台在开发机"的版本简单得多（没有 SSH 隧道、没有日志拉取）：

| 链路 | 走法 |
| --- | --- |
| 指标 | Prometheus 直接抓 `127.0.0.1:8087`（应用 actuator 管理端口）与 `127.0.0.1:9100`（node_exporter） |
| 日志 | Filebeat 直接读 `/opt/shang-pivot/current/logs/*.log`（`filestream` 输入） |
| 追踪 | 应用把 OTLP 推到 `127.0.0.1:4318`，Tempo 就地接收 |

## 5. 与元气购（projectku）那一套的关系

**同一个平台，两台被测应用。** 服务器上原有的平台只配了元气购；本次以"加法"接入尚品汇：

- 采集：多两个 job（`shang-pivot` / `shang-pivot-host`），元气购的 job 原样保留；
- 规则：多一个规则文件，告警名带「尚品汇-」前缀——Alertmanager 按 `alertname` 分组，
  重名规则会被合并进同一条通知，前缀避免混淆；
- 仪表板：独立目录 + 独立文件夹，元气购的仪表板不受影响；
- 日志：独立索引 `shang-pivot-logs-*`（元气购是 `projectku-logs-*`），互不混杂；
- k6 客户端指标：同一个 Prometheus，用 `--tag app=shang-pivot` 区分，
  仪表板里的 k6 面板按该标签过滤。

## 7. 实测踩过的坑

1. **服务器 JVM 是 Java 17，不是 pom 里写的 21**：直接构建出的包（class 65）在服务器上
   `UnsupportedClassVersionError`，应用每 21 秒重启一次。`deploy-app.sh` 已固化
   `-Djava.version=17 clean package`（`SERVER_JAVA_VERSION` 可覆盖）。
2. **ES 管道上传的请求体就是管道本身**，不能再套一层 `{"<名字>": {...}}`，否则 400
   `[processors] required property is missing`。
3. **新增 Grafana provider 必须重启 Grafana**：仪表板 JSON 是热加载的，但 provisioning 的
   *配置*（dashboards.yml）只在启动时读一次。脚本里已按"文件有变化才重启"处理。
4. **Filebeat 用 per-input 的 `index`/`pipeline` 覆盖**：全局 output 指向 `projectku-logs-*`，
   尚品汇靠 input 级覆盖写到 `shang-pivot-logs-*` 并走 `shang-pivot-logs` 管道。
5. **服务器时钟比真实时间慢约 100 秒**（出不了网、NTP 同步不上）。同机部署下应用/Tempo/ES
   用同一时钟，span 不会被 Tempo 丢弃；但**看板上按"最近 1 分钟"查询会看不到刚产生的数据**，
   把窗口放大到 5 分钟以上即可（面板统一用 `[5m]` 窗口就是这个原因）。
6. **`executor_queued_tasks > 0` 会误报**：Spring 的 `taskScheduler` 队列常驻 1~2 个周期任务，
   尚品汇的规则已改为 Tomcat 线程占用比 + 排除 taskScheduler 的异步池规则。
7. **Tomcat 线程池指标默认不暴露**，需要 `server.tomcat.mbeanregistry.enabled=true`。
8. **雪花 ID 在 k6 里必须按字符串传**：地址/订单主键是 19 位（如 `2107309261480067073`），
   `Number()` 会丢精度，下单直接报"收货地址无效"。
9. **bash 变量紧邻中文全角字符会被吞进变量名**（`$VAR（` → 变量名变成 `VAR（`），
   `set -u` 下报 unbound variable；脚本里统一写 `${VAR}`。
10. **长连接会断**：服务器公网链路偶发抖动，部署脚本等待健康检查时的 SSH 可能被掐断
    （应用本身没事，但自动回滚会半途而废）。排查先上服务器 `systemctl status` 看真实状态。


## 8. 持续剖析（Pyroscope）与 Span Profiles 状态

- **已部署**：`pyroscope.service`（`/opt/monitoring/pyroscope/`，单进程、零配置，HTTP 4040 / gRPC 9095），
  CPU 火焰图可查（`/pyroscope/render` 返回 flamebearer，近 30 分钟 200+ 秒样本）。
- **已接入**：Grafana 数据源 `Pyroscope`（uid=`pyroscope`）；Tempo 数据源的
  `tracesToProfiles`（`service.name → service_name`，profileType `process_cpu:cpu:nanoseconds:cpu:nanoseconds`）。
- **应用侧**：OTel agent + `pyroscope-agent.jar` + `otel-profiling-java` 扩展（`OTEL_JAVAAGENT_EXTENSIONS`），
  profiling 已启动；实测 **span 上已带 `pyroscope.profile.id`**（如 `GET /api/me` 的 span）。
- **未打通**：本版 Pyroscope 1.21 没有按 profile-id 检索的 API/索引（`__profile_id__` 等标签查不到样本），
  因此 Grafana trace 视图里"点 span → 火焰图"这一步还不会出数据。
  下一步建议：升级 Pyroscope 2.x（原生 span profiles 支持）或改用 Pyroscope 2 的 OTel 接收端。

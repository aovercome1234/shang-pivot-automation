# 04 · 课程课件：从“能跑”到“企业级”

> 适用对象：已掌握 Java 基础、了解 HTTP 与浏览器开发者工具，希望把自动化测试做成工程能力的团队。
> 课程目标：能独立设计分层、可诊断、可进 CI 的 BDD 自动化框架，并能向团队讲清每个技术选择的理由。

## 第 1 课：为什么是 BDD，而不是“脚本堆”

### 1.1 三种写法对比

```gherkin
# 反例：步骤里塞满技术细节
When 我访问 http://127.0.0.1:5174/product/101 并点击 .buy-actions .btn-secondary
Then 页面出现 .pop-panel

# 正例：业务语言，技术细节下沉
When 我在商品详情页把商品加入购物车
Then 购物车应包含该商品
```

### 1.2 Feature 的四个要素

1. **角色与意图**：谁在什么场景下做什么；
2. **可执行规格**：每条语句都能被 Step Definition 匹配；
3. **稳定 ID**：`@UI-MALL-E2E-001`，用于缺陷、禅道、报告检索；
4. **分层标签**：`@api/@ui/@smoke/@regression/@negative/@e2e`。

### 1.3 Scenario Outline 与数据驱动

`features/api/02-catalog.feature`：

```gherkin
Scenario Outline: 搜索关键词的命中与未命中
  When 我匿名搜索关键词 "<keyword>"
  Then 搜索结果总数应 "<expectation>"

  Examples:
    | keyword        | expectation |
    | iPhone         | 大于 0      |
    | 不存在的商品xyz | 等于 0      |
```

**课堂讨论**：为什么不在 Step 里写 `if (keyword.equals("iPhone"))`？
因为数据与逻辑耦合后，新增数据必须改代码；Outline 把数据留在 Feature，Step 只表达通用行为。

### 1.4 依赖注入：PicoContainer

Cucumber 通过 `cucumber-picocontainer` 为每个场景创建一套 Step 类实例，并把构造函数参数自动注入：

```java
public class ApiOrderPaymentSteps {
    private final ScenarioContext ctx;
    public ApiOrderPaymentSteps(ScenarioContext ctx) { this.ctx = ctx; }
}
```

同一场景里的多个 Step 类共享同一个 `ScenarioContext`，场景结束自动丢弃，天然避免静态变量污染。

**练习**：新增一个 Step 类，注入 `ScenarioContext`，打印当前会员手机号，验证同一场景内多次调用一致、不同场景不同。

## 第 2 课：API 自动化——先测规则，再测页面

### 2.1 统一响应体

尚品汇所有接口返回：

```json
{ "code": 0, "msg": "success", "data": {}, "traceId": "32位十六进制" }
```

`ApiResult` 把 HTTP 状态与业务 `code` 分开断言：

```java
result.assertSuccess();          // HTTP 2xx 且 code=0
result.assertCode(40902);        // 业务失败：重复支付
result.assertHttpStatus(401);    // 鉴权失败
```

**重要**：很多项目的业务失败返回 HTTP 200 + `code!=0`。只断言 HTTP 状态会漏掉大量缺陷。

### 2.2 REST Assured 的三层配置

```java
RequestSpecification spec = given()
    .config(RestAssuredConfig.config()
        .httpClient(HttpClientConfig.httpClientConfig()
            .setParam("http.connection.timeout", 5_000)
            .setParam("http.socket.timeout", 30_000)))
    .baseUri(baseUrl)
    .contentType(ContentType.JSON)
    .accept(ContentType.JSON);
```

- 连接超时与读超时分开；
- 统一 Content-Type；
- 鉴权头在 `RestClient` 集中注入，业务 API 不重复拼 `Bearer`。

### 2.3 契约校验：JSON Schema

`SchemaValidator` 使用 networknt 的 2020-12 实现：

```java
SchemaValidator.validate(result.data(), "schemas/order-submit.json");
```

`schemas/order-submit.json` 要求：

```json
{
  "required": ["orderId","orderNo","status","goodsAmount","freight","payAmount"],
  "properties": {
    "orderNo": {"type":"string","pattern":"^O[0-9]{10,}"},
    "status": {"const":"PENDING_PAY"}
  }
}
```

**价值**：字段改名、类型变化、状态枚举变化会直接让契约场景失败，而不是等到前端报错。

### 2.4 负向测试清单

| 场景 | 断言 |
|------|------|
| 验证码错误 | `code=40101`，无 token |
| 冻结会员 | `code=40310`，提示“账号不可用” |
| 超库存加购 | `code=40901`，提示“库存不足” |
| 未登录访问购物车/订单 | HTTP 401 |
| 重复支付 | `code=40902` |
| 已支付订单取消 | `code=40902` |
| 会员 token 访问管理端 | HTTP 401 |

**课堂练习**：为“地址超过 20 条”“售后重复申请”“评价非已完成订单”各写一条负向场景，并说明期望业务码的依据。

## 第 3 课：UI 自动化——稳定优先于“写得快”

### 3.1 为什么选 Playwright

| 维度 | Playwright | Selenium |
|------|-----------|----------|
| 自动等待 | 内置 actionability 检查 | 需显式等待 |
| 浏览器管理 | 一条命令安装 | 需 driver 版本匹配 |
| trace | 内置 trace viewer | 需额外方案 |
| 本机条件 | 已有 Chromium | 需下载 driver |

### 3.2 Context 隔离

```java
BrowserContext context = browser.newContext(new Browser.NewContextOptions()
    .setViewportSize(1280, 720)
    .setLocale("zh-CN"));
```

- 每个场景独立 context：cookie、localStorage、缓存互不影响；
- 固定 1280×720：商城在 <768 时切换 H5 DOM，混用断点会读到不同结构；
- trace 开启截图、DOM snapshot、source，失败可直接回放。

### 3.3 选择器策略

优先级：

1. 语义/业务类：`.web-feed-grid`、`.spec-layer`、`.van-checkbox[aria-checked]`；
2. 用户可见文本：`getByRole("button", name="提交订单")`；
3. 避免：`div:nth-child(3)`、XPath 绝对路径、依赖 DOM 顺序的 `last()`。

**真实案例**：规格层与“请选择规格”提示层都是 `.pop-panel`，`last()` 会随渲染顺序变化而点错层。修复方式是锁定 `.pop-panel.spec-layer`。这类问题在报告里表现为“按钮明明可见却超时”。

### 3.4 Token 注入：API 登录 + UI 操作

```java
session.injectLocalStorage("shang_mall_access", ctx.customerToken());
```

- Playwright 的 `addInitScript` 会在页面脚本执行前写入 localStorage；
- 用于“已登录用户”的前置条件，跳过重复的登录 UI 流程；
- 但**登录本身**仍保留独立的 UI 场景，保证登录界面被真实覆盖。

### 3.5 失败留证

`BrowserSession.finish()` 在场景失败时保存：

- 全页截图（Allure 附件）；
- 页面 HTML（DOM 快照）；
- 浏览器控制台日志；
- Playwright trace zip（`playwright show-trace` 可回放每一步）。

**课堂练习**：故意把某个选择器改错，运行后从 Allure 报告打开 trace，定位是哪一步开始偏离预期。

## 第 4 课：Allure 报告——让失败“自解释”

### 4.1 结果模型

- 一个场景 → 一个 `*-result.json`；
- 步骤 → `steps` 数组；
- 附件 → `attachments`，文件落在同目录；
- 环境 → `environment.properties`；
- 执行器 → `executor.json`；
- 分类 → `categories.json`。

### 4.2 本框架的附件规范

| 类型 | 名称 | 内容 |
|------|------|------|
| API | `POST /api/orders` | 请求体、HTTP 状态、响应体、耗时、`traceId` |
| UI | `执行截图 · 场景名` | 全页截图 |
| UI 失败 | `失败截图`、`失败页面 DOM`、`浏览器控制台`、`Playwright trace` | 现场四件套 |
| 运行 | `运行环境`、`场景标签` | 地址、浏览器、标签 |
| 清理 | `清理问题` | 清理失败的资源 ID |

### 4.3 脱敏

```java
SECRET_JSON = "(\"(?:accessToken|refreshToken|token|password|secret)\"\\s*:\\s*\")[^\"]+(\")"
BEARER = "(Bearer\\s+)[A-Za-z0-9._\\-]+"
```

任何进入 Allure 的文本都会先经过 `AllureSupport.mask()`。报告可以给测试、开发、产品看，不会泄露令牌。

**课堂讨论**：为什么不在日志里打印完整 token？因为报告会被下载、转发、归档，令牌等同于密码。

## 第 5 课：测试数据治理

### 5.1 唯一数据生成

```java
public static String uniquePhone() {
    return "139" + String.format("%08d", ...);
}
```

尚品汇的演示环境对任意合法手机号 + `123456` 自动注册，因此每个写场景都能拥有独立会员。

### 5.2 登记与清理

```java
ctx.registry().registerCartItem(cartItemId);
ctx.registry().registerAddress(addressId);
ctx.registry().registerOrder(orderId);
```

`ScenarioContext.cleanup()`：

1. 待支付订单 → 取消；
2. 登记过的地址 → 删除；
3. 登记过的购物车项 → 删除；
4. 返回无法清理的问题列表。

### 5.3 为什么不能“按标题删除”

旧套件用商品标题子串删除购物车项，存在两个风险：

- 误删用户真实加购的同名商品；
- 标题在 SKU 规格拼接后变化，匹配不到。

精确 ID 是唯一可靠的方式。

**课堂练习**：模拟“场景在第 3 步失败”，验证清理器仍能删除前两步创建的数据。

## 第 6 课：并行、超时与稳定性

### 6.1 并行的前提

- 无共享可变状态（本框架用场景级 `ScenarioContext`）；
- 数据隔离（唯一会员）；
- 线程安全的浏览器管理（`ThreadLocal<Playwright/Browser>`）。

### 6.2 API 并行

```bash
mvn test -Dcucumber.filter.tags="@api" \
  -Dcucumber.execution.parallel.enabled=true \
  -Dcucumber.execution.parallel.config.strategy=fixed \
  -Dcucumber.execution.parallel.config.fixed.parallelism=4
```

实测 21 个 API 场景 1.5 秒完成，全部通过。

### 6.3 UI 为什么默认串行

- 共享演示环境，后台/库存/订单数据会互相影响；
- 单机启动多个 Chromium 内存开销大；
- 企业实践中通常按“测试环境分片”而不是“同环境高并发 UI”。

如需并行 UI，建议：

1. 每 worker 独立测试租户；
2. 固定 2 worker 起步；
3. 用 `@ui` 之外的标签切分到不同 job。

### 6.4 超时策略

| 层级 | 超时 | 位置 |
|------|------|------|
| HTTP 连接 | 5s | `RestClient` |
| HTTP 读 | 30s | `RestClient` |
| 页面默认动作 | 15s | `BrowserSession` |
| 页面导航 | 30s | `BrowserSession` |
| 支付结果 | 25s | `MallPayPage` |

原则：**等待可观察状态，不 sleep**。只有在没有可观察状态时才用固定等待，并写注释说明原因。

## 第 7 课：CI 落地

`.github/workflows/e2e.yml` 做了五件事：

1. 启动 PostgreSQL/Redis 服务容器；
2. 构建并启动后端，启动两个前端 dev server；
3. 安装 Playwright Chromium；
4. `mvn clean test` 跑全量；
5. 生成 Allure 报告并上传 artifact。

关键点：

- CI 中 `SHANG_UI_HEADLESS=true`；
- 用 `curl` 等待服务就绪，而不是固定 sleep；
- 失败也要上传 `artifacts/`（`if: always()`）；
- 报告用 Allure CLI 生成，不依赖本地 GUI。

**课堂练习**：把 workflow 拆成 `api` 与 `ui` 两个 job，说明为什么要给 UI job 单独的准备步骤。

## 第 8 课：如何评审一套自动化框架

拿到任何框架，按下面 10 个问题打分（1–5 分）：

1. 能否一条命令启动环境、执行、出报告？
2. 失败时能否在 5 分钟内定位到请求/响应/页面/代码？
3. 是否有测试数据隔离与清理？
4. 是否区分 API 与 UI 的职责？
5. 是否有稳定的用例 ID 与标签体系？
6. 是否能在 CI 干净机器复现？
7. 是否有契约校验？
8. 是否有并行策略与线程安全说明？
9. 敏感信息是否脱敏？
10. 新成员能否在一天内新增一条合格用例？

本框架对应得分：

| 问题 | 得分 | 证据 |
|------|------|------|
| 1 | 5 | `scripts/run-all.sh` |
| 2 | 5 | Allure 四件套 + traceId |
| 3 | 5 | 唯一会员 + Registry 清理 |
| 4 | 5 | API 21 / UI 12，职责分离 |
| 5 | 5 | `@API-*`/`@UI-*` + 分层标签 |
| 6 | 5 | GitHub Actions |
| 7 | 5 | 3 份 JSON Schema |
| 8 | 4 | API 可并行；UI 默认串行（有意保守） |
| 9 | 5 | `AllureSupport.mask()` |
| 10 | 4 | 文档齐全，但业务选择器仍需熟悉 |

总分 48/50。扣分项不是缺陷，而是有意的稳定性取舍。

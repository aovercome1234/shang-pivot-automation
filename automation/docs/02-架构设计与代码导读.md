# 02 · 架构设计与代码导读

## 1. 一次执行的完整链路

```
Maven Surefire
└─ RunCucumberTest（JUnit Platform Suite）
   └─ Cucumber Engine 扫描 features/
      ├─ Hooks.before：环境预检 → Allure 环境信息 → 按 @ui 启动浏览器
      ├─ Step Definitions
      │  ├─ Api*Steps → 领域 API → RestClient → REST Assured → 后端
      │  └─ *UiSteps  → Page Object → Playwright → 商城/管理端
      └─ Hooks.after：截图/trace → 数据清理 → RunSummary
```

## 2. 分层与职责

| 层 | 代表类 | 只做什么 | 明确不做 |
|----|--------|----------|----------|
| Runner | `RunCucumberTest` | 指定 feature 路径、glue、Allure 环境 | 不写断言 |
| Hooks | `Hooks` | 预检、浏览器开关、失败留证、清理、摘要 | 不写业务步骤 |
| Steps | `ApiAuthSteps`、`MallCheckoutUiSteps`… | 业务语句 → 领域动作 + 断言 | 不拼 HTTP、不写长选择器 |
| API | `AuthApi`、`OrderApi`… | 端点、请求体、响应解析 | 不编排场景 |
| Page | `MallProductPage`、`AdminProductsPage`… | 页面导航、元素定位、页面状态 | 不写业务规则 |
| Core | `RestClient`、`BrowserSession`、`AllureSupport`… | 超时、日志、附件、上下文、清理 | 不含业务 |

## 3. 核心类导读

### 3.1 TestConfig

`config/TestConfig` 是唯一配置入口：

- `SHANG_` 前缀优先，兼容无前缀与 `-D` 系统属性；
- 启动时不做网络访问，`EnvironmentProbe` 负责可达性；
- `runDir()` 创建 `artifacts/run-<RUN_ID>/{screenshots,failures}`；
- `describe()` 输出到 Allure 和日志，报告环境页可直接看到本次地址与浏览器参数。

### 3.2 EnvironmentProbe

`core/env/EnvironmentProbe` 在第一个场景前检查 API、商城、管理端：

- 使用 JDK `HttpClient`，**固定 HTTP/1.1**。Vite 对明文 HTTP/2 升级处理不友好，默认 HTTP/2 会超时，导致“服务明明活着却预检失败”。
- 任一目标不可达直接抛 `IllegalStateException`，不跳过、不假绿。
- 错误信息附带一键启动命令。

### 3.3 RestClient 与 ApiResult

```java
ApiResult result = ctx.order().submitDirect(addressId, "10026", 1, key).assertSuccess();
String orderId = result.data().path("orderId").asText();
```

- `RestClient` 负责超时、`Authorization: Bearer`、JSON 序列化、响应解析；
- 每次请求/响应写入 Allure 附件，`AllureSupport.mask()` 把 `accessToken/refreshToken/password` 与 `Bearer xxx` 替换为 `***`；
- `ApiResult` 统一暴露 `status/code/message/data/traceId`，`assertSuccess()` 的失败信息包含完整响应体，定位问题不需要再翻日志。

### 3.4 ScenarioContext

PicoContainer 按场景注入同一个实例，承载：

- 唯一手机号（`TestData.uniquePhone()`）、会员/管理员 token；
- 领域 API 工厂：`cart()/order()/address()/payment()/admin()`；
- 场景状态：商品标题、订单号、最后一个响应；
- `TestDataRegistry`：登记本场景创建的购物车项、地址、订单；
- `cleanup()`：取消仍待支付的订单、删除登记过的地址与购物车项。

清理采用**精确 ID**，不按标题模糊匹配，避免误删其他用例/真实用户数据。

### 3.5 BrowserSession

- 每个场景新建 `BrowserContext`，天然隔离 cookie/storage；
- Playwright/Browser 按线程持有，可在 API 层并行时互不干扰；
- 每个场景开启 trace（截图 + DOM snapshot + source）；
- 结束：成功也保存全页截图；失败额外保存 HTML、控制台日志、trace zip；
- `injectLocalStorage()` 可在页面脚本执行前写入 token，用于“API 登录 + UI 操作”的快速准备。

### 3.6 Page Object

- `BasePage` 只提供导航、路径断言、Toast、通用弹层；
- 选择器锁定语义结构（`.web-feed-grid`、`.spec-layer`、`.van-checkbox[aria-checked]`），不依赖易变的下标；
- 规格弹层与“请选择规格”提示层都是 `.pop-panel`，因此加购必须锁定 `.pop-panel.spec-layer`，这是实际踩过的坑。

### 3.7 Allure 集成

- Cucumber 插件：`io.qameta.allure.cucumber7jvm.AllureCucumber7Jvm`；
- 运行前写 `environment.properties`、`executor.json`、`categories.json`；
- 每个 UI 场景附截图；每个 API 调用附请求/响应；失败附 DOM/控制台/trace；
- Feature 名称自动成为 Suite，标签成为 Allure Tags。

### 3.8 RunSummary

`Hooks` 在场景结束时登记结果，JVM 关闭时写 `run-summary.json`：

```json
{
  "summary": {"total": 33, "passed": 33, "failed": 0, "passRate": 100.0},
  "api": 21,
  "ui": 12
}
```

Scenario Outline 的多个 Examples 行名称相同，因此 key 使用“名称 + 递增序号”，否则会互相覆盖（本框架已修复）。

## 4. 测试数据策略

| 数据 | 策略 |
|------|------|
| 会员 | `139` + 8 位随机数，首次成功登录自动注册 |
| 地址 | 场景内创建，登记 ID，结束后删除 |
| 购物车 | 场景内添加，登记 cartItemId，结束后删除 |
| 订单 | 场景内创建，登记 orderId；待支付订单结束前取消，已支付订单保留但归属唯一会员 |
| 管理端 | 优先只读；发货场景使用本场景创建的订单，不影响演示数据 |

## 5. 失败诊断顺序

1. Allure 场景页看失败步骤与附件；
2. API 失败看同一步骤的请求/响应附件与 `traceId`；
3. UI 失败看全页截图 → DOM → 控制台 → trace（`playwright show-trace`）；
4. 数据问题看 `cleanup` 附件与 `run-summary.json`；
5. 环境问题看 `EnvironmentProbe` 输出与 `artifacts/logs/*.log`。

## 6. 扩展新用例的步骤

1. 在 `features/api|ui/` 新建或追加 feature，写业务语言；
2. 在对应 `*Steps` 中增加步骤，只调用领域 API/Page；
3. 新增页面时在 `ui/pages/` 建 Page Object，继承 `BasePage`；
4. 写数据必须 `register...`，保证清理；
5. 跑 `mvn test -Dcucumber.filter.tags="@你的标签"`，确认 Allure 附件齐全。

# 05 · 落地指南与常见问题

## 1. 迁移到另一个项目：检查清单

### 1.1 环境与配置

- [ ] 确认后端/前端/数据库的启动方式，写成 `scripts/start-local.sh`；
- [ ] 把所有地址、账号、超时集中到 `TestConfig`；
- [ ] 确认演示账号、验证码、测试数据生成规则；
- [ ] 确认本地端口不与已有服务冲突（本机曾因 8086 被 20 天前进程占用而启动失败）。

### 1.2 分层

- [ ] API 优先：先覆盖登录、查询、写链路、状态机、权限；
- [ ] UI 只保留关键旅程与页面级回归；
- [ ] 每个写操作都能通过 API 准备和清理。

### 1.3 数据

- [ ] 每个场景唯一标识（手机号/租户/订单号前缀）；
- [ ] 登记所有创建的资源，`@After` 精确清理；
- [ ] 清理失败让场景红，不静默放过。

### 1.4 报告

- [ ] 每个 API 调用附请求/响应；
- [ ] 每个 UI 场景附截图；
- [ ] 失败附 DOM、控制台、trace；
- [ ] 环境信息写 `environment.properties`；
- [ ] 敏感字段脱敏。

### 1.5 CI

- [ ] 服务容器与健康检查；
- [ ] 等待服务就绪，不用固定 sleep；
- [ ] 失败也上传产物；
- [ ] 报告作为 artifact 保留 7–14 天。

## 2. 常见问题

### Q1：场景通过但清理失败，为什么让场景变红？

因为残留数据会污染下一次运行，属于“隐形的失败”。如果只是打印日志，问题会累积到某天突然大面积失败。企业级做法是：清理失败 = 场景失败，并附上残留资源 ID。

### Q2：为什么没有默认开启失败重试？

重试会掩盖真实缺陷，尤其是 UI 的时序问题。本框架优先通过以下方式消除 flake：

- Playwright 自动等待；
- 唯一测试数据；
- 明确的前置条件；
- 失败现场四件套。

如果团队确实需要重试，建议只对带 `@flaky` 标签的场景在 CI 层重跑，并单独统计“重试后通过”的比例，作为质量指标而不是修复手段。

### Q3：UI 场景能不能并行？

可以，但有前提：

1. 每个 worker 独立测试租户/账号；
2. 不从共享库存/订单中抢数据；
3. 限制 worker 数（建议 2 起步）；
4. 观察服务器与浏览器内存。

本框架默认串行，是为了在单机演示环境里稳定复现；API 已经验证可 4 worker 并行。

### Q4：接口返回 HTTP 200，但业务失败，怎么断言？

用 `ApiResult.assertCode(expected)`，不要只看 HTTP 状态。尚品汇的业务失败统一返回 `{code: 40xxx, msg: ...}`，HTTP 仍是 200。

### Q5：UI 元素明明可见，Playwright 却超时？

优先检查：

- 是否有同名元素/多层弹层（本项目的 `.pop-panel` 同时用于规格层与提示层）；
- 是否被遮罩层挡住（actionability 检查会等待可点击）；
- 是否在 iframe/Shadow DOM 中；
- 是否是 H5/Web 两套 DOM（视口是否被改动）。

打开失败 trace 可以逐步看到“等待哪个 locator、当时页面长什么样”。

### Q6：为什么 Allure 报告必须用 HTTP 打开？

Allure 报告的 `data/` 是通过 XHR 加载的，`file://` 会被浏览器同源策略拦截，页面空白。用：

```bash
python3 -m http.server 18080 --directory automation/artifacts/allure-report
```

### Q7：`mvn clean` 之后报告为什么没了？

`clean` 删除 `target/`，包括 `target/allure-results`。重新执行测试后用 `scripts/generate-report.sh` 再生成。

### Q8：如何只跑某一条用例？

```bash
mvn test -Dcucumber.filter.tags="@UI-MALL-E2E-001"
```

或用行号：

```bash
mvn test -Dcucumber.filter.tags="@ui" -Dcucumber.filter.name="完整购买旅程.*"
```

### Q9：如何新增一个页面对象？

```java
public final class MallFavoritesPage extends BasePage {
    public MallFavoritesPage(BrowserSession session) {
        super(session, TestConfig.MALL_BASE_URL);
    }
    public void open() {
        open("/favorites");
        waitVisible(page().locator("h1.page-title"), 15_000);
    }
}
```

Step 中只调用 `new MallFavoritesPage(session).open()`，不要在 Step 里写选择器。

### Q10：如何保证选择器不随重构失效？

- 优先使用业务语义 class（`.product-card`、`.spec-layer`）与可访问角色；
- 与前端约定关键元素的稳定属性（如 `data-testid`）；
- 避免 `nth-child`、绝对 XPath、依赖渲染顺序的 `last()`；
- 选择器集中放在 Page Object，重构时只改一处。

## 3. 已知边界

| 边界 | 说明 | 后续建议 |
|------|------|----------|
| UI 并行 | 默认串行 | 独立租户后可开 2 worker |
| 浏览器 | 仅 Chromium | 需要跨浏览器时增加 Firefox/WebKit job |
| 视觉回归 | 未接入 | 可接 Playwright `toHaveScreenshot` 或 Percy |
| 网络 Mock | 未使用 | 异常分支可用 `page.route()` 补 |
| 文件上传 | 未覆盖 | MinIO 未在本地启动，后续单独加 |
| 性能 | 未覆盖 | 已有 k6/可观测平台，另行执行 |
| 重试 | 默认关闭 | 用 `@flaky` + CI 重跑统计 |
| Allure 趋势 | 单次运行 | 保留历史 results 或接 Allure TestOps |

## 4. 维护节奏建议

| 频率 | 动作 |
|------|------|
| 每次提交 | 跑 `@smoke`（约 1 分钟） |
| 每日 | 跑全量 + 归档 Allure 报告 |
| 每周 | 检查 flake 率、清理 test 数据、更新选择器 |
| 每次发版 | 全量 + 手工探索性测试 |
| 每季度 | 升级依赖、评审框架缺口、更新课程材料 |

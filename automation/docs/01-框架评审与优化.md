# 01 · 框架评审与优化

> 评审对象：仓库内 `ui_testcases/`（Java 21 + Cucumber 8 + Playwright，12 个 UI 场景）与业界常用组合
> （cucumber-jvm、REST Assured、Playwright Java、Allure 2）。
> 目标：不是再写一套 demo，而是给出可落地的企业级分层、可观测、可维护、可进 CI 的自动化框架。

## 0. 参考来源与取舍

| 来源 | 借鉴内容 |
|------|----------|
| cucumber/cucumber-jvm 官方示例 | Feature 组织、Scenario Outline、标签、glue 扫描、PicoContainer 注入 |
| rest-assured/rest-assured | RequestSpecification 复用、统一超时、JsonPath 断言 |
| microsoft/playwright-java | BrowserContext 隔离、auto-wait、trace、Page Object |
| allure-framework/allure-java | `allure-cucumber7-jvm`、环境信息、步骤附件、分类 |
| 仓库内 `ui_testcases/` | 稳定用例 ID、失败留证、不假绿、页面对象分层 |
| 外部 `shang-pivot-automation` 仓库 | 本次网络不可达，未能直接比对代码；只借鉴“API + UI + 报告”整体目标 |

结论：不照搬某一个框架，而是取各家已验证模式，结合本项目实际（Vant 弹层、固定验证码、Long 转字符串、统一响应体）落地。

## 1. 结论摘要

现有 `ui_testcases` 的骨架方向是对的：分层清楚、失败留证、不假绿、有稳定用例 ID。但它更接近“能跑通的单机套件”，
距离企业级还有 6 类硬缺口：**报告体系、测试数据隔离、API/UI 分层、并行与稳定性、CI 门禁、可诊断性**。

新框架 `automation/` 保留其优点，并逐项补齐：

| # | 现有缺口 | 严重度 | 新框架的优化 |
|---|----------|--------|--------------|
| 1 | 只有 Cucumber HTML/JSON + 自定义 JSON，没有 Allure；无法按 feature/severity/owner 聚合，也没有历史趋势 | P0 | 接入 `allure-cucumber7-jvm`，统一 suite/epic/feature/story/severity/owner 标签；生成 `allure-report` |
| 2 | 测试数据共享：固定账号、固定购物车、固定商品；清理靠标题子串匹配，可能误删用户数据 | P0 | 每场景唯一手机号（自动注册新会员）+ `TestDataRegistry` 精确登记/清理；管理端优先只读 |
| 3 | 所有验证都走 UI，后端业务规则（运费、幂等、库存、状态机）验证成本高且不稳定 | P0 | API 层用 REST Assured 验证契约与规则；UI 只验证关键用户旅程，形成“金字塔” |
| 4 | 无并行、无重试策略、无可诊断上下文；一次超时只能看到一张 PNG | P1 | API/UI 分层标签；API 可并行；UI 默认串行并支持 2 worker；失败附全页截图、DOM、控制台日志、Playwright trace |
| 5 | 断言偏弱：分页只断言“有翻页器”、搜索只断言首行含关键字、金额只校验格式 | P1 | 断言可观察结果：总数变化、排序单调性、金额等于商品价×数量、状态机前后置条件 |
| 6 | 无 CI；README 明确“CI 手动” | P1 | GitHub Actions：服务容器 + 起后端/前端 + 分标签执行 + Allure artifact |
| 7 | 无日志框架，只有 stdout；token/请求体无脱敏策略 | P1 | SLF4J + Logback，按 run 落文件；日志与 Allure 附件统一脱敏 Authorization/refreshToken |
| 8 | 配置散落在 `Env` 常量；缺配置校验；默认值把演示凭据写死在代码 | P2 | `TestConfig` 集中管理 + 启动校验 + `.env.example`；默认值仅用于本地演示并显式标注 |
| 9 | 无 JSON Schema 契约校验；接口字段靠手工断言 | P2 | 关键接口加 JSON Schema（home/product/cart/order），契约变更即失败 |
| 10 | 无 Page Object 复用规范之外的组件抽象；弹层/Toast 逻辑散落在步骤里 | P2 | `BasePage` + 组件方法（Toast、Dialog、Popup），步骤只表达业务语言 |
| 11 | 单浏览器、单视口；H5 断点（<768px）与 Web 混用会读到不同 DOM | P2 | 固定 1280×720，视口作为配置项；H5 作为独立 profile，禁止混跑 |
| 12 | 无运行摘要/趋势数据；只有 Cucumber JSON | P2 | 每次运行输出 `artifacts/run-<id>/run-summary.json`（场景数/通过率/耗时/失败原因） |

## 2. 目标架构

```
automation/
├─ src/test/java/com/shangpivot/automation
│  ├─ runner/            JUnit Platform Suite 入口（Cucumber 引擎）
│  ├─ config/            TestConfig：环境变量、默认值、启动校验、脱敏
│  ├─ core/
│  │  ├─ api/            RestClient：超时、日志、Allure 附件、统一响应解析
│  │  ├─ ui/             BrowserSession：上下文隔离、trace、截图、控制台日志
│  │  ├─ allure/         AllureSupport：环境信息、分类、附件
│  │  ├─ data/           TestDataRegistry：唯一数据生成、登记、清理
│  │  └─ env/            EnvironmentProbe：API/商城/后台可达性预检
│  ├─ api/               AuthApi / CatalogApi / CartApi / AddressApi / OrderApi / AdminApi
│  ├─ ui/pages/          Mall*/Admin* Page Objects
│  ├─ steps/             按领域拆分的 Step Definitions（API / UI / Common）
│  ├─ hooks/             Hooks：场景生命周期、失败留证、清理
│  └─ context/           ScenarioContext：场景内共享状态（PicoContainer）
└─ src/test/resources
   ├─ features/api       认证、商品、购物车、订单支付、管理端
   ├─ features/ui        商城浏览、购物车结算、端到端购买、管理端
   ├─ schemas/           JSON Schema 契约
   └─ junit-platform.properties
```

### 分层职责

| 层 | 职责 | 不该做什么 |
|----|------|-----------|
| Feature | 业务语言描述“谁在什么条件下做什么，期望什么” | 不写选择器、URL、SQL、接口路径 |
| Steps | 把业务语句翻译成领域动作与断言 | 不直接拼 HTTP、不写长串 Playwright 选择器 |
| API/Page | 封装协议与页面细节，提供意图明确的方法 | 不做业务断言编排 |
| Core | 配置、超时、日志、附件、清理、浏览器生命周期 | 不含业务逻辑 |

### 测试金字塔

- **API 用例（约 60%）**：契约、参数校验、状态机、权限、幂等、库存与运费规则。
- **UI 用例（约 30%）**：登录、搜索、加购、结算、支付、订单状态、后台关键页面。
- **端到端（约 10%）**：一条完整购买旅程，作为发布冒烟。

## 3. 企业级质量门禁

| 门禁 | 规则 |
|------|------|
| 失败即失败 | 任一场景失败，Maven 返回非 0；禁止 `testFailureIgnore=true` |
| 不假绿 | 预检失败（服务不可达）直接失败，不 skip |
| 数据隔离 | 写操作必须有唯一标识；场景结束自动清理；清理失败让场景红 |
| 可诊断 | 失败必须同时有：全页截图、页面 HTML、浏览器控制台、Playwright trace、API 请求/响应 |
| 报告 | Allure 报告 + `run-summary.json`；报告内可见环境、耗时、失败分类 |
| 标签 | `@api/@ui/@smoke/@regression/@negative/@e2e` + 稳定用例 ID |
| 并行 | API 可并行；UI 默认串行，允许按 worker 数显式开启 |
| 安全 | 不提交真实密钥；日志与附件对 Authorization/refreshToken 脱敏 |

## 4. 本次落地范围

- API：认证（含负向、冻结账号）、商品列表/详情/搜索/排序、购物车增删改选、地址 CRUD 与默认地址、
  下单（运费门槛、幂等）、沙箱支付与重复支付、取消订单与状态守卫、管理端登录/看板/商品/订单。
- UI：商城首页、登录成功/失败、搜索空态、商品详情加购、购物车未勾选拦截、结算确认、完整购买旅程、
  订单取消、管理端登录/看板/商品搜索。
- 运行产物：Allure 报告、JUnit/Cucumber 报告、每场景截图、失败 trace/DOM/控制台、运行摘要。

## 5. 与“简单 demo”的边界

以下能力不是可选项，而是本框架的验收条件：

1. 同一套代码既能跑 API 也能跑 UI，且标签可分层执行。
2. 每个写场景使用独立数据，重复执行不互相污染。
3. 失败现场可直接从 Allure 报告定位到请求体、响应体、截图、DOM 与 trace。
4. 本地一条命令启动依赖，一条命令执行，一条命令出报告。
5. CI 可在干净机器上复现同一套结果。

# 接口级测试点识别与校验生成方法

> 最后更新：2026-11-04
> 适用范围：`pytest_automation/tests/api/endpoints/` 下的接口级场景用例，以及按接口聚合的巡检/落库/中间件用例。

核心原则：**接口为组织边界，业务场景为执行单元，DB / Redis / MQ / 幂等 / 安全 / 大数据量等作为验证维度和校验点**。生成不是“拍脑袋补边界值”，而是先解析接口契约与源码副作用，再按维度展开；只要接口存在某种**约束、状态变化、副作用、外部资源或失败模式**，就必须有对应的校验点。

---

## 1. 生成流程

```text
接口契约（Controller/DTO/OpenAPI）
  + DB 结构（表、列、唯一索引、软删）
  + 中间件副作用（Redis Key、MQ 发布/消费）
  + 业务状态机（订单/支付/售后/评价状态）
  + 安全边界（认证、角色、资源归属）
  + 历史缺陷与 500 日志
        ↓
测试点清单（按维度分组）
        ↓
接口级测试代码（类级上下文 + 参数化 + 分层断言）
        ↓
Allure 聚合：业务域 → 业务模块 → 接口 → 测试大分类 → 用例
```

报告结构固定为：

```text
业务域
  └── 业务模块
        └── METHOD /path
              ├── 功能正向校验
              ├── 逆向校验
              ├── 边界值校验
              ├── 异常校验
              ├── 特殊场景校验
              └── 其他校验
```

## 2. 测试点从哪里来（识别信号）

### 2.1 Controller / DTO → 必填、格式、枚举、边界

| 识别信号 | 生成的校验点 | 示例 |
|---|---|---|
| `@RequestBody`、手动 `hasText()` 判断 | 必填缺失、空白字符串 | 品牌缺 name、仓库缺 name |
| `@NotNull` / `@NotBlank` / `@Size` / `@Pattern` | 必填、长度、手机号格式、编码格式 | 地址手机号非法、名称 65 字符 |
| 枚举或有限状态字段 | 合法值、非法值 | 售后 `type=REFUND` / `NOT_A_TYPE` |
| 数值字段 quantity / page / size | 0、负数、1、最大值 | 购物车数量 0 / -1 / 1 |
| `List<...>` / 数组 | 空数组、单项、多项、上限项 | 20 个购物车项下单 |
| Controller 中查重逻辑 | 唯一性冲突 | 字典 code 重复返回 40900 |

### 2.2 Mapper / Service → DB 落库

| 识别信号 | 校验点 |
|---|---|
| `mapper.insert()` | 响应 ID 定位 DB 行；请求字段 ↔ DB 列逐字段比对；默认列正确；失败场景不落库 |
| `selectById()` + `updateById()` | 更新字段确实变化；不该变的字段不变；不存在 ID 返回 40400 |
| `deleteById()` / 软删字段 | 删除后行不存在或 `deleted=true`；被引用时不能删除；列表不可见 |
| 多表写入 / `@Transactional` | 多表一致性；失败不产生半提交 |

由 `helpers/db_contract.py` 的 `verify_write()` / `verify_deleted()` 承接，避免只断言 HTTP 200 的“假绿”。

### 2.3 状态机 → 状态流转、重复操作、冲突

看到 `PENDING_PAY / PAID / PENDING_AUDIT / COMPLETED / HIDDEN` 等状态判断时，补：

- 正确状态可以操作；
- 错误状态不能操作；
- 重复操作有明确业务结果；
- 状态流转后 DB 一致。

例：支付 `待支付订单可支付 → 支付后 PENDING_SHIP → 重复支付 40902 且 payment 只有一行`；售后 `创建后 PENDING_AUDIT → 审核后 COMPLETED`。

### 2.4 幂等键 / 唯一索引 / 重复调用 → 幂等校验

信号：`idempotencyKey`、DB 唯一索引、duplicate key 捕获、409xx 冲突码、MQ 可能重复投递、用户可重复点击（支付/下单/加购）。

校验语义：**同一业务请求重复执行，只产生一次业务副作用**。

```text
同幂等键重放 → 返回同一 orderId、订单只有一行、库存只锁一次
二次支付     → 40902、payment 仍然只有一行
重复投递     → 同 order_id + event_type 只保留一行
```

### 2.5 Redis 操作 → 缓存、TTL、锁、黑名单

信号：`redisTemplate.opsForValue().set(..., TTL)`、`expire()`、`delete()`、`sms:phone:*`、`login:fail:*`、`jwt:blacklist:*`。

| 副作用 | 校验点 |
|---|---|
| 验证码 | Key 存在、TTL 0 < ttl ≤ 300、登录成功后 Key 被消费 |
| 冷却 | 第一次成功、冷却内第二次被拒、错误不刷新冷却 |
| 登录失败计数 | 连续失败到阈值锁定、锁定 TTL ≤ 15 分钟、成功清零 |
| Token 黑名单 | 登出后原 Token 立即失效、黑名单带 TTL、不永久封禁 |

原则：**代码中出现缓存副作用，且该副作用会影响业务行为，就必须校验**。

### 2.6 MQ 发布者 / 消费者 → 消息、幂等、重试、DLQ

信号：`RabbitTemplate.convertAndSend`、Exchange/RoutingKey、`@RabbitListener`、retry 配置、DLQ/DLX、事件表、消费者唯一键。

标准拆法：

1. 接口完成后消息真实发布；
2. 消费者真实消费；
3. 事件落库（如 `commerce.order_event_log`）；
4. Payload 与业务数据一致；
5. traceId 贯通；
6. 重复投递幂等；
7. 非法消息重试后进入 DLQ。

只验证“接口返回成功”会漏掉异步链路，因此 MQ 链路必须是 API → DB → MQ 三段闭环。

### 2.7 认证 / 权限 / 资源归属 → 安全与越权

| 识别信号 | 校验点 |
|---|---|
| `/admin/**` 路径 | 未登录 401、会员 Token 403 |
| 依赖当前用户 ID | 是否允许操作他人资源 |
| 路径 `{id}` | IDOR：其他会员能否读取/修改/支付/取消 |
| 请求体携带资源 ID（如 addressId） | 资源是否属于当前用户 |
| 登出 / 刷新 / 黑名单 | Token 生命周期安全 |

除返回码外，还必须验证：无 DB 副作用、无 Redis 副作用、无订单/库存/支付状态变化。

### 2.8 列表 / 循环 / 批量 → 大数据量校验

信号：`List` 入参、`Page` 分页、`batch-*`、批量库存扣减、金额汇总。校验点：

- 1 项 / 20 项 / 上限项；
- size=0、-1、1、100，大页码；
- 金额、数量、库存聚合正确；
- 失败不产生部分副作用；
- 响应时间可接受。

### 2.9 请求生命周期 → 异常输入与请求方式

由 `test_endpoint_sweep.py` 自动展开，无需人工逐个写：

- 错误请求方法（405）；
- malformed JSON；
- 路径参数类型错误（`/api/orders/abc`）；
- 缺失 body / 错误 Content-Type。

### 2.10 历史缺陷与 500 日志 → 缺陷护栏

已知后端缺陷（如畸形 JSON 返回 500、review rating 越界 500）进入 known_failures 台账和 Gitee 缺陷，不复制到接口级新模板；新场景必须保持通过，缺陷修复后由台账清理机制转绿。

## 3. 规则速查表

| 识别到什么 | 至少增加什么校验 |
|---|---|
| 必填 / 长度 / 枚举 / 数值范围 | 逆向、边界、错误提示、无落库 |
| mapper.insert/update/delete | API + DB 逐字段比对 |
| 状态机 | 状态前置、状态流转、非法状态 |
| 幂等键 / 唯一约束 / 重复调用 | 重放、单行、一次副作用 |
| Redis set/delete/expire/lock | Key、TTL、冷却、锁定、黑名单 |
| MQ publish/listen/retry/DLQ | 事件、消费、Payload、traceId、重复投递、DLQ |
| `/admin/**` / 当前用户 / 资源 ID | 401、403、IDOR、越权 |
| List / Page / batch | 批量、上限、分页、聚合、失败无副作用 |
| conflict / exists | 重复编码、重复操作、409 系列 |
| 500 日志 / 历史缺陷 | 已知失败台账、缺陷单、回归护栏 |

## 4. 测试代码组织模板

```text
一个接口或一组紧密 CRUD 接口
  ├── 类级上下文：复用会员、地址、SKU、类目等只读资源
  ├── 参数化逆向/边界：保留每个测试点独立失败粒度
  ├── 正向用例：API → DB → MQ/Redis 分层断言
  └── 特殊场景：幂等、安全、大数据量、冲突单独成用例
```

可变链路使用函数级上下文，避免类级共享状态污染；`data/endpoint_attribution.yaml` 显式声明主体接口，避免夹具中的登录/列表等 setup 请求抢占接口归属。

参考实现：

- `tests/api/endpoints/test_orders.py` — 订单接口：API/DB/MQ 分层 + 幂等/批量/越权
- `tests/api/endpoints/test_cart_address.py` — 加购合并、默认地址
- `tests/api/endpoints/test_auth_payment_after_sales.py` — Redis 登录、支付 MQ、幂等、售后审核、评价隐藏
- `tests/api/endpoints/test_admin_crud.py` — 管理端品牌/类目/字典/部门/仓库 CRUD

## 5. 业务约定（校验时的口径）

- 成功：HTTP 200 + `code == 0`；
- 业务失败：HTTP 200 + `code != 0`（如 40902 订单状态非法）；
- Bean 校验失败：HTTP 400 + `code == 40000`；
- 未认证：HTTP 401 + `code == 40100/40103`；
- 提示信息需包含关键字段名，断言用关键字而非整句，避免文案改动引起误报。

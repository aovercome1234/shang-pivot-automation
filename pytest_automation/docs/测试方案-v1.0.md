# 尚品汇自动化测试方案 v1.0

> 适用代码：本仓库 `backend/`（Spring Boot 4.1.1 + PostgreSQL 16）、`shang-mall`（C 端）、`shang-admin-web`（后台）。
> 执行框架：`pytest_automation/`（pytest + requests + Playwright + Allure）。
> 本方案在 v0（145 条既有用例）基础上，落地了评审提出的 P0/P1 改善点：测试数据基线、水平越权、业务不变量、DB 驱动数据、traceId 诊断、flaky 重跑。

---

## 1. 目标与范围

**目标**：以源码为真值源，建立"源码 → 端点模型 → 用例 → 数据 → 执行 → 报告"的可重复流水线，并保证：
- 可重复：每轮执行前有数据基线快照，执行后可对比污染；
- 可定位：失败时带 traceId 与后端日志片段；
- 有深度：除契约断言外，覆盖业务不变量与安全越权。

**范围**：

| 层 | 覆盖对象 | 用例载体 |
|---|---|---|
| 接口契约 | 135 个端点（方法/路径/参数/鉴权） | `tests/api/*.py` + `api_testcases` 清单 |
| 业务链路 | 登录→加购→下单→支付→发货→收货→售后→评价 | `tests/e2e/`、BUS-* 清单 |
| 业务不变量 | 库存三态守恒、金额守恒、订单状态机 | `tests/api/test_invariants.py`（本方案新增） |
| 安全 | 无凭证、篡改 token、SQLi/XSS、**水平越权 IDOR** | `tests/api/test_security.py` + `test_security_idor.py`（新增） |
| UI | 商城/后台关键旅程 | `tests/ui/`（Playwright） |

**不在范围**：真实支付清结算、压测/容量、V3 智能客服（模块未实现）。

## 3. 测试分层与用例设计

### 3.1 契约层（每端点 5 类）
正向 / 鉴权缺失（401）/ 参数校验（400）/ 幂等重放 / 边界值。边界值从 DB 列定义推导（`VARCHAR(n)`、`NUMERIC` 精度），不凭空造。

### 3.2 业务链路层
按 `B*` 稳定 ID 组织：`B-LOGIN`、`B-CART`、`B-ORDER`、`B-PAY`、`B-SHIP`、`B-AFTERSALE`、`B-REVIEW`。

### 3.3 不变量层（v1.0 新增核心）
| 不变量 | 断言点 | 判断依据 |
|---|---|---|
| 库存守恒 | 下单后 locked+qty、physical 不变；取消后 locked 复原；`physical = locked + available` | `commerce.stock` + `/api/products/{id}` |
| 金额守恒 | `pay_amount = total_amount + freight`；Σ(`order_item.subtotal`) = `total_amount` | `commerce.order` / `order_item` |
| 状态机 | PENDING_PAY→(pay)→PENDING_SHIP→(ship)→PENDING_RECEIVE→(confirm)→COMPLETED；取消仅限 PENDING_PAY | `OrderController` / `OrderSubmitService` |
| 幂等 | 同 `idempotentKey` 重放返回同一 orderId | `OrderSubmitService:54-59` |

### 3.4 安全层（v1.0 补强）
- 无 token / 过期 token / 篡改 token / 跨端 token（已有）；
- **水平越权（IDOR）**：A 建资源，B 的 token 尝试读/改/删 A 的订单、地址、购物车项，断言 40400/40100 且资源未被改动（新增）；
- 注入与 XSS：登录手机号 SQLi、搜索 XSS 载荷惰性化（已有）。

## 4. 测试数据策略

| 层 | 内容 | 来源 | 生命周期 |
|---|---|---|---|
| L1 种子基线 | 类目/品牌/SPU/SKU/库存/运营位/字典 | Flyway 迁移 | 环境级；**执行前 `pg_dump` 快照**，执行后可恢复 |
| L2 演示账号 | 7 个会员（13500000005 为 FROZEN 负面账号）、admin | 迁移种子 | 环境级；仅登录类用例使用 |
| L3 运行时工厂 | 随机手机号（任意号 + 固定码 123456 自动注册）、地址、幂等键 | `helpers/data_factory.py` | 用例级，用完即弃 |
| L4 夹具链 | customer → address → cart_item → order | `fixtures/api_fixtures.py` | 用例级，pytest 依赖注入 |
| L5 DB 驱动 | 从 `stock`/`sku`/`spu` 查真实在售 SKU 与库存水位 | `helpers/db.py`（新增） | 只读；保证用例数据与库一致，杜绝硬编码 SPU |

**纪律**：
1. 写用例只用 L3/L4 隔离账号，不动 L2 演示账号；
2. 下单必带 `idempotentKey`；
3. 库存断言只断"增量"和等式，不断绝对值；
4. DB 只读封装统一在 `helpers/db.py`，用例不散写 SQL（API 能查到的优先走 API）。

**基线防污染**：session 级 fixture 记录执行前后指纹（关键表行数 + 库存总量），差异写入 Allure 附件与 `artifacts/db-baseline-diff.json`；执行前快照见 §8。

## 5. 依赖建模与执行编排

```
浏览器/API 调用 → 端点 → Controller → Service → Mapper → 表（call-graph.json）
                        └── 鉴权前置（401 类用例反向验证）
                        └── 资源 ID 传递（order.addressId → address.id 等）
                        └── 状态机（order.status 流转）
```

**执行顺序**：pytest 夹具链天然保证依赖序（`order` 依赖 `customer/sku/address`）；跨用例共享资源（配置、库存）标记串行；API 可并行、UI 串行。
**选测**：源码变更后用 `build_call_graph.py` + `reconcile.py` 反查受影响端点，只跑相关链路（后续接入 CI）。

## 6. 断言策略（Oracle 分层）

| 层 | 断言内容 | 工具 |
|---|---|---|
| L1 传输 | HTTP 状态、Content-Type、traceId 格式 | `core/assertions.py` |
| L2 业务码 | 成功 0 / 失败数值码 / 参数 400 | `ok()` / `error()` |
| L3 结构 | 响应 schema、分页结构 | `schemas/` |
| L4 业务语义 | 字段值、状态、金额 | 用例内 |
| L5 内部一致性 | 库存守恒、流水、金额拆解 | `helpers/db.py`（仅 API 不可见部分） |

失败诊断：`helpers/diagnose.py` 依据响应 `traceId` 抓取后端日志片段挂到 Allure（`backend/logs/shang-pivot.log`）。

## 8. 执行流程

```bash
cd pytest_automation

# 0) 前置：基础设施 + 后端
docker start shang-postgres shang-redis shang-minio        # 或 docker compose up -d
java -jar backend/shang-server/target/shang-server-0.0.1-SNAPSHOT.jar  # 期望 /api/home=200

# 1) 基线快照（P0：可重复性）
docker exec -e PGPASSWORD=shang shang-postgres pg_dump -U shang shang \
  > artifacts/db-baseline.sql

# 2) 执行（环境变量注入凭据，不落文件）
TEST_ENV=dev ADMIN_PASSWORD='***' \
  .venv/bin/python -m pytest -m api -q \
  --alluredir=artifacts/allure --clean-alluredir

# 3) 报告
bash scripts/allure_report.sh           # 生成静态站
# 或 bash scripts/allure_report.sh --serve

# 4) 可选：恢复基线
cat artifacts/db-baseline.sql | docker exec -i -e PGPASSWORD=shang shang-postgres psql -U shang -d shang
```

**flaky 治理**：`--reruns 1 --reruns-delay 1`（pytest-rerunfailures），重跑结果在 Allure 中标记 retry；连续 flaky 的用例进 `known-failures.json` 隔离清单。

## 11. v1.1 增量（2026-10-28）

- **用例编号**：`API-<模块前缀>-NNN`（如 `API-ADDR-001`），与 `test_cases.md` 一致；标题前置编号，报告按名称排序即编号正序。编号在 `conftest.pytest_collection_modifyitems` 中按收集顺序分配，不依赖手工维护。
- **幂等专项**（`tests/api/test_idempotency.py`，7 条）：下单幂等键重放（同/不同请求体、缺键拒绝）、重复支付、重复发货、重复加购合并、重复删除；均以库表行数（payment/shipment/cart_item/order_item）佐证"只生效一次"。
- **大数据量专项**（`tests/api/test_bulk_data.py`，6 条）：size=100 大分页、page=9999 深翻页、搜索大分页、批量建 6 单后翻页一致性、批量加购 15 SKU 金额校验、管理端大分页；软 perf 门禁 3s/8s。
- **失败留痕**：任何 failed/broken 自动附加「失败依据」（阶段、堆栈、最后请求响应、traceId）+ 后端日志片段；UI 另附截图/DOM/trace。分类规则改为 8 类互斥（Allure 一条用例可命中多分类，故不设兜底分类）。演示入口：`DEMO_FAILURE=1 pytest -m demo`，产出独立报告 `artifacts/failure-demo-report/`。

### 11.1 校验专项（v1.2）
- `tests/api/test_validation.py`（22 条）：以源码注解 / 数据库约束为真值，按「必填性 → 非空/空白 → 类型格式 → 长度上下界 → 取值范围 → 引用完整性」六维取等价类与边界（上限、上限+1、下限、0、负值、超大值）。
- 覆盖对象：登录手机号/验证码、管理端密码、地址姓名/详细地址/手机号、购物车数量、下单明细与数量、售后必填/枚举/原因长度、评价必填/评分范围/类型、分页参数。
- 结果：15 通过、7 失败，失败即缺陷 D-06～D-12（500 或非法输入被放行），用例保留为回归护栏，修复后自动转绿。

### 11.2 参数联动校验（v1.3）
- `tests/api/test_validation_interactions.py`（41 条）：在单字段等价类/边界之外，覆盖三类跨字段关系——
  **必填性联动**（A 合规、B 缺失/空白）、**匹配性联动**（格式都合法但业务不匹配，如手机号对+验证码错/超长）、
  **判定顺序**（多字段同时非法时先报哪个错，固化短路规则）。
- 覆盖：登录（10 组合 + 正向）、管理端登录（5）、地址六必填字段逐个缺失（7）、加购 skuId×quantity（5）、
  下单幂等键×地址×商品×数量（6）、售后订单×类型×原因（4）、评价订单项×评分×内容（3）。
- 固化顺序：加购 quantity 先于 SKU 存在性；下单 idempotentKey → addressId → 商品 → quantity；
  售后 必填 → 枚举 → 订单；管理端登录多字段同时缺失时允许任一必填提示（Bean Validation 顺序不稳定）。
- 结果：38 通过、3 失败（D-13 加购缺 skuId、D-15 加购缺 quantity、D-14 评价缺 rating，均为 500）。

### 11.3 单接口全维度矩阵（v1.4）
- `tests/api/test_endpoint_matrix_orders.py`（17 条）：以 `POST /api/orders` 为样板，把**边界值、参数组合、幂等、大数据量、异常**五个维度集中在一个模块，报告里一个 feature 即可感知该接口全部测试点。
- 边界值：quantity 0/-1/1/库存+1、幂等键空白；参数组合：cartItemIds 与 skuId 并存（购物车优先）、缺键+地址非法（先报键）、无明细、数量 0；幂等：同键同参/换参重放；大数据量：20 项合并下单、订单列表 size=100；异常：畸形 JSON、skuId 类型错误、500 伪造项、未认证。
- 结果：15 通过、2 失败（D-16 畸形 JSON → 500、D-17 skuId 非数字 → 500）。
- 推广方式：新接口按同一模板建模块（`tests/api/test_endpoint_matrix_<接口>.py`），五个维度各留 2–5 条代表用例。

### 11.4 全接口巡检（v1.5）
- 生成器：`scripts/build_endpoint_matrix.py` 读取 `api_testcases/artifacts/endpoint-model.json`（135 端点真值模型），产出 `data/endpoint_matrix.json`（397 条巡检用例）。
- 七类检查：安全-匿名 401、安全-跨角色越权 401/403、逆向-资源不存在 404、逆向-路径参数类型 4xx、边界-分页零/负/超大值不 5xx、异常-畸形 JSON 400、异常-空请求体不 5xx；全部为拒绝类/只读类请求，不产生业务副作用。
- 执行：`tests/api/test_endpoint_sweep.py`；报告按端点分组（feature=METHOD path），安全与健壮性可逐接口查看。
- 结果：397 条中 317 通过、80 失败，失败归并为 D-18～D-21 四类根因（类型转换/消息解析/缺参/请求体校验），建议在 GlobalExceptionHandler 统一修复。
- 维护：后端新增/删除端点后重跑生成器即可同步巡检用例，无需手写。

### 11.5 接口视图页面（v1.6）
- 映射采集：`core/endpoint_recorder.py` 在 ApiClient 层记录「用例 call 阶段 → METHOD + 归一化路径」，会话结束合并落盘 `artifacts/case_endpoint_map.json`（夹具创建/清理阶段不采集，避免噪声）。
- 结果关联：conftest 为每条 Allure 结果写入 `pytest_nodeid` 标签（Allure fullName 会丢参数/类名），报告据此精确聚合。
- 页面生成：`scripts/build_api_matrix.py` 合并端点模型 + OpenAPI + 映射 + Allure 结果，产出 `ext/manifest.json`、`ext/data/api-matrix.json` 与静态资源；`allure_report.sh` 在 generate 后自动执行并注入悬浮入口。
- 交互：接口列表（搜索/方法过滤/仅看失败）、参数与返回值示例悬浮查看 + 复制（标注来源）、测试点「详情」抽屉按维度分组并深链到 Allure 用例。

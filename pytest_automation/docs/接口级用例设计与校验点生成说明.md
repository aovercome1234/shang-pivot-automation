# 接口级用例设计与校验点生成说明

> 版本：v1.0 ｜ 最后更新：2026-11-03
> 适用范围：`pytest_automation/tests/api/endpoints/` 下的接口级用例；旧专项用例作为回归对照
> 核心模型：**接口为组织边界，场景为执行单元，维度为标签**

---

## 1. 总体思路

用例不是按“测试维度文件”散乱堆叠，也不是凭经验补几个边界值，而是按下面流水线生成：

```text
接口契约解析 → 副作用识别 → 按维度拆分测试点 → 分层断言 → 接口归属与分类 → 报告聚合
```

1. **接口契约解析**：从 Controller / DTO / Bean Validation / OpenAPI / MyBatis-Plus 实体 / DB 表结构提取
   请求方式、路径、参数类型、必填性、枚举、长度、数值范围、响应结构与业务码。
2. **副作用识别**：找出该接口会触碰的表、Redis Key、MQ 事件、库存/状态机等外部状态。
3. **按维度拆测试点**：每个接口固定覆盖功能正向、逆向、边界、异常、特殊场景（幂等/安全/大数据量等）。
4. **分层断言**：每个测试点至少有一层断言；正向事务按 HTTP → 业务码 → DB → 中间件逐层验证。
5. **接口归属**：通过 `data/endpoint_attribution.yaml` 显式声明主体接口，避免夹具 setup 抢占归属。
6. **报告聚合**：Allure Suites 按「业务域 → 业务模块 → 接口 → 测试大分类 → 用例」展示。

---

## 2. 接口契约提取清单

生成用例前，对每个接口先确认以下事实，全部来自源码或运行证据，不臆造：

| 项 | 来源 | 用途 |
|---|---|---|
| METHOD / PATH | `@GetMapping` 等注解 | 端点唯一标识、报告聚合 |
| Path/Query/Body 参数 | Controller 签名、DTO 字段 | 逆向/边界/组合测试点 |
| 必填/格式/枚举/长度 | DTO 校验注解、业务校验代码 | 等价类与边界值划分 |
| 业务错误码 | `ErrorCode`、异常处理器 | 期望断言（40000/401xx/409xx） |
| 写表映射 | MyBatis-Plus 实体、字段映射 | DB 落库断言 |
| Redis 职责 | 验证码/冷却/锁定/黑名单代码 | 缓存一致性与安全用例 |
| MQ 职责 | 发布者/消费者/事件表 | 消息队列用例 |
| 状态机 | 订单/支付/售后流转代码 | 幂等与冲突用例 |
| 量级边界 | 批量/分页/限购逻辑 | 大数据量用例 |

失败响应约定（当前项目）：

- 成功：HTTP 200 + `code == 0`
- 业务失败：HTTP 200 + `code != 0`（如 40901 库存不足、40902 状态非法）
- Bean 校验失败：HTTP 400 + `code == 40000`
- 未认证：HTTP 401 + `code 40100/40103`
- 无权限：HTTP 403 + `code 40300`

## 3. 维度 → 测试大分类映射

维度是细粒度标签，报告里收敛成固定的测试大分类：

| 测试大分类 | 包含的维度 |
|---|---|
| 功能正向校验 | 功能、功能正向、数据库落库、消息队列、缓存一致性、数据一致性、CRUD 往返、数据驱动、冒烟、UI 功能、端到端 |
| 逆向校验 | 参数校验 |
| 边界值校验 | 边界值、边界与校验、参数组合、参数联动 |
| 异常校验 | 异常、请求方式 |
| 特殊场景校验 | 安全、越权、幂等、大数据量、接口巡检 |
| 其他校验 | 兜底 |

接口组内分类顺序固定：

```text
功能正向校验 → 逆向校验 → 边界值校验 → 异常校验 → 特殊场景校验 → 其他校验
```

实现位置：`core/business_taxonomy.py`（维度与分类）、`conftest.py`（Allure 标签注入）、
`scripts/group_suites_by_endpoint.py`（接口分组与分类节点插入）。

## 4. 各维度的测试点与校验点设计

### 4.1 功能正向

- **选取**：一组合法、典型、业务代表性的入参。
- **校验**：响应 `code=0`；响应 ID/状态/金额正确；DB 行与请求一致；状态机流转正确；
  涉及中间件时继续校验 Redis/MQ/事件表。
- **示例（沙箱支付）**：
  - API：响应 `status == PENDING_SHIP`
  - DB：`commerce.payment.status=PAID`，`commerce.order.status=PENDING_SHIP`
  - MQ：消费者落库 `ORDER_PAID`，`payload.orderId` 与订单一致，traceId 贯通

### 4.2 逆向校验（参数校验）

- **选取**：等价类分组——必填缺失、空白、类型非法、枚举非法、格式错误。
- **组织**：`pytest.mark.parametrize` 参数化，每个测试点独立失败粒度。
- **校验**：HTTP/业务码符合约定；错误提示含关键字段；**不产生副作用**（无 DB 行、不签令牌、不锁库存）。
- **示例（品牌创建）**：缺品牌名称 → 40000；缺类目 → 40000；且 `commerce.brand` 无新增行。

### 4.3 边界值校验

- **选取**：按实际约束取 min/min-1/max/max+1：数量 0/1、长度 64/65/256、分页 0/1/100。
- **校验**：
  - 合法边界（如 `quantity=1`）必须成功并落库正确；
  - 非法边界必须被业务码拒绝，且不产生副作用。
- **示例**：`quantity=1` 创建待支付订单，DB 明细 `quantity=1`；`quantity=0/-1` 返回 40000 且不锁库存。

### 4.4 异常校验

- **选取**：malformed JSON、错误请求方式、路径参数类型错误、重复编码、状态机冲突。
- **校验**：不出现无解释 500；业务码明确（40000/40900/40902）；不产生半提交数据。
- **示例**：字典重复编码 → 40900 + “已存在”，且不新增行。

### 4.5 DB 落库校验

- **机制**：`helpers/db_contract.py` 的 `verify_write()` / `verify_deleted()`，
  契约来自 `data/write_contracts.yaml` → `artifacts/write-contracts.json`。
- **定位方式**：响应 ID、自然键（手机号、code、sku+cart）、路径参数、多列自然键。
- **校验**：请求字段 ↔ 表列逐一比对；生成列（id/状态/时间/trace_id）单独断言；删除校验 `deleted=true`。
- **示例（品牌）**：响应 brandId → `SELECT * FROM commerce.brand WHERE id=brandId`
  → name/category_id 与请求一致，status 默认 ENABLED。

### 4.6 Redis 缓存一致性

- **选取**：接口涉及的缓存职责——验证码、冷却、登录失败计数、Token 黑名单。
- **校验**：Key 存在/被消费、TTL 范围、冷却秒数、锁定窗口、黑名单 TTL。
- **示例（短信登录）**：
  - `sms:phone:{phone}` 存在，`0 < TTL ≤ 300`，`cooldownSec == 60`
  - 登录成功后验证码立即失效，`identity.customer` 有 NORMAL 会员行

### 4.7 MQ 消息队列

- **选取**：接口的事务事件（如支付成功发布 ORDER_PAID）。
- **校验**：事务提交后投递；消费者写入事件表；payload 与业务数据一致；traceId 贯通。
- **特殊场景**：重复投递幂等（唯一键去重）、非法事件重试进 DLQ、暂停消费积压后恢复。
- **证据**：真实请求/响应、事件 Payload、队列/DLQ 深度，写入 Allure 附件与三方组件视图。

### 4.8 幂等

- **定义**：同一业务请求重复执行，只能产生一次业务副作用。
- **校验**：同幂等键重放返回同一 orderId；订单只有一行；库存只锁一次；二次支付 40902 且 payment 只有一行。
- **覆盖层**：API 响应 + DB 行数 + 中间件事件，不能只看响应。

### 4.9 安全与越权

- **选取**：未登录、会员 Token 调管理端、跨会员数据访问（IDOR）。
- **校验**：401/403 正确返回；**无 DB/Redis/MQ 副作用**。
- **示例**：使用他人地址下单被拒，不创建订单；非管理员登录管理端返回 403。

### 4.10 大数据量

- **选取**：20 项购物车合并下单、分页 size=100、批量下架、深翻页。
- **校验**：明细行数、金额守恒、库存守恒、响应时间、失败时不部分生效。

## 5. 代码组织模板

```text
一个接口或一组紧密 CRUD 接口
  ├── 类级上下文：复用会员、地址、SKU、类目等只读资源（避免重复登录/造数）
  ├── 函数级上下文：可变链路（加购、下单、支付）用独立数据，避免状态污染
  ├── 参数化逆向/边界：每个测试点独立失败粒度
  ├── 正向用例：API → DB → MQ/Redis 分层断言
  └── 特殊场景：幂等、安全、大数据量、冲突独立成用例
```

当前迁移文件：

- `tests/api/endpoints/test_orders.py`：`POST /api/orders`，参数化逆向/边界 + API/DB/MQ 正向 + 幂等/批量/越权/未认证
- `tests/api/endpoints/test_cart_address.py`：加购/地址，同 SKU 合并、默认地址
- `tests/api/endpoints/test_auth_payment_after_sales.py`：短信登录（Redis+DB）、支付（API/DB/MQ）、幂等、售后审核、评价隐藏
- `tests/api/endpoints/test_admin_crud.py`：品牌/类目/字典/部门/仓库的 POST/PUT/DELETE + DB 分层

## 6. 接口归属与报告

- `data/endpoint_attribution.yaml`：显式声明「用例 → 主体接口」，避免夹具中的登录/列表/setup 抢占归属；
  参数化用例的归属会按 base nodeid 展开到每个参数项。
- `data/business_taxonomy.yaml`：业务域/模块规则 + 维度覆盖（`dimension_overrides`）。
- 报告效果：同一接口的正向、逆向、边界、异常、安全、幂等、DB、Redis、MQ、大数据量用例聚合在一个接口组内，
  组内按测试大分类再聚合，失败定位直达单个测试点。

## 7. 新接口接入清单（DoD）

1. 从 Controller/DTO/实体提取契约，确认必填、枚举、边界、错误码；
2. 识别副作用：写表、Redis Key、MQ 事件、状态机；
3. 按模板生成：参数化逆向/边界、API/DB(/MQ/Redis) 正向、独立特殊场景；
4. 补 `data/case_meta.yaml` 元数据（title/verify），方法名带业务前缀且在文件内唯一；
5. 补 `data/endpoint_attribution.yaml` 与 `business_taxonomy.yaml` 维度覆盖；
6. 执行 `scripts/export_cases.py` 注册稳定 ID，评审通过后 `review_cases.py --check --strict-p0`；
7. 单文件跑绿后纳入全量回归；已知缺陷不在新接口场景里强制断言 400，只保留原专项用例与 known_failures 台账；
8. 不清理测试数据（DB/Redis/MQ 证据保留）；会产生 UI 干扰的数据（如顶级类目）通过排序等手段避免污染页面。

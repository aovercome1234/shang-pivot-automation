# 覆盖率与缺陷报告：技术栈、实现思路与底层原理

> 适用版本：2026-10-30（run `20261030-113600`）
> 对应报告：`artifacts/allure-report/ext/index.html`
> 相关脚本：`pytest_automation/scripts/`

---

## 1. 总体定位

扩展报告在 Allure 原生报告之外提供两组业务视图：

- **覆盖率**：从“接口有没有用例”深入到“入口方法 → 链路方法 → 代码行”的覆盖情况；
- **缺陷**：把失败用例转换成可追溯的缺陷单，包含真实失败请求、后端堆栈、最底层代码、Git 作者与提交。

两者都不修改 Allure 原始结果，而是消费 Allure 结果 + 测试埋点 + 源码/调用链 + JaCoCo，生成独立的 JSON 数据与静态页面。

```text
pytest / Playwright
        │
        ├── Allure result JSON ──────────────┐
        ├── case_endpoint_map.json（埋点）    │
        ├── run-manifest.json（run/git）      │
        └── jacoco.xml / jacoco.exec          │
                                              ▼
                          build_api_matrix.py
                          build_coverage_matrix.py
                          build_defects.py
                                              │
                                              ▼
                     ext/data/*.json + ext/index.html
                     defects/<run_id>/*.md|html
```

## 2. 技术栈

| 层 | 技术 | 用途 |
|---|---|---|
| 测试执行 | Python 3.13、pytest 8、pytest-xdist、requests | API/UI 用例、并行、重试 |
| 浏览器 | Playwright（Chromium / Firefox） | UI 自动化 |
| 报告 | Allure 2.35.1 | 原始结果、附件、深链、历史趋势 |
| 扩展 UI | HTML5 + CSS3 + 原生 JavaScript（无框架） | 多视图、抽屉、悬浮、下钻 |
| 后端 | Java 21、Spring Boot 4、MyBatis-Plus | 被测系统 |
| 中间件 | PostgreSQL 16、Redis 7、RabbitMQ 3.13 | 数据、缓存、MQ |
| 覆盖率 | JaCoCo 0.8.12（agent + CLI） | 运行时类/方法/行覆盖 |
| 静态分析 | 自研 call-graph、Java 源码轻量解析 | 接口调用链、方法链 |
| 数据库访问 | psycopg2 | DB 落库断言、基线指纹 |
| Redis/MQ 测试 | redis-py、pika | 缓存状态、事件消费 |
| 调度 | Bash + GitHub Actions | 夜间回归、选测、归档 |
| 版本溯源 | Git（log / blame / branch -r） | 缺陷代码作者与提交 |

扩展页没有使用 Vue/React，原因是它需要作为纯静态文件随 Allure 报告一起发布，不能依赖构建产物；hash 路由 + manifest 已足够支撑多视图。

## 4. 覆盖率 Tab

### 4.1 数据流

```text
Allure results + case_endpoint_map
        │
        ▼
api-matrix.json（每接口的测试点/状态/请求响应/失败日志）
        │
        ├── endpoint-model.json      接口全集
        ├── call-graph.json          静态调用链
        ├── write-contracts.json     写接口 DB 契约
        ├── jacoco.xml               方法/行覆盖
        └── 源码                      方法体/行号
        │
        ▼
coverage.json
  ├── summary            接口/DB/组件/方法/链路汇总
  ├── interfaces[]       每个接口一行
  ├── jacocoClasses{}    类 → 方法 → 行状态
```

### 4.2 接口覆盖率

```text
接口覆盖率 = 至少一条用例触达的接口数 / 接口总数
```

- “触达”来自 ApiClient 运行期埋点，不依赖人工维护映射；
- 夹具中的登录等调用记录在 `setup` 阶段，单独用于兜底归属；
- 当前：**135 / 135 = 100%**。

### 4.3 请求方式校验

- 端点模型定义 `METHOD /path`；
- 用例实际请求方法由 recorder 记录；
- 两者一致记为“已校验”；
- 当前 135/135。

### 4.4 DB 落库断言：三态

| 状态 | 条件 | 展示 |
|---|---|---|
| 已覆盖 | 写接口有契约，测试文件包含 `verify_write` / `verify_deleted` | 已覆盖 |
| 不适用 | 认证/令牌/预签名等无业务表写入 | 不适用 + 悬浮原因 |
| 待补 | 有用例触达，但没有落库断言 | 待补 |

判定：

```python
is_write = method in ("POST", "PUT", "DELETE")
db_checked = is_write and contracts[endpoint]["tests"]
if db_checked: "covered"
elif db_exemption(path): "not_applicable"
else: "missing"
```

`db_exemption` 当前包含：

- `/admin/auth/login|logout|refresh`
- `/api/auth/login|logout|refresh|phone|sms/send`
- `/files/presign`

KPI 使用“适用写接口”作为分母：

```text
33 / 68 = 48.5%
78 个写接口 - 10 个不适用 = 68
```

底层校验不是“接口返回 200”，而是：

1. `verify_write` 通过响应 ID / 路径 ID / 自然键定位刚写入行；
2. 按契约逐字段比较类型：Long→String、Decimal→数值、JSONB→JSON、bool；
3. 删除类 `verify_deleted` 检查 `deleted=true` 或物理删除。

### 4.5 Redis / MQ 组件校验

当前组件相关端点：

| 组件 | 端点 |
|---|---|
| Redis | 管理端登录/退出/刷新、会员登录/退出/刷新、验证码、手机号别名登录 |
| MQ | `POST /api/payment/sandbox`（ORDER_PAID） |

判定：

```text
组件覆盖率 = 有 Redis/MQ 断言的组件接口 / 组件相关接口
当前 9 / 9
```

断言不是看响应，而是直接读中间件事实：

- Redis：`sms:phone:*` TTL、`sms:cooldown:*`、`login:fail:*`、`jwt:blacklist:*`；
- MQ：`commerce.order_event_log` 行、重复投递幂等、DLQ 深度。

### 4.6 方法级调用链

#### 4.6.1 静态边

`call-graph.json` 提供：

- `endpoint → controller + method`
- `endpoint → service.method`（`calls` 边的 `detail`，如 `afterSaleService.audit`）
- `service → mapper`
- `mapper → table`

#### 4.6.2 源码补全

`build_coverage_matrix.py` 做轻量 Java 解析：

1. 字段注入：`private final AfterSaleService afterSaleService;` → `afterSaleService → AfterSaleService`；
2. 方法声明：正则定位 + 大括号配平，截取方法体与方法起始行；
3. 调用：`var.method(`，用字段类型还原 `Class#method`；
4. Service 方法递归解析（深度 ≤ 2），Mapper 方法通过 call-graph 边挂到表；
5. 去重并按“入口 → 底层”排序。

示例：

```text
AfterSaleController#audit
  → AfterSaleService#audit
  → AfterSaleMapper#updateById
  → commerce.after_sale
  → commerce.order
```

#### 4.6.3 方法覆盖

从 JaCoCo XML 读取：

```xml
<method name="audit">
  <counter type="LINE" covered="4" missed="12"/>
</method>
```

状态：

- `covered`：有覆盖行且无未覆盖行；
- `partial`：既有覆盖行也有未覆盖行；
- `uncovered`：0 覆盖行；
- `unknown`：Mapper/第三方类，无采集数据。

接口行：

```text
方法 2 / 3
```

KPI：

```text
链路方法覆盖 = 有覆盖行的方法数 / 链路方法总数
当前 230 / 465 = 49.5%
```

#### 4.6.4 逐行覆盖

JaCoCo XML 的 `<sourcefile><line>`：

- `ci`：covered instructions
- `mi`：missed instructions

结合源码方法起止行，生成：

```json
{"nr": 49, "code": "if (failCount != null ...)", "status": "uncovered"}
```

状态：

- `ci>0 && mi==0` → covered
- `ci>0 && mi>0` → partial
- `ci==0 && mi>0` → uncovered
- 无计数器（声明/括号/空行）→ unknown

### 4.7 JaCoCo 采集

```text
start_backend_jacoco.sh
  → java -javaagent:jacocoagent.jar=output=tcpserver,port=6300
  → pytest -m api
  → jacoco_dump.sh --reset
  → jacoco_report.py
      → jacococli report
      → jacoco.csv / jacoco.xml / jacoco.html
      → summary.json
  → build_coverage_matrix.py
  → allure_report.sh 复制到 report/jacoco 与 report/ext/jacoco
```

细节：

- 只统计 `includes=com.shangpivot.*`；
- Spring Boot fat jar 的 class 来自 `BOOT-INF/classes` 与嵌套 `shang-*.jar`；
- `tcpserver` 支持运行时 dump/reset；
- 报告链接统一为 `ext/jacoco/html/...`，避免根路径差异 404；
- 当前行覆盖 **72.99%（2421/3317）**。

### 4.8 补充建议

对 `partial` / `uncovered` 方法生成：

```text
补充 AfterSaleService#audit 的未覆盖分支/异常用例
```

建议只表示“代码未被完全执行”，不等于业务优先级；按接口展示在「补充建议」列。

### 4.9 边界与限制

- 接口/链路是**静态可达**：有测试点即链路节点算覆盖；
- JaCoCo 是**整轮运行**覆盖，不是单接口归属；
- 源码解析是轻量正则，不处理反射/动态代理/重载歧义；
- 方法覆盖包含 partial；建议以未覆盖行为主；
- DB/组件状态是静态判定，最终断言仍以用例为准。

## 5. 缺陷 Tab

### 5.1 数据流

```text
Allure results
  → 按 nodeid 去重
  → 失败测试点
  → 解析「失败依据」附件
      → 真实最后请求 METHOD path
      → HTTP 状态
      → 响应体 code/traceId
  → 选择 500 日志附件
  → 堆栈定位最底层应用帧
  → 路径归一为端点模板
  → Git blame 作者
  → defects/<run>/<id>.md|html
  → ext/data/defects.json
```

### 5.2 为什么之前都显示入口

两个根因：

1. **多接口用例取错响应**
   用例先发货（200）再售后（500），原逻辑用接口明细的最后一个响应，把缺陷归到发货接口，只能定位 Controller。
2. **真实路径未归一**
   `/admin/after-sales/abc/audit` 与模板 `/admin/after-sales/{id}/audit` 精确匹配失败，退化为入口。

修复：

- 从 Allure「失败依据」提取真实失败请求/状态/traceId；
- 用 `{param}` 正则把真实路径归一为端点模板；
- 后端日志额外读取 `backend*.out`（JaCoCo 启动时堆栈在 stdout）。

### 5.3 堆栈定位

正则：

```regex
at (com\.shangpivot\.[\w.$]+)\((File\.java):(\d+)\)
```

过滤：

- `GlobalExceptionHandler`
- `JwtAuthFilter`
- `AccessLogFilter`
- `.exception.` / `.filter.` 包

选择：

- 堆栈自上而下，第一个非框架应用帧 = 最底层应用代码；
- 反向遍历得到入口 → 底层调用链；
- 无应用帧时按端点映射 Controller，并标记「入口」。

入口是真实结论的场景：

- 路径参数 `abc → Long` 在参数解析阶段失败；
- 畸形 JSON 在反序列化阶段失败；
- Controller 尚未进入，不存在更底层业务代码。

业务异常会落到 Service：

| 缺陷 | 定位 |
|---|---|
| 售后原因 513 | `AfterSaleService#apply` |
| 收货人姓名 65 | `AddressService#create` |
| 空请求体 | `ProductService#create` |

### 5.4 Git 溯源

详情页展示：

- 仓库：`remote.origin.url` → HTTPS；
- 本地分支；
- 远端包含该提交的分支：`git branch -r --contains`；
- 运行 Commit；
- 该行最后修改 Commit：`git blame --line-porcelain -L n,n`；
- 作者、邮箱、提交时间；
- 文件行链接（按 blame commit，避免分支漂移）。

支持：

- `git@host:group/repo.git`
- `ssh://git@host/group/repo.git`
- HTTPS

GitLab 使用 `/-/blob/`、`/-/commit/`；其他平台使用 `/blob/`、`/commit/`。

### 5.5 缺陷单输出

| 产物 | 用途 |
|---|---|
| `defects/<run_id>/<id>.md` | 仓库归档、禅道适配 |
| `defects/<run_id>/<id>.html` | 报告内查看，UTF-8，避免 `.md` 乱码 |
| `ext/data/defects.json` | 列表数据 |

详情顺序：

1. 代码来源（仓库/分支/Commit/作者）
2. 代码调用链路
3. 具体代码

缺陷 ID：

```text
sha1(case_id + 失败摘要前 120 字)[:8]
```

用于同一轮/跨轮去重。

### 5.6 边界

- 日志缺失时只能端点映射，可能停在 Controller；
- 堆栈截断到 160 行时可能找不到应用帧；
- blame 依赖本地工作区与运行 commit 一致；
- 私有仓库链接需要登录；
- 同一用例多个接口失败按 nodeid 去重，只生成一条缺陷。
